# Utility OS: USB-приёмка на WLAN Pi M4+

20 октября 2026, провижинер `wlanpi-da2`; пользователь подключил новую плату
с двумя перемычками BOOT/OTG к USB-A провижинера и Gi0/2 коммутатора
`t-iof-sw01-provision`. Обе платы — фиолетовые Mcuzone CM4 WiFi7.
На провижинере BOOT и OTG разомкнуты; на сенсоре обе пары замкнуты.

## Подтверждённая идентичность

| Поле | Значение |
|---|---|
| CPU serial | `10000000e611110c` |
| CM4 | Compute Module 4 Rev 1.0, около 4 GiB RAM |
| Ethernet MAC | `e4:5f:01:62:9f:d3` |
| DHCP | `172.20.108.222`, установленная ОС называлась `wlanpi-fd3` |
| Накопитель | eMMC `/dev/mmcblk0`, 61071360 секторов, 31268536320 байт |
| CID | `150100424a5444345203b3f2c00e7800` |

Это другая плата: предыдущие сетевые тесты проходили на
`100000004acecfa4` / Gi0/5. Переносить её идентичность на USB-сенсор нельзя.

## Найденная проблема и диагностический прогон

После снятия OTG на провижинере появился USB hub и обнаружился `BCM2711 Boot`
с ROM serial `e611110c`. rpiboot передавал вторую ступень, `config.txt`,
`start4.elf` и `fixup4.dat`, затем ждал новое устройство. До ядра, initramfs
и запроса скрипта дело не доходило. Флаг `-l` в службе уже был.

Диагностический `boot.img` FAT32 собран из тех же ядра, initramfs, DTB и
overlays. Изменены только адрес скрипта на отдельный принимающий сведения
сервер и UART-логирование. Ответ скрипта сообщал версию ядра и режим старта;
операций с накопителем и EEPROM в нём не было.

В 09:50:25 UTC rpiboot передал `boot.img`, в 09:50:37 сервер получил:

- серийный номер, MAC и CID из таблицы выше;
- `bootmode=3`, версия Utility OS `2026.10`;
- ядро `6.18.50-cmprovision`, архитектура `aarch64`;
- параметры накопителя и память, температура 43,8 °C.

Подтверждены ROM USB boot, загрузка временного Linux, DHCP/Ethernet и
получение/исполнение HTTP-скрипта. Во время этого теста в приложении осталось
79 записей CMs, активных прошивок не было: это успешная диагностика загрузки,
полная запись и SHA256 ещё не проверены.

В ходе подключения перезапускался также провижинер. Временные systemd-настройки
из `/run` при этом сбрасывались; перед успешным прогоном диагностическая служба
была восстановлена. Это отдельное наблюдение, причина перезапуска не установлена.

## Исправление для обычного запуска

В обеих ОС добавлен отдельный каталог `usb/`: bootstrap `config.txt`,
`bootfiles.bin` и FAT32 `boot.img` с их исходными загрузочными файлами.
Служба rpiboot использует `etc/boot/usb`, dnsmasq продолжает использовать
обычный `etc/boot`. Переключение Utility OS меняет оба пути общей ссылкой.
Накопитель и EEPROM при построении FAT не монтируются; инструменты сборки
нужны только на хосте сборки, готовые образы входят в пакет.

Внутри обычного USB-образа адрес скрипта штатный `/scriptexecute`,
диагностический сервер не используется. Тесты сверяют извлечённые из FAT
файлы с исходными, включая ядро, initramfs и командную строку, и проверяют
повторную сборку и отказ при недостающих исходных файлах.

Проверки после исправления: 130 тестов ОС/упаковки с 567 assertions, затем
полный PHP-набор — 1258 тестов, 4410 assertions, 21 прежний пропуск окружения.
Ошибок нет. В набор входит фактическая сборка FAT и извлечение его файлов,
а также запуск post-image на подготовленном дереве входных файлов.

В 10:07:20 UTC исправленные USB-каталоги, MANIFEST и служба установлены на
`wlanpi-da2` для приёмки. Это изменение файлов тестовой установки поверх
`2.7.0~dev2`, новый пакет и релиз не публиковались. SHA256 всех прежних файлов
сетевой загрузки на стенде перед установкой совпали с локальными; обе ОС
после установки валидны по MANIFEST. Временное ограничение rpiboot по USB serial
`e611110c` направляет следующий прогон только на выбранную плату. Предыдущие
79 записей CMs сохранены без изменений phase и времён запуска/OS check.

## Полный USB-прогон: успешен

После нового полного отключения питания сенсора (USB и PoE/Ethernet) он
загрузился через штатный `etc/boot/usb`. На фактическом стенде использовался
прямой USB-A → USB-C кабель и включённый PoE на Gi0/2; отдельный питаемый USB hub
в этом прогоне не проверялся.

| Этап | Время UTC, 20 октября |
|---|---|
| Первое USB-обнаружение | 10:11:54 |
| Передача 40 MiB boot.img | 10:11:59–10:12:01 |
| Начало записи, проект 3 | 10:12:12 |
| Начало сверки | 10:14:18 |
| Post-install и Done | 10:16:44 |

Записаны и проверены 6211764224 байта образа
`wlanpi-os-26.10-DeadEye-full.img.gz`. Ожидаемый SHA256 распакованного образа:
`4c6d703e710014465306ec66ef0c6f77a7d5b8b558421c501d33460de712477a`.
Сенсор сообщил успешную сверку, журнал содержит
`Provisioning completed. Verification successful.`. Возврат post-install — 0,
агент re-provision установлен. EEPROM сенсора не обновлялась.

Запись заняла 2:06, сверка и завершение — 2:26; от регистрации запуска до
Done — **4:32**, от первого USB-обнаружения — **4:50**. В карточке Utility OS
`2026.10`, OS check `skipped`, в журнале явно указана причина USB boot.
Это ожидаемый результат: загрузка записанной ОС этим проходом не проверяется.

В 10:17:55 восстановлен проект `stage1-test` (id 2); временные подробные логи
и фильтр rpiboot по serial убраны. Штатная служба активна и использует
`etc/boot/usb`. Обе ОС валидны по MANIFEST; остальные 79 записей CMs не
изменили phase и времена запуска/OS check. Всего записей теперь 80.
Сенсор остался во временной ОС, продолжает опрашивать сервер для Identify.

## Загрузка записанной ОС с eMMC: подтверждена

Пользователь полностью отключил сенсор от USB и Ethernet/PoE, снял BOOT и
OTG и вернул только Ethernet/PoE. В 10:23:27 UTC сенсор получил прежний адрес
`172.20.108.222` с именем `wlanpi-fd3`. На Gi0/2 подтверждены гигабитный линк
и единственный MAC `e4:5f:01:62:9f:d3`; USB-устройство сенсора на провижинере
больше не обнаруживается.

В 10:26:23 UTC команда `identify` через установленный ограниченный SSH-ключ
успешно вернула serial `10000000e611110c`, накопитель `/dev/mmcblk0`,
CID `150100424a5444345203b3f2c00e7800` и 61071360 секторов. Перед таким
ответом агент проверяет, что корень текущей системы — второй раздел именно
этого накопителя с ext4. Это подтверждает работу записанной ОС с eMMC
после отключения USB и штатный доступ для re-provision без ввода пароля.
Команда `wipe` не выполнялась.

Вход стандартной учётной записью вернул `password_expired`: образ требует
сменить пароль при первом входе. Пароль и это требование не изменялись.
Ограниченный ключ поддерживает только протокол агента, поэтому версия ядра
установленной ОС и состояние всех её служб отдельно не считывались.

Активных прошивок нет, выбран `stage1-test` (id 2), штатная служба rpiboot
активна с `etc/boot/usb`. Результат автоматического OS check USB-прохода
остаётся `skipped`: последующая отдельная проверка загрузки его не подменяет.

## Остаётся подтвердить

- Приёмка USB с legacy, если она входит в согласованную матрицу; наличие
  проверенного FAT-образа само по себе не означает аппаратного прогона legacy.
- tty2, визуальные LED и одновременный старт нескольких сенсоров остаются
  отдельными пунктами [чек-листа](2026-10-20-usb-tty2-acceptance.md).

Стабильный выпуск не выполнялся.
