## Стенд и границы

Провижинер `wlanpi-da2`, WLAN Pi M4+, обновлён с 2.6.4 до тестовой 2.7.0.
Снимок для отката: `/var/backups/cmprovision/20261019-190631-2.6.4`.
Пользователь подтвердил запись `stage1-test` на CM4 `100000004acecfa4`,

## Исправление и повторный цикл

Коммит `2f65405` освобождает SPI после pre-install, переподключает LED-драйвер,
обновляет имена ACT/PWR и повторно получает helper, если его первоначальная
проверка выполнялась без доступных LED. Неудачная передача GPIO остаётся
повторяемой. Ядро и initramfs не изменены.

Три новых shell-теста воспроизвели ошибку до исправления. Полный PHP-набор после
исправления: **1254 теста, 4368 проверок, 21 прежний пропуск окружения**.
LED/first-boot/docs: 42 теста, 142 проверки; LED/init: 32 теста, 104 проверки.

На простаивающий провижинер установлен `2.7.0~dev2` из `2f65405`, SHA256
`ca4fbc3532514c4a28d3d035cef58a5a92c9bca234a75948e1fa1b46b1b094b5`.
Контрольная сумма шаблона на стенде совпала с исходником; службы активны,
`dpkg --audit` пуст, выбран `scriptexecute64`.

Повторный wipe подтверждён в `16:41:21`, старт — `16:41:56`, запись —
`16:41:58`. Во время записи без ручного вмешательства подтверждены:
SPI освобождён, LED-драйвер подключён, маркер передачи GPIO существует,
helper `check=0`, ACT на timer 50/50 мс, PWR постоянно включён.
За 100 чтений sysfs PWR был включён во всех, ACT сменил состояние 47 раз.
Ошибка GPIO 42 в журнале нового цикла отсутствует.

Проверка началась в `16:44:03`, SHA256 совпал, загрузка установленной ОС началась
в `16:46:30`. OS check прошёл в `16:48:04`: systemd `running`, failed units нет.
Полный цикл — **6:08**, без ручного изменения GPIO. После загрузки работает
один `ledpattern ready` из root-owned `/run/cmprovision-leds.QGRdlT/`, файл
и каталог имеют права 0700, в каталоге только helper. Одноразовые скрипты,
unit и ссылка включения уже удалены; тестовый пакет установлен.

В Identify процесс переключился на `ledpattern identify`; 100 чтений ACT/PWR
дали 100 противоположных состояний и по 14 переходов каждого LED примерно за
две секунды. Отдельная проверка подтвердила возврат в `ready` после Stop до
истечения продлённого срока Identify. Повторное включение без Stop завершилось
автоматически по 30-секундному сроку и тоже вернуло `ready`. На каждой проверке
работал один helper, основной PID службы оставался 1810, время OS check —
`16:48:04`; пакеты, скрипты и отчёт OS check не повторялись.

Итог: 79 записей CMs сохранены, активных прошивок нет, target id 78 — `done`,
другие две платы сохранили время своих запусков и OS check. Проект не изменён.
Выбрана новая Utility OS. nginx, PHP-FPM, DHCP/TFTP, rpiboot, обе очереди и
uplink timer активны, login HTTP 200, `dpkg --audit` пуст. Временные SSH-каталоги

## Параметры загрузки

По настоящим запросам nginx serial, model, storagesize, MAC, CID, CSD,
bootmode `2` и inversejumper `111` совпали с legacy. Запись CMs осталась id 78.
Добавился `uos=2026.10`. `memorysize` — фактический MemTotal ядра: legacy
3 920 160 КиБ, новое ядро 3 886 964 КиБ; приложение в обоих случаях определяет
4 ГБ. Температура первого старта 48,2 °C против 48,7 °C в предыдущем legacy.

## Оставшаяся аппаратная приёмка

Этот прогон не подтверждает запись изменённого EEPROM и возврат настройки,
resume split image после отключения PoE, новый полный цикл под legacy,
сравнение времени от физического включения питания и одновременный старт
нескольких модулей. Отдельные режимы `done`/`fail` не воспроизводились:
нормальный цикл с OS check завершился `ready`. USB boot через rpiboot и tty2
без подходящего подключения не проверены. Визуальное наблюдение LED требует
человека у стенда; здесь подтверждены процессы, триггеры и состояния sysfs.
Слияние, стабильный тег, push и выпуск 2.7.0 не выполнялись.
