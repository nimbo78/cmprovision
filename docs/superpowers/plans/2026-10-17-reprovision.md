# Перепрошивка модуля из веб-интерфейса: разбор и план

Дата: 2026-10-17. Основа: `stage2`, `2a10e46`, приложение 2.6.2.
Исходная [спецификация](../specs/2026-10-15-reprovision-design.md) совпадает с файлом в ветке `wipe-spec` (`9ddf3b7`).

Статус: план принят и реализован в рабочей копии 18 октября 2026 как 2.6.3~dev1. Локальные проверки и сборка пакета завершены; приёмка на настоящем CM4 предстоит. Исходная спека остаётся исторической записью; utility OS имеет отдельный дизайн 2.7.0.

## Результат для оператора

Один модуль, уже загрузившийся в установленную ОС, можно вернуть на перепрошивку из его карточки:

1. Найти адрес на стенде по MAC и проверить доступ сначала ключом провижинера.
2. Если ключ не подходит, принять логин и пароль; при требовании ОС провести смену просроченного пароля.
3. Показать подтверждённые serial, hostname, адрес, диск и проект следующего прогона.
4. После отдельного подтверждения сделать начало выбранного диска незагрузочным и запросить перезагрузку.
5. Дождаться нового обращения модуля за скриптом; дальше работает существующий provisioning.

Это уничтожение загрузочной структуры для повторной прошивки, а не гарантированное удаление всех данных.
Групповое стирание, произвольные IP-адреса и отдельный публичный wipe API не входят в первый выпуск.

## Что необходимо уточнить относительно старой спеки

### 1. Какой диск стирать

Нельзя брать путь только из текущего `$cm->project->storage`: проект мог быть отредактирован после прошивки. Нельзя путать его с `$cm->storage`, где хранится ёмкость.

Предлагается отдельное nullable-поле `cms.provisioning_storage`, записываемое при начале прогона вместе с проектом. При возобновлении записи путь должен совпадать с сохранённым, иначе продолжение запрещается.

В агенте путь фиксируется при установке. Ответ `identify` дополняется версией протокола и сведениями о диске. В обоих способах входа перед стиранием на самом модуле проверяются serial, существование целого блочного устройства и его соответствие подтверждённому носителю. Непустой CID используется как дополнительная проверка для eMMC/SD, когда он доступен; для первого выпуска фиксируется поддерживаемый профиль носителя.

Для старых записей без снимка пути нужен удалённый read-only probe: определить родительский диск корневого раздела, показать его оператору и проверить поддерживаемую схему. При неоднозначности отказать с причиной. Тихий fallback на `/dev/mmcblk0` из старой спеки убрать. Сценарий старого sensor1 сохраняется, если его eMMC определяется однозначно.

### 2. Между Check и Wipe состояние меняется

Проверка доступа не выдаёт бессрочное разрешение. Перед действием повторно прочитать модуль, DHCP-аренду, активный проект и его конфигурацию; повторно проверить удалённую идентичность и диск.

Проверка принадлежит конкретным пользователю, веб-сессии, модулю и операции. Изменение адреса, диска, проекта или начало другого прогона отменяет подтверждение. Отдельная блокировка только вокруг каждого HTTP-запроса не решает повторное использование старого результата проверки.

Для согласования SSH-стирания, PoE и старта прогона нужен общий `ModuleOperationLock`. Блокировки брать в одном порядке, а состояние перечитывать после захвата. Долгую SQLite-транзакцию на время SSH не держать.

### 3. Проект при следующей загрузке

Сейчас `startProvisoning()` выбирает глобальный активный проект, а `ProjectActivator` публикует общий `public/uploads/pieeprom.bin`. Обещать модулю зафиксированный проект, просто подменив `project_id`, нельзя.

Предложение для первого выпуска: сохранять намерение перепрошивки с id и отпечатком подтверждённой конфигурации. Перед wipe и при следующем старте сверять его с активным проектом. Если проект изменился, не прошивать неожиданным проектом: показать причину и потребовать повторного выбора оператором. Не вводить в этом выпуске отдельную очередь проектов для каждого модуля.

Правило действует и на редактирование того же проекта, его образа, скриптов и EEPROM. Отпечаток должен отражать фактические параметры, а не только `updated_at` проекта. Неопределённое/просроченное намерение после отправленной команды не должно молча превращаться в обычный автоматический старт.

### 4. Результат стирания и повтор команды

Разрыв SSH после отправки команды означает неизвестный результат. Он не доказывает ни успех, ни отказ.

Нужны состояния «проверено», «команда отправляется», «стирание подтверждено, ждём загрузку», «результат неизвестен», «новый прогон начался», «отказ». Команда не повторяется автоматически. Повторный клик с тем же id операции возвращает её состояние.

Агент проверяет результат записи и синхронизации до положительного ответа. Фоновая перезагрузка отсоединяет stdin/stdout/stderr от SSH; иначе завершение команды может зависнуть. Успех нового прогона подтверждает сервер, когда реально получает запрос модуля.

Перед намеренной перепрошивкой необходимо сбросить отметки resume так, чтобы следующий старт шёл с начала. При неопределённом результате их нельзя оставить основанием для продолжения старой записи.

### 5. Установка агента и SSH

Наличие `/etc/ssh` и ключа не доказывает, что вход root разрешён или sshd запущен. Установка не должна безоговорочно менять SSH-политику целевого образа. Результаты «файлы установлены» и «доступ по ключу проверен» различаются.

Формат `restrict,command="..."` подходит для ограничения ключа: запрещает PTY и forwarding, а агент получает исходную команду через `SSH_ORIGINAL_COMMAND`. Однако `PermitRootLogin=no` запрещает такой вход; совместимость конкретного WLAN Pi OS нужно проверить. См. [authorized_keys](https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT) и [PermitRootLogin](https://man.openbsd.org/sshd_config.5#PermitRootLogin).

Установщик должен работать синхронно, освобождать mount при ошибке, сохранять чужие ключи и не добавлять дубликатов. Не следовать symlink за пределы смонтированного корня при записи агента и authorized_keys. Ошибка установки остаётся нефатальной, как в исходной спеке, но имеет явный результат в журнале.

Создание ключа провижинера — под блокировкой с атомарной публикацией пары, каталог 0700, приватный файл 0600. Отсутствующий public key можно восстановить из существующего private key; не менять действующий private key молча.

### 6. Пароли и просроченный пароль

Повторить уже используемый подход WifiSettings: пароль живёт в Alpine, передаётся аргументом действия и сразу очищается; он не становится публичным свойством Livewire.

Между шагами — зашифрованный cache entry на 120 секунд, привязанный к пользователю, веб-сессии и операции. В БД операции паролей нет. Отмена, успех и истечение срока очищают доступ к секретам. Открытый id операции не является авторизацией; приватное свойство компонента само по себе не обеспечивает сохранение состояния между запросами Livewire.

Для SSH — argv-массив, фиксированный helper, секреты вне аргументов команд и исключений. Ошибки процесса/вывод PAM проходят ограничение длины и удаление секретов; сырые исключения с окружением не логировать. Сначала пробовать `sudo -n` для NOPASSWD, иначе проверять пароль через stdin без зависимости от прошлого sudo timestamp.

Принудительный askpass предусмотрен OpenSSH: [SSH_ASKPASS_REQUIRE](https://man.openbsd.org/ssh.1#SSH_ASKPASS_REQUIRE). Смена просроченного пароля требует отдельного проверяемого обмена с PAM. Не считать, что заранее отправленные три строки и поиск одной английской фразы работают на всех образах. После смены нужен новый успешный вход и проверка sudo; при неоднозначном ответе не переходить к wipe.

Сверка serial защищает от случайного выбора другого модуля, но не аутентифицирует злонамеренный SSH-сервер. Предложение: временный known_hosts на одну операцию, сохранение ключа при первом подключении и обязательное совпадение на последующих шагах. Это не решает доверие при первом контакте; остаётся исходное допущение об изолированном стенде. Политика OpenSSH описана в [StrictHostKeyChecking](https://man.openbsd.org/ssh_config.5#StrictHostKeyChecking).

## Порядок реализации и критерии завершения

### Этап 1. Проверить SSH до большого интерфейса

Поднять отдельный тестовый sshd на loopback в изолированной среде. Проверить ключ с forced command, пароль, NOPASSWD, sudo с паролем, отказ sudo, просроченный пароль и отклонение нового пароля. Зафиксировать поддерживаемый диалог PAM и таймауты. Все действия пока без стирания дисков.

Готово, когда есть повторяемые интеграционные тесты реального SSH, а не только mock с желаемыми строками. При необходимости интерактивного process I/O выбрать его после этого эксперимента; требование «без новой зависимости» пока является целью, а не доказанным результатом.

### Этап 2. Данные, адрес и контракт операции

Миграции, снимок пути диска, опция проекта/API, SensorAddress, хранилище операции и секретов. Общая блокировка с согласованным порядком захвата. Проверки старых записей без пути, истёкших аренд, двух операторов и смены проекта.

Готово, когда ни адрес, ни диск, ни подтверждение нельзя произвольно передать через публичное действие Livewire; неподдерживаемые старые записи дают понятный отказ.

### Этап 3. Агент и интеграция в provisioning

Генерация ключа и агента, установка в смонтированный образ, строгий разбор команд, повторная удалённая проверка цели, подтверждение результата записи. Обе ветки генерации скрипта используют один генератор. Ошибки установки не ломают обычную прошивку.

Готово, когда тесты настоящего sh с подставными устройствами/командами доказывают: неверный или пустой serial, неправильный диск и ошибка записи никогда не приводят к перезагрузке; успешная запись затрагивает только разрешённый диапазон.

### Этап 4. Полный двухшаговый сценарий на сервере

Reprovision связывает SSH, проверку цели, одноразовое подтверждение и ожидание нового старта. Перед отправкой создаётся намерение; повторы HTTP не повторяют команду. Ошибки и неизвестный результат записываются отдельно. При новом запросе модуля проверяется проект, сбрасывается resume и устанавливается связь с новым прогоном.

Готово, когда воспроизводятся гонки двух операторов, PoE, смены проекта, DHCP-адреса, старта provisioning и обрыва SSH после отправки команды.

### Этап 5. Диалог и публичный ключ в Settings

Реальные состояния диалога: проверка, запрос учётки, смена пароля, готовность, отправка, ожидание, ошибка/неизвестный результат. Проверки на сервере повторяются независимо от disabled-кнопок. Нет сети/активного проекта/поддерживаемого диска — видимая причина. Закрытие окна до отправки очищает секреты; после отправки сохраняется статус операции.

Готово, когда Playwright проходит сценарий с fake SSH в светлой/тёмной теме и на телефоне, а тесты Livewire не находят пароли в snapshot, HTML, ошибках и журналах.

### Этап 6. Пакет, восстановление и приёмка на CM4

Проверить установку/обновление пакета, владельца и права ключа, обычный backup и restore --data-only. Выполнить регрессию PHP/JS и тесты shell.

На отдельно согласованном тестовом модуле: старый образ без агента → доступ по учётке → новый прогон с установкой агента → повтор по ключу. Отдельно проверить смену просроченного пароля. Проверить сочетания с OS check и split/resume, а также фактическую загрузку по сети после удаления первого MiB для поддерживаемой разметки/BOOT_ORDER. Не объявлять поддержку любой GPT/USB/NVMe-конфигурации по результату только одного eMMC-образа.

Обновить руководство по операциям и галерею после появления работающего диалога. Номер релиза и положение относительно utility OS определить перед выпуском.

- `ReprovisionTest`: два оператора, прямой вызов wipe без check, старое подтверждение, смена IP/носителя/проекта, активная запись/firstboot, неизвестный результат, отсутствие повторной команды.

- `ReprovisionIntentTest`: новый старт, сменившийся проект, сброс resume, перезапуск сервера, неопределённое/просроченное намерение.
- Регрессия `OsCheckModuleScriptTest`, image-write/resume, `PoeRestartTest`, API permissions; проверка backup/restore ключа.

## Рекомендуемый первый шаг

Начать с небольшого проверяемого SSH-адаптера и тестового sshd: именно связка просроченного пароля, PAM, sudo и отсутствия секретов в ответах содержит больше всего ещё не проверенных предположений. Затем реализовать полный путь по ключу, добавить fallback по учётке и интегрировать диалог. Все три пользовательских сценария остаются частью итогового объёма.
