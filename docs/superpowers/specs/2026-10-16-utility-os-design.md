# Своя утилитарная ОС (2.7.0)

Дата: 2026-10-16. Раздел 3 ROADMAP («Из upstream, дальше»): «Новая утилитарная ОС `scriptexecute`» (#73, #47, #26).

## Зачем

Модуль прошивается из утилитарной ОС, которую грузит по сети (TFTP от dnsmasq) или по USB (`rpiboot`). Сейчас это готовые
файлы из `scriptexecute/`, собранные в 2020–2022 годах проектом raspberrypi/scriptexecutor. Этот проект заброшен: последний
коммит `640d749` от ноября 2022, buildroot 2019.11.1 лежит в нём тарболом и на современных системах не собирается
(issue #1).

Что в нашей `scriptexecute/`:
- 32-битное ядро `kernel.img`, Linux 5.4 (ветка `rpi-5.4.y` без закрепления), пользовательская часть ARMv6 на uClibc;
- BusyBox 1.31.1, curl 7.66 без TLS, e2fsprogs 1.45.4, flashrom 1.1, parted 3.2, rpi-userland (`vcgencmd`);
- загрузочные файлы из raspberrypi/firmware `995e9f03` (март 2022).

Почему это мешает:
- `resize2fs` 1.45 не справляется с файловыми системами новых образов (#73);
- CM5 нужны 64-битное ядро от 6.12 и свежая прошивка;
- 10 октября 2026 da2 переустановлен с `rpiboot 20261005`. С тега usbboot 20261002 `rpiboot` больше не содержит встроенного
  `bootcode4.bin` и, получив `-d <каталог>`, ищет его только там. В `scriptexecute/` его нет, поэтому загрузка CM4 по USB на
  da2, скорее всего, уже не работает. Сетевую загрузку это не трогает.

Готовые форки не подходят:
- ysi-camerona и ZiathLtd/scriptexecutor — buildroot 2024.08.1, но пользовательская часть по-прежнему 32-битная, а ссылка на
  ядро битая (`6.6.y` вместо `rpi-6.6.y`);
- ZiathLtd/cmprovision кладёт ядро Raspberry Pi OS 6.12.47 к 32-битному initramfs, где SPI собран модулем: `flashrom`,
  скорее всего, не найдёт `/dev/spidev0.0`;
- Dude90 `cm5_support` — только CM5.

Успех выглядит так:
- новая ОС собирается одной командой из закреплённых версий, одинаково в WSL-стенде и в GitHub Actions;
- версии обновляет одна команда, а раз в месяц CI сам предлагает PR с новыми версиями;
- пакет везёт старую и новую ОС, оператор переключает их в Settings и так же переключает обратно;
- скрипт модуля не меняется, а всё, что он делает сейчас, работает и под новой ОС.

## Решения пользователя

- Подход A: своё BR2_EXTERNAL-дерево на buildroot LTS 2025.02.x, arm64.
- Одна команда сборки для WSL-стенда и GitHub Actions. На самом провижинере не собираем: 4–8 часов, 15–20 ГБ на eMMC и
  помеха прошивке.
- Актуальность: команда обновления для ручного запуска и она же в CI раз в месяц с PR.
- Обе ОС в пакете и переключатель в Settings.
- CM5 — отдельным выпуском, но сборка его закладывает.
- `bootcode4.bin` для `rpiboot` чинится в этой работе, для обеих ОС.
- Одновременно грузятся 10–15 модулей, не 48.

## Не входит

- CM5: деревья устройств bcm2712, его драйверы, сигнатура «RPi5» в option 97 у dnsmasq, `bootcode5.bin`, EEPROM 2712
  через `/dev/spidev10.0`. Отдельный выпуск.
- Удаление старой ОС — отдельным выпуском, когда новая отработает пару выпусков.
- TLS в curl: в старой его нет, на стенде нет интернета.
- Изменения скрипта модуля (`scriptexecute.blade.php` и его частей): договор с ОС остаётся прежним.
- `ledpattern` внутри новой ОС: модуль по-прежнему качает 32-битный помощник с сервера, ядро запускает его через
  совместимость с 32 битами.
- Режимы старого init, которые нам не нужны: скрипт с NFS-шары и USB-гаджет с IPv6 link-local (он был для CM3).
- Подписанная загрузка (secure boot).

Ядро и `raspberrypi/utils` buildroot берёт из git неглубоким клоном (тег ядра, коммит utils) и сам собирает из них

качаем отдельные файлы `boot/` по тегу, каждый со своим SHA256; так же `bootcode4.bin` из usbboot.

```
  board/cmprovision/

    post-image.sh                 каталог для TFTP: ядро, initramfs, загрузочные файлы, MANIFEST
    config.txt, cmdline.txt       шаблоны (версия ОС подставляется)
  package/
    rpi-boot-files/               start4.elf, fixup4.dat из релиза прошивки
    raspberrypi-utils/            vcgencmd, vcmailbox, dtoverlay, dtmerge, pinctrl

  update.sh                       подъём версий
  test.sh                         проверки собранного, с тестовым сервером для QEMU
scriptexecute64/                  собранная новая ОС (коммитится)
scriptexecute/                    старая ОС, плюс bootcode4.bin и MANIFEST (написан вручную)

```

`versions.env` — единственное место с версиями и хэшами. `build.sh` подставляет их в конфигурацию buildroot и в файлы хэшей
наших пакетов. `update.sh` переписывает только `versions.env`.

Собранные файлы коммитятся, как сейчас `scriptexecute/` и `public/tools/ledpattern`: пакет собирается без сети. Новый
коммит с бинарниками появляется, только когда новая версия ОС принята (несколько раз в год, около 15 МБ).

## Что в новой ОС

### Ядро

- Исходники raspberrypi/linux по тегу `stable_*`, arm64 `bcm2711_defconfig` и наш `linux.fragment`.
- Модулей в ОС нет: всё, что ей нужно, встроено (`=y`), остальное в образ не попадает. Поддержку модулей
  (`CONFIG_MODULES`) при этом не выключаем: без неё Kconfig делает встроенным каждое `=m` из `bcm2711_defconfig` (сотни
  драйверов: Wi-Fi, звук, камера…). Ядро раздулось бы, а каждая новая версия добавляла бы своё. Модули собираются, и
  `post-build.sh` убирает их из образа; сборка ядра от этого дольше на 20–40 минут без кэша.
- Обязательно встроены (`=y`; проверка сборки сверяет):
  - SPI контроллера BCM2835 и `spidev` (`flashrom -p linux_spi:dev=/dev/spidev0.0`);
  - доступ к GPIO для `pinctrl` (`/dev/gpiomem*`);
  - канал к прошивке для `vcgencmd` (`/dev/vcio`);
  - `leds-gpio` и триггеры timer, heartbeat, default-on;
  - eMMC контроллера BCM2711, ext4, vfat;
  - GENET и PHY Broadcom (Ethernet);
  - консоль на экране: кадровый буфер прошивки и консоль на нём (туда init и скрипт пишут ход и причины отказа);
  - USB (dwc2, XHCI) и клавиатура (HID) — для отладочной оболочки на tty2;
  - devtmpfs, initramfs с xz, совместимость с 32-битными программами (`COMPAT`) для `ledpattern`;
  - virtio-mmio и virtio-net: на Pi их устройств нет, а проверка в QEMU грузит этим же ядром.
- `LOCALVERSION="-cmprovision"`, образ `Image.gz` → `kernel8.img`.
- CM5 позже грузит тот же `kernel8.img` (без `kernel_2712.img` прошивка CM5 берёт его): добавятся деревья устройств bcm2712,
  драйверы RP1 и MACB.

### Каталог для TFTP (`scriptexecute64/`)

- `kernel8.img`, `scriptexecute.img` (cpio с xz);
- `start4.elf`, `fixup4.dat` из релиза прошивки;
- `bcm2711-rpi-cm4.dtb`, `bcm2711-rpi-4-b.dtb`, `bcm2711-rpi-400.dtb` и `overlays/` с `spi-gpio40-45.dtbo` и `dwc2.dtbo`,
  собранные из того же ядра;
- `bootcode4.bin` для `rpiboot`;
- `config.txt` — как у старой (`gpio=5,13,21=pu`, `[pi4]`: `dtoverlay=dwc2`, `dtparam=audio=off`,
  `dtoverlay=spi-gpio40-45`), плюс явные `arm_64bit=1` и `initramfs scriptexecute.img followkernel`;
- `cmdline.txt`: те же `readjumper script=…` и подстановки, что у старой, и в конце адреса `&uos=<версия>`;
- `MANIFEST`: версия ОС, все версии из `versions.env`, размер и SHA256 каждого файла.

### Пользовательская часть

BusyBox 1.37 (ash, init, getty, udhcpc, dd, gzip, xz, bunzip2, base64, awk, sed, grep, tr, cmp, od, wc, tail, tee,
timeout, sha256sum, mount), curl 8.22 без TLS, e2fsprogs 1.47, flashrom 1.5, parted, util-linux, mmc-utils, `bsdtar`,
sysfsutils; из `raspberrypi/utils` — `vcgencmd`, `vcmailbox`, `dtoverlay`, `dtmerge` и `pinctrl`.

**Правило совместимости.** Каждая команда из `legacy-commands.txt` есть в новой ОС. Список снят один раз с образа старой ОС
(и апплеты BusyBox, и отдельные программы). Из него убраны только камера и мультимедиа rpi-userland (`raspistill`,
`raspivid`, `mmal_vc_diag`, `containers_*`, `tvservice`, `vchiq_test` и подобные): скрипты прошивки их не вызывают.

**Вывод программ — тоже договор.** Сервер разбирает, что пишут программы модуля:
- `ScriptExecuteController::WRITE_FAILURE_HINTS` — сообщения распаковщиков (gzip, xz, bzip2) и `dd`;
- `write.blade.php` — строку `dd` «N+M records in»;
- скрипт прошивки EEPROM ищет `identical` в выводе flashrom, `FailureAdvice` — `No EEPROM/flash device found`, а у
  `sha256sum -c` — `FAILED` и `did NOT match`.

Эти сообщения новой ОС снимает проверка в QEMU (см. «Проверки»), а тест приложения сверяет их с шаблонами сервера.

**Консоль — как у старой.** Ход загрузки и скрипта — на экране (tty1). Отладочная оболочка — на tty2 (`getty`, вход root
без пароля). Это только физический доступ: клавиатура и экран модуля. Служб входа по сети (telnetd, sshd) в ОС нет.

### Init (`S99scriptexec`, POSIX sh)

Повторяет init старой ОС (`etc/init.d/S99scriptexec` из её `scriptexecute.img`) без bash-измов и без `set -e`, который
обрывал старый на любой ошибке.

1. Разбирает `/proc/cmdline`: шаблон `script=` и флаг `readjumper`.
2. Гасит ACT (`led0` или `ACT`: имя зависит от ядра), монтирует debugfs, запускает `getty` на tty2.
3. Ждёт появления `eth0` и несущей, печатая на консоль, чего ждёт; поднимает интерфейс.
4. Получает адрес `udhcpc -i eth0`. udhcpc остаётся работать и продлевает аренду, как у старой.
5. Подставляет значения в шаблон. Источники и форматы — как у старой: сервер узнаёт модуль по серийному номеру, и другой
   формат сделал бы из него новую запись.

| Подстановка | Откуда |
|---|---|
| `{serial}` | строка `Serial` из `/proc/cpuinfo`, как у старой; если её нет — `/proc/device-tree/serial-number` |
| `{model}` | `/proc/device-tree/model` без нулевого байта, пробелы → `+` |
| `{storagesize}` | `/sys/block/mmcblk0/size` (секторы по 512 байт) |
| `{cid}`, `{csd}` | `/sys/block/mmcblk0/device/cid`, `…/csd` |
| `{bootmode}` | четвёртый байт `/proc/device-tree/chosen/bootloader/boot-mode` числом (`od -An -tu1 -j3`) |
| `{memorysize}` | MemTotal из `/proc/meminfo`, в кБ |
| `{temp}` | `vcgencmd measure_temp` без `temp=`; если не ответил — `/sys/class/thermal/thermal_zone0/temp` в том же виде (`48.3'C`) |
| `{mac}` | `/sys/class/net/eth0/address` |
| `{jumper}` | только с `readjumper`: уровни GPIO 5, 13, 21 подряд (`111`), через `pinctrl lev` |

   Источника нет — значение пустое, как у старой. Перемычки старая читала через `/sys/class/gpio/export` с номерами 5, 13,
   21. С ядра 6.6 номера GPIO в sysfs сдвинуты (контроллер начинается не с 0), поэтому новая читает уровни `pinctrl`.
   Подтяжки, как и раньше, ставит `config.txt`.
6. Качает скрипт в `/tmp/script` (`curl -g --retry 10 --retry-connrefused`, как старая) и смотрит код ответа:
   - 200 — запускает `sh /tmp/script`;
   - нет связи или 5xx — повторяет через 10 секунд. Например, 502, пока php-fpm перезапускается при обновлении пакета:
     старая исполнила бы страницу ошибки nginx как скрипт и встала;
   - другой код — печатает его на консоль и останавливается.

   Отказы самого приложения сервер отдаёт скриптом с кодом 200, и модуль исполняет их, как раньше.
7. Если скрипт вернулся (обычно он не возвращается: `finish` ждёт оператора), печатает код выхода на консоль и больше
   ничего не делает: повтор мог бы начать прошивку заново.

## Обновление версий (`tools/utility-os/update.sh`)

1. Находит новейшее:
   - точечный релиз buildroot в текущей LTS-ветке (`git ls-remote --tags`);
   - последний тег ядра `stable_*` (`git ls-remote`) и версию Linux в его `Makefile`;
   - последний релиз прошивки (GitHub API);
   - последний коммит `raspberrypi/utils`;
   - последний тег usbboot.
2. Скачивает, считает SHA256, переписывает `versions.env`.
3. Поднимает версию ОС: год и месяц (`2026.11`), при второй версии за месяц — `2026.11.1`.
4. Печатает таблицу «было → стало».

С `--check` команда только сообщает, есть ли новое (код выхода 0 — нет, 10 — есть).

Политика:
- buildroot автоматически — только в пределах LTS-ветки. Переход на следующую LTS (2027.02) делается вручную; команда о нём
  напоминает.
- Ядро, прошивка, `raspberrypi/utils`, usbboot — до последних.
- Хэши строгие: файл по закреплённой версии, скачавшийся с другим SHA256, останавливает сборку.

## Сборка (`tools/utility-os/build.sh`)

- Хост: Debian или Ubuntu x86_64 (WSL-стенд, раннер `ubuntu-24.04` в GitHub). Скрипт проверяет нужные пакеты хоста (и
  `qemu-system-aarch64` для проверок) и говорит, чего не хватает.
- Скачивает тарбол buildroot из `versions.env`, сверяет SHA256, распаковывает в каталог вне репозитория.
- `make BR2_EXTERNAL=utility-os cmprovision_defconfig`, затем подстановка версий, затем `make`. Конфигурация
  пересоздаётся при каждой сборке, а не только при отсутствии `.config`: иначе правка defconfig не дошла бы до сборки.
- Кэши загрузок и ccache — в каталогах из переменных окружения (в WSL — `/root/utility-os-cache`, в CI — `actions/cache`).
- В конце копирует каталог для TFTP в `scriptexecute64/` и собирает `legal-info`.

## Проверки (`tools/utility-os/test.sh`)

- **Ядро:** все обязательные опции встроены.
- **Состав:** каждая команда из `legacy-commands.txt` и `pinctrl` есть; модулей ядра в образе нет.
- **Загрузка в QEMU.** `qemu-system-aarch64 -M virt -cpu cortex-a72` грузит тот же `kernel8.img` и `scriptexecute.img`
  (сеть — virtio-net, консоль — PL011). Тестовый сервер на хосте сначала отвечает 502, потом отдаёт проверочный скрипт. Тот
  возвращает:
  - запрос старта: все подстановки заменены, `uos` равен версии из `MANIFEST`; у источников, которых в QEMU нет (серийный
    номер, eMMC, `vcgencmd`, GPIO), значения пустые, и адрес от этого не ломается;
  - вывод `--version` ключевых программ: так видны битые бинарники и библиотеки;
  - сообщения программ: распаковщики на мусоре и на обрезанном архиве (gzip, xz, bzip2), `dd` на заполненной файловой
    системе, «records in» от `dd`, несовпадение у `sha256sum -c`, строки `identical` и `No EEPROM/flash device found` в
    программе `flashrom` (сам flashrom в QEMU не запустить).

  `test.sh` записывает сообщения в `tests/fixtures/utility-os/messages.txt`, файл коммитится вместе с `scriptexecute64/`.
  Специфику Pi (`vcgencmd`, светодиоды, SPI, перемычки, eMMC) QEMU не проверяет.
- **Размеры** ядра и initramfs печатаются вместе с разницей от закоммиченной версии; больше 32 МБ вместе — провал.
- **`MANIFEST`** совпадает с файлами каталога.

## CI (`.github/workflows/utility-os.yml`)

- Запускается кнопкой (workflow_dispatch), по расписанию раз в месяц и на PR, который трогает `utility-os/` или
  `tools/utility-os/`.
- `ubuntu-24.04`, освобождение диска, `actions/cache` для загрузок и ccache (ключ — хэш `versions.env`), лимит 5 часов.
- На PR и по кнопке: сборка и проверки, артефакты — каталог для TFTP и `legal-info`.
- По расписанию: `update.sh --check`. Если новое есть — `update.sh`, сборка, проверки и PR в stage2 с новыми
  `versions.env`, `scriptexecute64/` и `messages.txt`. В описании — таблица версий «было → стало», размеры, итог проверок,
  ссылка на артефакты. Расписание GitHub берёт файл workflow из ветки по умолчанию, поэтому он работает после выпуска 2.7.0
  в main, а сам прогон берёт stage2.
- PR создаётся токеном `GITHUB_TOKEN`. На такой PR CI сам не запускается, но сборка и проверки уже прошли в том же прогоне.

Шаги пользователя в GitHub:
- включить Actions в форке: в форках они выключены, пока владелец не включит их на вкладке Actions;
- разрешить Actions создавать PR (Settings → Actions → General);
- GitHub выключает расписание в публичном репозитории после 60 дней без коммитов; включается снова кнопкой
  «Enable workflow».

## Пакет, переключатель и `rpiboot`

### Каталоги и ссылка

- Пакет ставит `scriptexecute/` (старая ОС) и `scriptexecute64/` (новая), `debian/install`. `dh_strip` правок не требует:
  единственный ELF в каталоге, `start4.elf`, уже исключён (`--exclude=.elf`), а программы ОС лежат внутри initramfs.
- Ссылка `/var/lib/cmprovision/etc/boot` указывает на `../scriptexecute` или `../scriptexecute64`. Каталог `etc/` и так
  принадлежит www-data (`WRITABLE` в `debian/rules`, `fix_ownership` с `chown -h`).
- dnsmasq: `tftp-root=/var/lib/cmprovision/etc/boot`. `rpiboot`: `-d /var/lib/cmprovision/etc/boot`. Оба открывают файлы по
  пути на каждый запрос, поэтому смена ссылки действует без перезапуска служб и без новых правил sudo.
- `postinst`:
  - создаёт ссылку на `../scriptexecute`, если её нет: после обновления раздаётся прежняя ОС;
  - возвращает ссылку на `../scriptexecute`, если её цели нет (ссылка из чужого снимка);
  - идемпотентно меняет в рабочем `etc/dnsmasq.conf` строку `tftp-root=/var/lib/cmprovision/scriptexecute` на путь
    ссылки. Conffile в пакете не меняется: рабочий `dnsmasq.conf` и так правлен (строки `dhcp-host=` пишет приложение), и
    новая версия conffile остановила бы обновление вопросом dpkg;
  - всё это делает от www-data (`runuser`), как и artisan: каталог принадлежит www-data, и root, читающий и пишущий в нём,
    пошёл бы по подложенной ссылке (`sed -i` прочитал бы, например, `/etc/shadow` и оставил копию, которую `fix_ownership`
    отдаст www-data).
- Юнит `cmprovision-rpiboot` (не conffile) приходит уже с новым путём.
- `prerm` при откате ниже 2.7 возвращает ссылку на `../scriptexecute` (тоже от www-data): в 2.6.x каталога `scriptexecute64/`
  нет, а `tftp-root` останется на ссылке.
- `postrm purge` удаляет ссылку.
- `cmprovision-backup` и так архивирует `/var/lib/cmprovision` целиком, вместе со ссылкой. `cmprovision-restore` после
  распаковки делает то же, что `postinst`: снимок 2.6 и старше несёт `tftp-root` на `scriptexecute`, а `--data-only` ссылку
  не восстанавливает вовсе. Полное восстановление снимка 2.7 возвращает выбор ОС из снимка, `--data-only` оставляет выбор
  установленной системы.

### Settings → Utility OS

- Обе ОС с данными из их `MANIFEST`: версия, ядро, разрядность, дата сборки.
- Какая сейчас раздаётся (`readlink`).
- Кнопка переключения с подтверждением и предупреждением «Switch when no module is booting: a module that is booting now
  may get the files of both.»
- Если `tftp-root` в `dnsmasq.conf` смотрит не на ссылку (например, после ручной правки), раздел говорит, что переключатель
  не действует.
- Приложение меняет ссылку атомарно (новая ссылка рядом, затем `rename`) и только на один из двух каталогов пакета.
  Переключение пишется в журнал Laravel с именем оператора.
- Service status показывает, какая ОС раздаётся.

### Модуль

- Новый столбец `cms.utility_os` (строка, может быть пустой). Старт берёт его из параметра `uos` (только
  `[0-9A-Za-z.-]`, до 32 знаков). Без параметра — пусто: модуль грузился старой ОС.
- Карточка модуля показывает строку «Utility OS: 2026.10» или «legacy», строка журнала о старте тоже называет ОС: после
  переключения по журналу видно, какой ОС шёл каждый прогон.

### `bootcode4.bin`

В оба каталога кладётся `bootcode4.bin` из закреплённого тега usbboot. Тест пакета проверяет, что он есть в обоих.

### Размер и нагрузка

Ожидаемо 14–16 МБ ядра и initramfs (ядро с полным `bcm2711_defconfig` — около 9 МБ) против нынешних 7 МБ. При 10–15
модулях одновременно это до 240 МБ по TFTP за волну: для da2 нормально. Время загрузки модуля замеряется на живой проверке.

## Живая проверка на sensor1 (по слову пользователя)

Под новой ОС, через переключатель:
- модуль остаётся той же записью в CMs: параметры старта у обеих ОС совпадают (журнал доступа nginx на da2) —
  `serial`, `model`, `storagesize`, `mac`, `memorysize`, `cid`, `csd`, `bootmode`, `inversejumper`; `temp` — близко;
- обычная запись со сверкой;
- прошивка EEPROM: «identical» и «written» безвредной настройкой (например `DHCP_TIMEOUT=45000`) с откатом;
- светодиоды во всех режимах, Identify и Stop — смотрит пользователь;
- проверка ОС;
- докачка после перезапуска по PoE на проекте с кусками;
- время от включения до старта скрипта, рядом с тем же замером у старой ОС.

Потом переключение на старую ОС и один прогон: откат работает. Загрузка по USB через `rpiboot` проверяется, если найдётся
CM4, который можно загрузить по USB; иначе отмечается как непроверенная. Отладочную оболочку на tty2 проверяет только модуль
с экраном и клавиатурой; у sensor1 их нет — тоже отмечается.

## Риски

1. Специфику Pi (светодиоды на ядре 6.18, SPI и `flashrom`, `vcgencmd` из `raspberrypi/utils`, перемычки через `pinctrl`,
   нумерация `mmcblk0`, которую в 6.18 задают алиасы дерева устройств) проверяет только живая проверка.
2. Новое ядро в обновлении может потерять нужную опцию: ловит проверка конфигурации, PR приходит красным.
3. Ядро Raspberry Pi может не загрузиться в QEMU `virt`. Тогда проверка грузит тот же initramfs отдельным ядром virt из той
   же сборки, а ядро модуля проверяет только живая проверка.
4. Время сборки не измерено: у похожих проектов 40–110 минут в CI, у нас к этому добавляются модули ядра.
5. PR из CI требует включить Actions в форке и разрешить им PR.
6. Ссылку `etc/boot` выбирает www-data, а `rpiboot` от root читает файлы по ней. Права почти не растут: www-data и сейчас
   пишет `tftp-root` в `dnsmasq.conf`, а `rpiboot` отдаёт файлы только устройству, подключённому к USB провижинера.
   Приложение пишет ссылку только на два каталога пакета.
7. Вход root без пароля на tty2 — только с клавиатуры модуля, как и у старой ОС с её оболочкой на tty2.
