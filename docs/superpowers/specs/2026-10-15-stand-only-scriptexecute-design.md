# `/scriptexecute` только для сети стенда (2.5.1)

Дата: 2026-10-15. Версия 2.5.1 после 2.5.0 — первая из трёх частей «сети провижинера» (ROADMAP, этап 2, пункт 2). Две другие — встроенный Wi-Fi холодным запасным (2.5.2) и управление Wi-Fi из веб-интерфейса (2.5.3) — свои спеки и выпуски. Как собрана сеть провижинера — [docs/provisioner-network.md](../../provisioner-network.md).

## Зачем

`/scriptexecute` открыт без входа и исключён из CSRF: его клиент — `curl` модуля в сети стенда. Но провижинер виден и из офисной сети (по Wi-Fi), и оттуда любой может:
- завести модуль с любым серийным номером, отметить модуль упавшим или готовым;
- вызвать уведомления в Mattermost и Telegram и печать этикеток;
- получить скрипт модуля со скриптами проекта (в них бывают ключи и пароли) и случайное имя файла образа.

Закрываем: адрес отвечает только сети стенда и самому серверу.

Успех: с офисного компьютера `curl http://<провижинер>/scriptexecute?serial=x` получает 403 с причиной; модули на стенде прошиваются как прежде; локальные инструменты на `http://127.0.0.1/scriptexecute` (нагрузочная репетиция `tests/load`, дымовой тест стенда, `simulate-modules.sh` на провижинере) работают.

## Решения пользователя

- Три отдельные спеки и выпуска вместо одной «сети провижинера»; эта — первая.
- Поддержка CM3/CM3+ по USB убирается: у пользователя CM4 (WLAN Pi M4+) по Ethernet, железа CM3 нет, путь CM3 на Trixie сам не настраивается и не проверялся.
- Проверка — в Laravel middleware; маршрут уходит из группы `web` в свой файл.

## Не входит

- `/uploads/` и `/tools/`: образы лежат под случайными именами из 40 символов, которые узнаются только из ответа `/scriptexecute` и из интерфейса и API под входом; в `pieeprom.bin` и `ledpattern` тайн нет.
- Закрывать веб-интерфейс от сети стенда.
- Правило в nginx.
- Другая подсеть стенда (upstream #22 остаётся в ROADMAP): `172.20.0.0/16` зашита ещё в пяти местах.
- Загрузочные файлы CM3 в `scriptexecute/` (`bootcode.bin`, `start.elf`, `fixup.dat`, `bcm2710-rpi-cm3.dtb`): это готовые бинарники upstream без исходников, вреда от них нет.

## Проверка доступа

### Маршрут

`/scriptexecute` переезжает из `routes/web.php` в новый `routes/module.php`. `RouteServiceProvider` подключает его с middleware `stand` вместо группы `web`:

```php
Route::middleware('stand')
    ->namespace($this->namespace)
    ->group(base_path('routes/module.php'));
```

У модуля нет сессии, cookie и CSRF-токена, поэтому `StartSession`, `VerifyCsrfToken` и остальные middleware группы `web` ему не нужны. Строка `scriptexecute` уходит из `VerifyCsrfToken::$except`. Глобальные middleware (`PreventRequestsDuringMaintenance`, `ValidatePostSize`, `TrimStrings` и прочие) работают как раньше.

Побочный выигрыш: модули перестают писать строку в таблицу `sessions` (`SESSION_DRIVER=database`) на каждый запрос. На wlanpi-da2 15 октября из 1445 строк `sessions` 1444 были от модулей (`curl/7.66.0` из `172.20.0.0/16`: опрос `identify` раз в 5 секунд); при 48 модулях это сотни лишних записей SQLite в минуту. Старые строки убирает штатная чистка сессий Laravel, миграция не нужна.

### Middleware

`App\Http\Middleware\StandNetworkOnly`, алиас `stand` в `$routeMiddleware` (`App\Http\Kernel`):
- адрес клиента — сырой `REMOTE_ADDR` соединения (`$request->server('REMOTE_ADDR')`), а не `$request->ip()`: `X-Forwarded-For` на решение не влияет, даже если когда-нибудь настроят доверие к прокси (`TrustProxies::$proxies` сейчас пуст);
- IPv4 в записи IPv6 (`::ffff:172.20.5.5`) сводится к IPv4;
- пропускает `NetworkStatus::STAND_NETWORK` (`172.20.0.0/16`, новая константа рядом с `SERVER_ADDRESS`) и loopback (`127.0.0.0/8`, `::1`); сравнение — `Symfony\Component\HttpFoundation\IpUtils::checkIp()`;
- всё остальное, включая любой IPv6 link-local и пустой адрес, получает 403 `text/plain` одной строкой:
  `cmprovision answers /scriptexecute only for the stand network 172.20.0.0/16 and for this server itself; this request came from <адрес>.`
- отклонённый запрос до контроллера не доходит: в базе не появляется ни модуля, ни строки журнала. Отказы не логируются: причина есть в ответе.

`StandNetworkOnly::allows(?string $address): bool` — та же проверка статической функцией, для тестов по таблице адресов.

Почему достаточно адреса клиента: подделать источник TCP из офиса нельзя — ответ на SYN уйдёт в сеть стенда, и рукопожатие не состоится. Почему нельзя проверять адрес назначения (`SERVER_ADDR`): Linux принимает пакет на любой свой адрес с любого интерфейса, и офис, прописав маршрут `172.20.0.0/16` через провижинер, дошёл бы до `172.20.0.1` по Wi-Fi. Почему не пускать IPv6 link-local: он есть и у `wlan0`/`wlan1`, офис на том же Wi-Fi до него дотягивается; нужен он был только CM3.

## Уборка CM3

У CM3/CM3+ нет ни Ethernet, ни EEPROM-загрузчика: до сервера модуль добирался только через USB-гаджет по IPv6 link-local. Уходят:
- `ScriptExecuteController::moduleServer()`: перезапись `[addr]` в `[addr%usb0]`. Сервер в ссылках скрипта берётся из `Host` как есть, и локальный запрос на `[::1]` больше не получает ссылок на `%usb0`;
- `debian/postinst`: блок, который меняет `slaac private` на `slaac hwaddr` в `/etc/dhcpcd.conf` (на Trixie dhcpcd нет, блок и так не срабатывал);
- `scriptexecute/config.txt`: секция `[pi3]` (USB-гаджет и `cmdline=cmdline.txt.ipv6ll`), и файл `scriptexecute/cmdline.txt.ipv6ll`. Это не conffile: dpkg обновит `config.txt` и удалит `cmdline.txt.ipv6ll` без вопросов;
- README: разделы «Provisioning Compute Module 3 and 3+ Devices» и «Provisioning from an alternate OS»; в первой строке вместо «Compute Module 3, 3+ and 4» — CM4, и абзац о том, что CM3/CM3+ с 2.5.1 не поддерживаются (для них — v1.6.11 этого форка на Raspberry Pi OS с dhcpcd или upstream raspberrypi/cmprovision).

Остаётся служба `cmprovision-rpiboot` (`rpiboot -l -d scriptexecute`): она нужна и CM4, загруженному по USB (bootmode 3 — новый модуль или переключённый джампером). Дальше такой модуль идёт к серверу по Ethernet, по IPv4.

## Проверка

### Тесты

- `tests/Feature/StandNetworkTest.php`:
  - модуль из `172.20.5.5` получает скрипт;
  - loopback (`127.0.0.1`, `::1`) пропускается;
  - 403 с текстом причины для `192.168.68.50` (офисный Wi-Fi), `172.21.0.1` и `172.19.255.255` (соседние сети), `fe80::1` (link-local), `2001:db8::1`, `::ffff:192.168.68.50` и пустого адреса; после отказа в базе нет ни модуля, ни строки `cmlogs`;
  - `::ffff:172.20.5.5` пропускается;
  - `X-Forwarded-For: 172.20.5.5` из офиса — всё равно 403;
  - отчёт с логом (multipart POST) из офиса для существующего модуля отклоняется, лог модуля не меняется;
  - маршрут `/scriptexecute` проходит через `StandNetworkOnly` и не проходит через `StartSession` и `VerifyCsrfToken` (`Router::gatherRouteMiddleware()`);
  - скрипт для `Host: [::1]` ссылается на `http://[::1]/…`, без `%usb0`.
- `tests/Unit/PackagingTest.php`: в `postinst` нет `dhcpcd`, в `scriptexecute/config.txt` нет `[pi3]`, файла `scriptexecute/cmdline.txt.ipv6ll` нет.
- Остальные тесты не меняются: тестовые запросы Laravel приходят с `127.0.0.1`.

### На стенде и провижинере

- Стенд WSL: дымовой тест (`05-smoke.sh`, `http://127.0.0.1`) проходит; запрос с Windows на nginx стенда получает 403. Если подсеть WSL сама попала в `172.20.0.0/16`, запрос пройдёт — адрес в ответе это покажет.
- wlanpi-da2 после установки:
  - с офисного компьютера `curl -i http://<провижинер>/scriptexecute?serial=x` → 403 с причиной;
  - модули на стенде (опрос `identify`) получают 200 в журнале nginx;
  - строки `sessions` от `curl/7.66.0` больше не прибавляются;
  - прогон модуля — только по просьбе пользователя.

## Риски

- Обратный прокси перед nginx сделал бы адресом клиента сам прокси (`127.0.0.1`), и проверка пропускала бы всех. Пакет ставит nginx, который говорит с php-fpm напрямую; в CLAUDE.md это записано.
- Офисная сеть, пересекающаяся с `172.20.0.0/16`, прошла бы проверку, но такая сеть и так ломает маршрутизацию стенда.
- CM3/CM3+ перестают прошиваться: rpiboot их загрузит, но до сервера они не дойдут (решение пользователя).
- Из офиса больше не посмотреть скрипт модуля через `curl`. На провижинере — `curl http://127.0.0.1/scriptexecute?…`; как и раньше, такой запрос заводит модуль в базе.
