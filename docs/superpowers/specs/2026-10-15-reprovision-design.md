# Перепрошивка сенсора из веб-интерфейса (2.5.1)

Дата: 2026-10-15. Версия 2.5.1 после 2.5.0. В ROADMAP это был пункт 2.5.2 «удалённое затирание сенсоров»; пользователь попросил его раньше, поэтому он выходит как 2.5.1, а сеть провижинера (`/scriptexecute` только для стенда, встроенный Wi-Fi холодным запасным, управление Wi-Fi) становится 2.5.2.

## Зачем

Перепрошить сенсор, который уже загрузился в свою ОС (WLAN Pi OS) на стенде, сейчас можно только вручную: зайти на него по SSH и обнулить начало eMMC. Так однажды затёрли сам провижинер (команду вставили не в то окно), а 14 октября ручное затирание sensor1 остановил классификатор безопасности автоматического режима. Нужна кнопка: сервер сам проверяет, что перед ним та самая железка, и после отдельного подтверждения затирает её. Сенсор уходит в сетевую загрузку и прошивается активным проектом, как новый.

Успех: оператор из карточки модуля перепрошивает sensor1 (WLAN Pi OS, на стенде) — проверка доступа, подтверждение, и через пару минут в карточке идёт новый прогон.

## Решения пользователя

- Один сенсор за раз, кнопка в карточке модуля.
- Вход на сенсор: ключ провижинера, а если его на сенсоре нет — логин и пароль из формы.
- Если сенсор требует сменить пароль (WLAN Pi OS просрочивает пароль `wlanpi` по умолчанию), открывается окно, в котором оператор вводит новый пароль; сервер меняет его и продолжает.
- Разделы дизайна 1–3 (что попадает на сенсор; сервер; интерфейс, ошибки, проверка, номер версии) одобрены.

## Не входит

- Несколько сенсоров разом, партия целиком.
- Модули, которые ждут в утилитарной ОС после прогона: там нет SSH; их перезагружает перезапуск по PoE.
- Ключ провижинера на боевых образах по умолчанию: опция проекта выключена, включает её пользователь.
- Сеть провижинера и Wi-Fi — 2.5.2.

## Что попадает на сенсор

### Опция проекта

Колонка `projects.reprovision` (bool, по умолчанию false), флажок в форме проекта «Re-provision from the web UI (puts the provisioner's key on the device)» с подсказкой, что ключ остаётся на каждом прошитом устройстве и умеет только назвать устройство и затереть его. API проекта принимает и отдаёт поле, как остальные. У существующих проектов опция выключена; на wlanpi-da2 её включают у `stage1-test` в форме проекта при выкатке.

### Сгенерированный пост-скрипт

При включённой опции `ScriptExecuteController` добавляет к пост-скриптам проекта сгенерированный шаг «Re-provision agent» после сверки SHA256 (тем же способом, что прошивку EEPROM и сверку). Шаг:
- монтирует второй раздел нового образа (`$PART2`) как ext4 во временный каталог; если это не ext4 или в нём нет `/etc/ssh` — печатает `agent skipped: <причина>` и выходит с кодом 0;
- кладёт `/usr/local/sbin/cmprovision-agent` (root, 0755);
- дописывает в `/root/.ssh/authorized_keys` (каталог 0700, файл 0600, владелец root) строку `restrict,command="/usr/local/sbin/cmprovision-agent" <открытый ключ провижинера> cmprovision@<hostname сервера>`, если такой строки ещё нет;
- размонтирует раздел и печатает `agent installed`.

Любая ошибка внутри шага не роняет прогон: шаг всегда выходит с кодом 0, причина остаётся в его выводе.

### Агент

`cmprovision-agent` читает команду из `SSH_ORIGINAL_COMMAND`:
- `identify` — печатает `serial=<Serial из /proc/cpuinfo> host=<hostname>`;
- `wipe <serial>` — если серийный номер совпал, обнуляет первый мегабайт устройства хранения проекта (`projects.storage`, например `/dev/mmcblk0`; `dd ... bs=1M count=1 conv=fsync`, затем `sync`) и через 2 секунды перезагружает (`reboot -f` в фоне, чтобы SSH-команда успела вернуться), печатает `wiping`; иначе печатает `refused: serial <настоящий>` и выходит с кодом 1;
- любая другая команда — `unknown command`, код 1.

### Ключ провижинера

Пара ed25519 у www-data в `storage/app/ssh/id_ed25519` (закрытая 0600), создаётся `ssh-keygen` при первой нужде (рендер скрипта модуля с включённой опцией или страница Settings). Закрытая часть с сервера не уходит. Settings показывает открытую часть (только чтение, кнопка копирования), чтобы её можно было положить на сенсор вручную. Бэкап и `restore --data-only` переносят её вместе с `storage/app`.

## Сервер

### Адрес сенсора

`App\Services\SensorAddress` — адрес из аренд DHCP провижинера (`etc/dnsmasq.leases`) по MAC модуля и имя хоста из той же строки. Адрес провижинера `NetworkStatus::SERVER_ADDRESS` (172.20.0.1) никогда не цель. Нет аренды — нет адреса.

### SSH

Интерфейс `App\Services\Sensor\SensorShell` (как `SnmpClient`), реализация `OpenSshSensorShell` — клиент OpenSSH от www-data через Laravel `Process`, без новых зависимостей:
- общие опции: `-o ConnectTimeout=5 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o LogLevel=ERROR`; таймаут процесса 15 с; ключи хостов не сохраняются (после каждой прошивки они у сенсора новые; от чужого устройства защищает сверка серийного номера);
- по ключу: `-o BatchMode=yes -o IdentitiesOnly=yes -i storage/app/ssh/id_ed25519 root@<адрес> <команда>`;
- по учётке: `-o PubkeyAuthentication=no -o PreferredAuthentications=password -o NumberOfPasswordPrompts=1`, пароль отдаёт помощник `SSH_ASKPASS` (скрипт печатает переменную окружения процесса) с `SSH_ASKPASS_REQUIRE=force`; `sudo` на сенсоре — `sudo -S -p ''` с паролем на stdin;
- смена просроченного пароля: `ssh -tt` с учёткой и ответами на запросы PAM (текущий, новый, повтор) на stdin; успех — `password updated successfully`, иначе ответ системы (`BAD PASSWORD: …` и т. п.) уходит оператору.

Признаки ответа сенсора: отказ ключа (`Permission denied (publickey)`), просроченный пароль (`You are required to change your password`, `Your password has expired`, `Password change required`), неверный пароль, нет ответа (таймаут, `No route to host`, `Connection refused`).

### Проверка доступа

`App\Services\Sensor\Reprovision::check(Cm $cm, ?array $account)`:
1. Адрес из аренды; нет — «not on the stand network».
2. Ключ: `identify` от root. Принят — сверка серийного номера с `cms.serial`.
3. Ключ не принят (на сенсоре его нет) и учётки нет — ответ «нужна учётка»; учётка есть — вход с ней, чтение серийного номера и имени хоста, `sudo -S -v`.
4. Пароль просрочен — ответ «нужен новый пароль»; с новым паролем — смена через `ssh -tt`, затем пункт 3 с новым паролем.
5. Итог: способ (`key` или `account`), имя хоста, серийный номер. Несовпадение серийного номера — отказ «по адресу другое устройство: <серийный>».

### Затирание

`Reprovision::wipe(Cm $cm, $способ, ?array $account, string $оператор)`: ключом — `wipe <serial>` агенту; учёткой — `sudo -S -p '' sh -c '<то же, что агент: сверка серийного номера, dd, sync, отложенная перезагрузка>'` по устройству хранения проекта, которым модуль был прошит (`cms.project_id`; без проекта — `/dev/mmcblk0`). Серийный номер сверяется на самом сенсоре. В журнал модуля (`cmlogs`) — строка `Re-provision by <оператор>: wiped over the provisioner's key` или `… over account <логин>` (смена пароля отмечается словами `password changed`, сам пароль — никогда). Без активного проекта затирание не выполняется.

### Пароли

Между шагами диалога пароли (текущий и новый) лежат в кэше сервера зашифрованными (`Crypt`) не дольше 2 минут под случайным ключом, который знает только компонент; в публичных свойствах Livewire и в ответах браузеру их нет, в журналы они не пишутся. Поля пароля в форме очищаются сразу после отправки.

### Защита от двух операторов

Замок `reprovision:<id модуля>` на время проверки и затирания; кнопка не работает, пока модуль прошивается (`isActive()` и старт в пределах `Cm::ACTIVE_HOURS`).

## Интерфейс

Карточка модуля (`CmCard`): кнопка «Re-provision…» рядом с Identify и строкой питания. Активна, когда у MAC модуля есть аренда в сети стенда и модуль не прошивается; иначе неактивна с причиной в подсказке.

Диалог (поверх верхней панели, поля `cmp-field`, цвета — токены):
- шапка: имя хоста и адрес из аренды, MAC, проект, которым сенсор прошьётся (активный);
- шаг 1 «Check access»: сначала ключ; при «нужна учётка» — поля логина (по умолчанию `wlanpi`) и пароля; при «нужен новый пароль» — окно «The sensor asks for a new password» с полями нового пароля и повтора (совпадение проверяется до отправки);
- итог проверки: «Access over the provisioner's key / over account wlanpi: wlanpi-059, serial 100000004acecfa4 matches»;
- шаг 2 «Wipe and re-provision» (красная) с подтверждением «Wipe wlanpi-059 (100000004acecfa4) and re-provision it with stage1-test?»; после — «Wiped: the sensor reboots into network boot», диалог закрывается, карточка показывает строку журнала, а затем новый прогон.

Ошибки понятным текстом: сенсор не отвечает (выключен или загружается), по адресу другое устройство, ключ не подошёл и учётка не введена, неверный пароль, `sudo` не принял пароль, новый пароль не прошёл правила системы (ответ системы), нет активного проекта.

## Проверка

### Тесты

- `ReprovisionTest` с подделкой `SensorShell`: ключ; учётка; смена пароля и повторная проверка; чужой серийный номер; нет ответа; нет аренды; модуль прошивается; нет активного проекта; строка журнала без пароля.
- `ReprovisionDialogTest` (Livewire): шаги диалога, пароль не попадает в состояние компонента и в HTML, кнопка неактивна без аренды.
- `SensorAddressTest`: аренды dnsmasq, адрес провижинера не цель.
- `ReprovisionAgentTest`: сгенерированный пост-скрипт и агент под настоящим `sh` (подставные `dd`, `reboot`, `mount`, файл cpuinfo и корень образа во временном каталоге): `identify`, `wipe` своего и чужого серийного номера, `agent skipped` без ext4, код выхода 0 при любой ошибке шага.
- `OpenSshSensorShellTest` на стенде WSL против настоящего sshd на 127.0.0.1 (пропускается без него): root с ключом и принудительной командой, пользователь с паролем, пользователь с просроченным паролем (смена через `ssh -tt`), неверный пароль.

### На железе

После выпуска на wlanpi-da2: опция включена у `stage1-test`; sensor1 (`wlanpi-059`, WLAN Pi OS) прошит ещё до 2.5.1, ключа на нём нет — проверка идёт учёткой `wlanpi` (тестовый проект снимает требование смены пароля и даёт `sudo` без пароля), затирание, сетевая загрузка, прогон с ключом агента; следующая перепрошивка sensor1 — уже по ключу.

## Риски

- Ключ провижинера на прошитых устройствах: кто получил закрытую часть (с провижинера), тот может затереть такие устройства, если дотянется до них по сети. Поэтому опция выключена по умолчанию и описана в форме.
- Смена просроченного пароля через `ssh -tt` зависит от текста запросов PAM; другой образ — другой текст. Не распознанный ответ показывается оператору как есть.
- Без сверки ключа хоста пароль уйдёт тому, кто ответит на адресе из аренды; сеть стенда изолирована, затирание всё равно сверяет серийный номер.
