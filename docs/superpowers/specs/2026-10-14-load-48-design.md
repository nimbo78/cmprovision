# 48 модулей разом (2.5.0)

Дата: 2026-10-14. Версия 2.5.0 после 2.4.1, первая из трёх частей 2.5 (2.5.1 — сеть провижинера: `/scriptexecute` только для стенда и встроенный Wi-Fi холодным запасным; 2.5.2 — удалённое затирание сенсоров).

## Зачем

Стенд растёт до двух 24-портовых коммутаторов, то есть 40–48 модулей. Сервер на wlanpi-da2 (CM4, 4 ядра, 3,8 ГБ, занято 0,3 ГБ) сейчас рассчитан на несколько модулей:
- пул php-fpm — стандартный Debian, `pm.max_children = 5`; каждый модуль раз в 5 с шлёт прогресс, а старт модуля держит воркер, пока идёт опрос коммутаторов (с 2.4 — всех, и ждёт чужой опрос до 10 с на каждый);
- SQLite в режиме `journal_mode = delete` без `busy_timeout`: читатели и писатели блокируют друг друга, при десятке записей в секунду возможен «database is locked»;
- один воркер очереди считает SHA256 образа минутами и держит всё остальное;
- уведомления уходят на каждое событие каждого модуля из воркера php-fpm после ответа (`app()->terminating()`); волна из 48 модулей — это 100–150 сообщений в тред и столько же правок сводки, а Telegram пропускает в группу около 20 в минуту; на 429 код спит до 10 с в воркере php-fpm;
- `NotificationBatch::current()` без замка: одновременные старты создают несколько партий;
- защита EEPROM при перезапуске по PoE смотрит на снимок коммутатора не старше 30 с: загружающаяся Raspberry Pi на снимке к моменту выключения уже может писать загрузчик.

Успех: волна из 48 модулей, стартующих разом, проходит без «нет связи» по вине сервера, каждый старт получает скрипт сразу и плату через секунды, каждый отчёт доходит, уведомления укладываются в лимиты и не отстают, на волну одна партия.

## Решения пользователя

- 2.5 делится на три части по очереди, у каждой своя спека, план и выпуск; эта — первая.
- Как стартует волна — «бывает по-разному»: рассчитываем на худший случай, все 48 разом.
- Уведомления пачками: события за ~10 с — одно сообщение, сводка правится свежими числами.
- Плата ищется фоном (подход Б): старт отдаёт скрипт сразу, один опрос стенда на волну.
- Разделы дизайна 1–5 (сервер, плата, уведомления, партия и EEPROM, проверка) одобрены.

## Не входит

- `/scriptexecute` только для стенда и встроенный Wi-Fi холодным запасным — 2.5.1.
- Удалённое затирание сенсоров — 2.5.2.
- LLDP/CDP, свой порядок блоков на Ports, API коммутаторов, разные VLAN — как в 2.4, позже.

## Сервер

### Пул php-fpm

`postinst` на каждом configure создаёт для найденной версии PHP файл `/etc/php/<версия>/fpm/pool.d/cmprovision.conf`:

```ini
; cmprovision4: its own pool, so 40-48 modules starting and reporting at once never wait for a worker
[cmprovision]
user = www-data
group = www-data
listen = /run/php/cmprovision-fpm.sock
listen.owner = www-data
listen.group = www-data
pm = dynamic
pm.max_children = 16
pm.start_servers = 4
pm.min_spare_servers = 2
pm.max_spare_servers = 6
pm.max_requests = 500
```

Сайт nginx (`debian/cmprovision` и правка существующих установок в `postinst`) переходит на `unix:/run/php/cmprovision-fpm.sock`. Пул `www` и его `www.conf` не трогаются: это conffile php-fpm, его правка вызывала бы вопросы dpkg при обновлениях PHP. Настройки `php.ini` (upload, `upload_tmp_dir`) общие для пулов и остаются как есть. Смена версии PHP (новая Debian) требует configure пакета (`dpkg-reconfigure cmprovision4`), как и сейчас для сокета; до этого сайт отвечает 502. `postrm purge` удаляет файл пула.

### SQLite

Подключение `sqlite` в `config/database.php` получает `'busy_timeout' => 5000`, `'journal_mode' => 'wal'`, `'synchronous' => 'normal'`. WAL записывается в файл базы и остаётся; файлы `database.sqlite-wal` и `-shm` создаются рядом, каталог `database/` уже принадлежит www-data. Бэкап (`sqlite3 .backup`) и восстановление (удаляет `-wal` и `-shm`) совместимы с WAL. Откат на 2.4.1 работает с базой в WAL без изменений.

### Очереди

- `cmprovision-queue` — `artisan queue:work --queue=boards,notifications`: быстрые задачи, платы раньше уведомлений.
- Новый `cmprovision-queue-images` — `artisan queue:work --queue=images`: `ComputeSHA256` уходит в очередь `images`.
- Задачи, которые ждут (лимит Telegram), не спят в воркере, а возвращаются в очередь с задержкой.
- Settings → Service status показывает обе службы очереди рядом с dnsmasq и rpiboot.

## Старт модуля и плата

### Старт

`ScriptExecuteController::startProvisoning()` больше не ищет порт в запросе:
- коммутаторы есть и модуль прислал MAC: строка модуля пишется с пустой платой и `cms.board_pending_since = now()`, коммутатор и порт пустые; ставится задача `ResolveBoards` (очередь `boards`);
- коммутаторов нет: плата из джамперов в запросе, как сейчас;
- партия назначается под замком (ниже), проверки отказа, фаза, журнал «Provisioning started» и скрипт — как сейчас;
- событие `CmProvisioningStarted` по-прежнему возникает в запросе старта (точка расширения);
- этикетка этапа preinstall печатается в запросе только у модуля без ожидания платы; у модуля, чья плата ищется, её печатает задача.

### Задача `ResolveBoards`

- `ShouldBeUnique`: одна задача на волну, новые старты к ней присоединяются.
- Берёт все строки с `board_pending_since`, опрашивает стенд один раз: `Stand::current($notOlderThan = самый поздний board_pending_since, PortLookup::WAIT)`.
- Для каждого модуля применяет правила 2.4 (`PortLookup::resolve($stand, $mac)` — бывший `find()` без опроса): плата «hostname порт», `switch_id`, `switch_name`, `switch_port`; молчащий коммутатор, занятый коммутатор, линк, «[multiple ports]» — как в 2.4.
- Переход «ищется → найдена» делается одной записью `update cms set … , board_pending_since = null where id = ? and board_pending_since is not null`; кто её сделал, тот и печатает этикетку preinstall (ровно один раз).
- Модуля нет на карте и с его старта прошло меньше 60 с — задача возвращается в очередь через 3 с и опрашивает заново (снимок не старше нового запроса). Прошло 60 с — плата не найдена: пометка снимается, предупреждение 2.4 («Switch port unknown: …») пишется в журнал модуля, этикетка печатается без платы.
- Новый старт модуля, у которого прошлый поиск не закончился, просто обновляет `board_pending_since`.

### Страницы

- Дашборд: в колонке Board у модуля, чья плата ищется, — «…» с подсказкой «looking up the switch port».
- Карточка модуля: строка Board — «looking up the switch port…».
- Уведомления собираются при отправке пачки из текущей строки модуля, поэтому плата в них уже есть.

## Уведомления

### Исходящие

Таблица `notification_outbox`: `id`, `channel_id` (каскадом с каналом), `batch_id` (null, если без партии), `cm_id` (null после удаления модуля), `event` (`started`, `completed`, `failed`), `created_at`, `sent_at` (null — не отправлено), `attempts`, `error`.

`SendProvisioningNotifications` больше ничего не шлёт: на событие модуля пишет строку в `notification_outbox` для каждого включённого канала и ставит задачу `FlushNotifications` (очередь `notifications`, `ShouldBeUnique`, задержка `WINDOW = 10` с). События, пришедшие за окно, отправляются этой же задачей.

### Отправка

`FlushNotifications` проходит по каналам с неотправленными строками:
- **Чат-каналы** (Telegram bot, Mattermost bot, Mattermost webhook): строки группируются по партии; для каждой группы одно сообщение с частями по видам событий, каждая — только если канал подписан на это событие:
  ```
  ▶️ 12 started: 1000000000000c01 sw01 Gi0/3, …
  ✅ 7 done: 1000000000000c02 sw01 Gi0/4 5:07, …
  ❌ 2 failed: 1000000000000c03 sw02 GE0/0/5 — Missing eMMC/SD card., …
  ```
  Строка модуля — из `Notifier::moduleLine()` по текущей строке модуля. Боты отвечают в тред партии (сводку постят при первой пачке партии, как сейчас), затем один раз правят сводку свежими числами — и тогда, когда события пачки каналу не нужны. Сообщение длиннее 4000 символов делится по строкам на несколько.
- **JSON webhook**: каждое событие — отдельный POST с полезной нагрузкой из `Notifier::payload()` по текущей строке модуля.
- После удачной отправки строки помечаются `sent_at`, у канала `last_sent_at`; ошибка — в `last_error` канала (через `Notifier::errorText()`, токен Telegram вырезается), у строк растёт `attempts`. После пяти попыток строка помечается `sent_at` с `error` и больше не отправляется.

### Лимиты

- Одна пачка на канал за окно, то есть не больше двух вызовов (ответ и правка) на 10 с: 12 в минуту при пределе Telegram около 20 в минуту на группу.
- Между вызовами в один канал не меньше 1 с.
- Ответ 429: задача возвращается в очередь на `retry_after` секунд (`release()`), строки ждут в таблице; сон в воркере php-fpm уходит вместе с отправкой из запроса.
- Адрес Telegram Bot API берётся из `config('cmprovision.telegram_api')` (по умолчанию `https://api.telegram.org`, переменная `TELEGRAM_API`): заглушка на репетиции.
- Кнопка Test канала остаётся синхронной.

## Партия

`NotificationBatch::current()` работает под замком `notification-batch` (`Cache::lock(…, 10)->block(5)`): одновременные старты видят одну открытую партию. Не дождались замка — партия перечитывается после ожидания (её создал соседний старт).

## Защита EEPROM при перезапуске

Перед выключением каждого порта `PoeRestart` (в `switchAllOff()`) заново читает из базы модули порта: по MAC, которые видел снимок (у загружающейся Raspberry Pi строки на снимке нет, но к этому моменту может быть), и по `switch_id` и `switch_port`, записанным при поиске платы. Если хоть один из них сейчас пишет загрузчик EEPROM и отвечает серверу (`StandMap::writingEeprom()`, `isActive()`, `silentFor() === null`), порт пропускается с причиной «the module on <label> is writing its bootloader EEPROM».

## Проверка

### Тесты

- `ResolveBoardsTest`: волна модулей на двух поддельных коммутаторах — один опрос на волну, платы и коммутаторы; модуль, который появляется со второго опроса; отказ через 60 с с предупреждением; этикетка preinstall ровно один раз; модуль без коммутаторов — плата из джамперов в запросе.
- `NotificationOutboxTest` (`Http::fake()`): пачка за окно, части по событиям и подпискам канала, свежие числа в сводке, правка сводки без нужных каналу событий, деление длинного сообщения, 429 с `retry_after` → задача отложена, строки не отправлены, пять попыток, JSON webhook по событию, токен вырезан из ошибки.
- `NotificationBatchTest`: замок партии.
- `PoeRestartTest`: модуль начал писать EEPROM после снимка (по MAC и по записанному порту) — порт пропущен.
- `DatabaseConfigTest`: WAL и `busy_timeout` у подключения (на временном файле).
- Существующие тесты уведомлений переходят с синхронной отправки на `FlushNotifications`.

### Нагрузочная репетиция на стенде WSL

На установленном пакете (nginx, пул `cmprovision`, обе очереди):
- фикстуры snmpsim `stand48a` и `stand48b` (`generate.py`): два 24-портовых Huawei с PoE, на портах 48 MAC модулей, линк между ними;
- скрипт-волна: 48 одновременных стартов `GET /scriptexecute?serial=…&mac=…`, затем прогресс каждые 5 с минуту, затем отчёты (45 done, 3 failed) — `curl` параллельно;
- заглушка Telegram (`php -S 127.0.0.1:8099`): отвечает как Bot API, считает вызовы по минутам, каждый десятый вызов — 429 с `retry_after` 3.

Критерии:
- каждый старт получил скрипт быстрее 2 с (95-й перцентиль), ни одного ответа 5xx;
- все 48 плат проставлены за 15 с от волны;
- в `storage/logs/laravel.log` нет «database is locked»;
- заглушка получила не больше 20 вызовов в минуту, каждое событие попало в сообщение, последняя правка сводки — итоговые числа;
- на волну одна партия.

### После выпуска

Перепрошивка одного сенсора на wlanpi-da2 (как в 2.4.0): плата, этикетка, уведомление пачкой. Живые 24-портовые коммутаторы — когда приедут.

## Риски

- Новая версия PHP без configure пакета оставляет сайт без пула (502): `postinst` печатает, где пул; README говорит про `dpkg-reconfigure cmprovision4`.
- Остановленный воркер очереди оставляет платы «ищется…» и уведомления неотправленными: Service status показывает обе службы, служба перезапускается сама (`Restart=always`).
- Лимиты Telegram меняются: окно и паузы — константы `FlushNotifications`.
- Сводка правится не на каждом событии, а раз в окно: в чате она отстаёт от стенда до 10 с.
