# Настройка новой станции cmprovision из проекта

Ветка разработки позволяет настроить новую станцию непосредственно во время записи универсального образа cmprovision Lite. Проект задаёт учётную запись Linux и опциональный Wi-Fi управления; общий файл образа остаётся неизменным. Для работы функции требуются пересобранный образ со **схемой настройки станции 1 (setup schema 1)**, 64-битная утилитарная ОС, а также eMMC/SD с таблицей MBR и разделом ext4 на втором разделе. Ранее протестированный образ `2.24.0~dev2` не содержит этой поддержки. Функция не предназначена для произвольной модификации стандартных образов Raspberry Pi OS или WLAN Pi OS.

## Подготовка проекта

1. Загрузите совместимый образ станции и дождитесь вычисления контрольных сумм.
2. Создайте проект, выберите данный образ и включите **Verify that image was written correctly**. Выберите **Check the OS after the first boot** для автоматической перезагрузки и проверки станции. Разрезание образа на части опционально. Не включайте изменение EEPROM без явной необходимости.
3. Включите опцию **Set up a cmprovision station**. Укажите имя администратора Linux и имя хоста. Значение по умолчанию `cmprovision-{serial}` присваивает каждой станции уникальное имя, подставляя полный серийный номер вместо `{serial}`.
4. Задайте начальный пароль, добавьте публичные SSH-ключи или используйте оба варианта. Включите **Enable SSH** для удалённого доступа. Если вход по паролю отключён, наличие хотя бы одного публичного ключа и включение SSH обязательны; в этом случае администратор получает беспарольный sudo. При наличии пароля действует стандартная политика sudo в образе.
5. При необходимости настройте Wi-Fi управления: SSID, тип защиты WPA2/WPA3, пароль, страну и флаг скрытой сети. При редактировании пустое поле пароля сохраняет прежнее значение. При смене SSID пароль требуется ввести заново. Сохранённые пароли или хэши паролей Linux никогда не отдаются в форму.
6. Сохраните проект, подтвердив действие паролем учётной записи веб-интерфейса. Активируйте проект только после проверки готовности устройств к сетевой загрузке. Для действующей станции предварительно сделайте и проверьте резервную копию вне устройства; см. [приёмка образа и перепрошивка станции](../../image/README.md#first-hardware-test-on-an-isolated-stand).
7. Запустите настраиваемую плату в 64-битной утилитарной ОС. Прогон проверяет целостность записи образа перед этапом **Configuring the station**, после чего выполняет оставшиеся post-install шаги и опциональную проверку ОС (OS check).

Новая станция сохраняет службы DHCP/TFTP и загрузки по USB замаскированными (disabled). Подключитесь через настроенный канал управления, создайте **отдельную веб-учётную запись** командой `sudo -u www-data /var/lib/cmprovision/artisan auth:create-user`, затем выполните [настройку роли станции](operations.md#addresses-routes-and-the-provisioning-network). Пароль Linux не создаёт и не изменяет учётную запись веб-интерфейса. Без настройки Wi-Fi станция сохраняет стандартное проводное управление по Ethernet; при настройке Wi-Fi DHCP-профиль для порта стенда CM4 `eth0` исключает шлюз по умолчанию и DNS, направляя трафик управления через Wi-Fi. Настройка Wi-Fi однократно включает радиомодуль после старта NetworkManager; последующие перезагрузки сохраняют выбор оператора.

## Доставка параметров и безопасность

Настройки проекта шифруются ключом приложения (APP_KEY) провижинера. Пароли Linux хэшируются перед сохранением в базу. Каждый прогон сохраняет зашифрованный снимок параметров, поэтому редактирование проекта во время записи не меняет учётные данные текущего целевого устройства. Успешная доставка удаляет этот снимок; истёкшие прогоны очищаются воркером очереди. Резервные копии базы и ключа приложения требуют бережного хранения.

После завершения сверки утилитарная ОС монтирует записанную систему и временно запускает её SSH-сервер на TCP-порту 2224. Ключ хоста и ограниченный авторизованный ключ создаются исключительно во временной файловой системе в оперативной памяти (RAM). Сервер фиксирует анонсированный SSH host key и проверяет серийный номер, CID накопителя и идентификатор прогона перед передачей настроек в stdin процесса SSH. Учётные данные никогда не попадают в скачиваемый образ, генерируемый shell-скрипт или HTTP-ответы. Временная служба SSH останавливается сразу после настройки; её авторизация не сохраняется для штатного входа.

Первичный bootstrap опирается на **изолированную сеть стенда**, как и сама загрузка образа. SSH защищает данные от пассивного перехвата; неаутентифицированный запуск PXE/HTTP не защищает от активного злоумышленника в том же сегменте сети. Изменение host key или параметров идентификации отклоняется с ошибкой.

Повторный идентичный запрос может быть выполнен при потере ответа об успехе. Частично применённая конфигурация принимает только тот же снимок настроек. Если питание пропало до завершения настройки, координатор первой загрузки образа откажется запускать службы приложения с неполной конфигурацией; в этом случае повторите запись образа с начала. Ошибки отображаются в фазе post-install. Не вставляйте пароли в пользовательские скрипты в попытке обойти эту процедуру.

## Статус проверки

Реализация протестирована на шифрованных записях базы, формах Livewire, реальном локальном OpenSSH-сервере, парсере keyfile NetworkManager и настройке учётных записей на копии реального arm64-образа под QEMU. Полный аппаратный прогон на модуле CM4 успешно прошёл сверку образа, автоматическое подключение к Wi-Fi управления, SSH-вход по паролю и публичному ключу, реальное повышение привилегий через sudo и холодный перезапуск по PoE. Данные и конфигурация существующей станции были успешно восстановлены из резервной копии. Физическая панель отрисовала все пять экранов, а клавиша KEY2 работала штатно. Остальные элементы управления, темы Classic/Dark и настройка образа через Raspberry Pi Imager ожидают приёмки.
