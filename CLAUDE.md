# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Обзор

Веб-приложение для массовой прошивки Raspberry Pi Compute Module 4 (и Pi 4 с включённой сетевой загрузкой); CM3/3+ с 2.5.1 не поддерживаются. Стек: Laravel 13, Jetstream 5.5 (Livewire 3 + Fortify + Sanctum 4), Tailwind 3.4 (самостоятельный бинарник, без Node), SQLite. Форк `raspberrypi/cmprovision`.

Целевая среда — Raspberry Pi OS на Pi 4: пакет `cmprovision4` ставится в `/var/lib/cmprovision` и работает поверх nginx + php-fpm, dnsmasq, rpiboot и systemd. Код вызывает Linux-утилиты (`systemctl`, `journalctl`, `sudo`, `bash`, `gzip`/`xz`/`bunzip2`, `sha256sum`), поэтому страница Settings и подсчёт хешей образов работают только на Linux, а сквозной провижининг проверяется только на Pi с подключёнными модулями.

С 2.0 приложение требует PHP 8.3 и новее и ставится только на Debian 13 / Raspberry Pi OS Trixie (в `debian/control` зависимости `php-*` с эпохой: `>= 2:8.3`). `composer.json` закрепляет `config.platform.php = 8.3.0`, чтобы lock подходил и для 8.3, и для 8.4. Ветка 1.6.x (Laravel 8, PHP 7.4) заморожена на теге `v1.6.11`; рабочий провижинер пользователя — Raspberry Pi OS Trixie (Debian 13, PHP 8.4, NetworkManager) на WLAN Pi M4+ с версией 2.0.

## Команды

- Стенд: `docker/bench.sh` поднимает контейнер trixie (PHP 8.4) с nginx и php-fpm в раскладке пакета; подробности в [docker/README.md](docker/README.md). На Windows ничего не запускается — стенд живёт на Docker-хосте или в WSL-дистрибутиве.
- Зависимости: `composer install`. Node нужен только для `npm run test:js`.
- Стили: `tailwindcss -c tailwind.config.js -i resources/css/app.css -o public/css/app.css --minify` бинарником Tailwind CLI 3.4.19 (плагины forms и typography внутри); Tailwind сканирует только `resources/views`, результат коммитится. Собирайте не в OneDrive (там нельзя `vendor/`): в WSL-стенде это `/root/bench/25-css.sh`.
- Тесты: `php artisan test` (база в памяти задана в `phpunit.xml`); для одного класса или метода добавьте `--filter=AuthenticationTest`. JS без сборки: `npm run test:js` (Node ≥ 20; файлы `tests/js/` перечислены в `package.json`: каталог аргументом `node --test` не работает).
- Линтера и форматтера в проекте нет.
- Помощник светодиодов `public/tools/ledpattern` — статический 32-битный ARM-бинарник из `tools/ledpattern/ledpattern.c`, закоммичен: при сборке пакета он не собирается, `dh_strip` его не трогает. Пересборка: `sh tools/ledpattern/build.sh` с кросс-компилятором `gcc-arm-linux-gnueabihf` (в WSL-стенде — `/root/bench/18-ledpattern.sh`, исходники на stdin). Провижинер на arm64 умеет его запускать: `public/tools/ledpattern` без аргументов печатает подсказку.
- Artisan-команды проекта: `auth:create-user` — штатный способ завести пользователя (регистрация выключена в `config/fortify.php`); `ethernetswitch:configure` — добавить или изменить коммутатор стенда (только v2c; пустой адрес — список коммутаторов, `--remove=<адрес>` убирает; полная настройка — на странице Settings).
- `.deb` собирается debhelper'ом из `debian/` (например, `dpkg-buildpackage -b -us -uc`); версия пакета — верхняя запись `debian/changelog`. `dh_auto_build` запускает корневой `Makefile`, цель `vendor` (`composer install --optimize-autoloader --no-dev`), а `debian/install` кладёт `vendor/` в пакет как есть. Если `vendor/` уже существует, цель пропускается и в пакет уходит локальный `vendor/` (с dev-зависимостями, если они ставились) — перед сборкой удаляйте его. debhelper выставляет всем файлам пакета mtime из даты записи changelog, поэтому при повторной установке той же версии opcache не замечает изменённый код — `postinst` перезапускает php-fpm при обновлении; при ручном копировании файлов на сервер перезапускайте его сами. `tools/backup.sh` и `tools/restore.sh` ставятся пакетом как `cmprovision-backup`/`cmprovision-restore` в `/usr/sbin`. Обычный restore возвращает и системные конфиги (сайт nginx с сокетом конкретной версии PHP, php.ini, сеть), поэтому для переезда на другую систему есть `cmprovision-restore --data-only`: на установленный пакет он кладёт только базу, `.env` (APP_KEY), `storage/app` (прошивки), `public/uploads` (если бэкап сделан `--with-uploads`) и `etc/dnsmasq.conf`, затем выполняет `migrate`. Пакет на debhelper compat 13 (`debhelper-compat (= 13)` в `debian/control`): службы включает и запускает `dh_installsystemd`, при обновлении он их перезапускает, а не останавливает до распаковки.
- 2.5 рассчитана на 40–48 модулей разом. Сайт работает в своём пуле php-fpm: `postinst` пишет `/etc/php/<версия>/fpm/pool.d/cmprovision.conf` (`[cmprovision]`, сокет `/run/php/cmprovision-fpm.sock`, `pm.max_children` 16; файл пишется заново при каждом configure, ручная правка теряется) и вписывает сокет в сайт nginx, если пул есть. Сайт — conffile: его копия в пакете (`debian/cmprovision`) остаётся с `php-fpm.sock`, иначе dpkg при обновлении остановится на вопросе о conffile. Новая версия PHP требует `dpkg-reconfigure cmprovision4`, `postrm purge` удаляет пул. При откате ниже 2.5 `prerm` останавливает и выключает `cmprovision-queue-images`: его юнит уходит вместе с пакетом. Очередь обслуживают две службы: `cmprovision-queue` (`boards,notifications`) и `cmprovision-queue-images` (`boards,images,default`: платы, если первая занята, и задачи, оставшиеся от 2.4), Settings → Service status показывает обе. SQLite работает в WAL (`busy_timeout` 5000, `synchronous` NORMAL, `config/database.php`), транзакции — `IMMEDIATE`: замок записи берётся в начале, иначе два воркера очереди, резервируя задачи (чтение, затем запись), получают «database is locked» сразу, мимо `busy_timeout` (Laravel ставит режим на PHP 8.4 и новее). root не открывает базу: в WAL это значит открыть по имени и `-wal`/`-shm` в каталоге веб-пользователя, где подложенная ссылка заставила бы root писать в любой файл или отдать его www-data. Поэтому artisan в `postinst` и `restore.sh` идёт через `runuser -u www-data`, а `backup.sh` делает копию от www-data в его временном каталоге и пишет снимок из потока его `cat`. Вручную — тоже от www-data (`sudo -u www-data …`). `restore.sh` до подмены базы останавливает и nginx с php-fpm (соединение, открытое через подмену, смешало бы старые `-wal`/`-shm` с новой базой), а после — чистит кэш: в нём замки уникальности задач, которых в восстановленной таблице нет.
- Обновление с версии ниже 2.5 (1.x → 2.0, 2.0–2.4 → 2.5) страхует `debian/preinst`: до распаковки он запускает `cmprovision-backup` старой версии (три попытки, каждая в своём каталоге), а `.deb` старой версии кладёт в снимок сам — `dpkg-repack` отказывается работать с пакетом в состоянии half-installed, а в `preinst` старый пакет именно такой. Без снимка обновление останавливается, и старая версия остаётся установленной; `CMPROVISION_NO_SNAPSHOT=1` пропускает снимок. `cmprovision-restore` не раскладывает снимок без пакета поверх другой установленной версии (`--force` разрешает). Репетиция на WSL-стенде — `/root/bench/26-upgrade-2.0.sh` (через `27-rehearse.sh`) и `28-snapshot-guards.sh`.
- Сайт nginx включается ссылкой `sites-enabled/cmprovision.conf`: в WLAN Pi OS `nginx.conf` — ссылка на конфиг wlanpi-core, который подключает только `*.conf`. На WLAN Pi OS 26.10 наш `default_server` забирает порт 80 у переадресации веб-интерфейса WLAN Pi на https, а сам веб-интерфейс остаётся на 443. UDP 69 там держит `tftpd-hpa`, и `cmprovision-dnsmasq` без TFTP не стартует (`postinst` предупреждает). Ещё на WLAN Pi OS (но **не** на рабочем провижинере) NetworkManager не управляет Wi-Fi, а `config.txt` выключает встроенный Wi-Fi CM4 (`dtoverlay=disable-wifi`): там холодный запасной и управление Wi-Fi (2.5.2, 2.5.3) недоступны. Рабочий провижинер wlanpi-da2 — Raspberry Pi OS Trixie, где NM управляет Wi-Fi и встроенная карта включена; как собрана его сеть (две карты, keyfile-профили с привязкой к MAC, метрики, `eth0` 172.20.0.1/16 с `never-default`) — в [docs/provisioner-network.md](docs/provisioner-network.md).
- Владельцы файлов: код принадлежит root, `www-data` пишет только в `storage/`, `bootstrap/cache/`, `public/uploads/`, `etc/` (dnsmasq.conf), каталог `database/` с файлом SQLite и `.env`. Это задают `override_dh_fixperms` в `debian/rules`, функция `fix_ownership` в начале и в конце `postinst` (dpkg не меняет владельца существующих каталогов при обновлении; artisan в `postinst` и `restore.sh` работает от www-data через `runuser`) и `tools/restore.sh`. Новое место, куда приложение пишет, добавляйте во все три.

Локальный запуск повторяет `debian/postinst`. Корневого `.env.example` нет, шаблон — `debian/env.example`: скопируйте его в `.env`, замените прод-путь в `DB_DATABASE`, выполните `php artisan key:generate`, создайте пустой файл БД, затем `php artisan migrate --seed`, `php artisan auth:create-user`, `php artisan serve`. Задачи очереди (`QUEUE_CONNECTION=database`) обрабатывает `php artisan queue:work`.

## Провижининг: сквозной поток

Модуль загружает `scriptexecute` — готовые бинарники из `scriptexecute/` (ядро, initramfs `scriptexecute.img`, загрузочные файлы, оверлеи; исходников в репозитории нет):

- **CM4 / Pi 4 — по Ethernet.** `etc/dnsmasq.conf` (сервис `cmprovision-dnsmasq`) раздаёт DHCP в 172.20.0.0/16, узнаёт Pi по сигнатуре в GUID из DHCP option 97 (в обоих порядках байтов) и отдаёт `scriptexecute/` по TFTP.
- **CM4 по USB.** Модуль, загруженный по USB (bootmode 3: новый CM4 или переключённый джампером), получает `scriptexecute` от `rpiboot -l -d scriptexecute` (сервис `cmprovision-rpiboot`), а к серверу идёт по Ethernet, как при сетевой загрузке. CM3/3+ с 2.5.1 не поддерживаются: у них нет Ethernet, а USB-гаджету с IPv6 link-local `/scriptexecute` не отвечает; секции `[pi3]`, файла `cmdline.txt.ipv6ll` и правки dhcpcd в `postinst` больше нет, загрузочные файлы CM3 в `scriptexecute/` остались как есть.

Дальше модуль общается с `/scriptexecute` → `ScriptExecuteController`. Маршрут открыт без входа, но только для сети стенда: `routes/module.php` подключается в `RouteServiceProvider` с middleware `stand` (`App\Http\Middleware\StandNetworkOnly`) вместо группы `web`, поэтому у модуля нет ни сессии (раньше каждый его запрос писал строку в `sessions`), ни cookie, ни проверки CSRF. Пропускаются `NetworkStatus::STAND_NETWORK` (`172.20.0.0/16`) и loopback (`127.0.0.0/8`, `::1`: нагрузочная репетиция `tests/load` и дымовой тест стенда WSL ходят на `127.0.0.1`) по сырому `REMOTE_ADDR` соединения, а не по `$request->ip()`; остальным, в том числе IPv6 link-local (он есть и у Wi-Fi-аплинков), — 403 `text/plain` с причиной. Обратный прокси перед nginx стал бы адресом клиента сам и открыл бы маршрут всем; модуль realip самого nginx (`set_real_ip_from` и `real_ip_header` в `nginx.conf` или `conf.d/`) брал бы адрес клиента из заголовка — с тем же итогом. Сайт пакета их не задаёт. Кэш маршрутов, сделанный вручную (`artisan optimize`), убирают `route:clear` в `postinst` и `restore.sh`: иначе после обновления `/scriptexecute` остался бы в группе `web`, без проверки стенда и с отказом 419 на каждый отчёт модуля.

1. `GET ?serial=…&mac=…&model=…` — upsert `Cm` по серийному номеру; ответ — shell-скрипт из `resources/views/scriptexecute.blade.php` (`text/plain`). Модуль исполняет любой ответ, поэтому отказ и ошибка сервера тоже отдаются как shell (`resources/views/scriptexecute/failed.blade.php`): причина на консоль, «ошибка» на светодиоды.
2. Скрипт сообщает загрузчик, с которым модуль пришёл (`vcgencmd bootloader_version` и `bootloader_config`; при загрузке через rpiboot — версию с самого чипа), затем выполняет пре-скрипты проекта (первым — сгенерированная прошивка EEPROM через `flashrom`, если у проекта выбрана прошивка), затем `curl` образа | распаковка | `dd`, затем пост-скрипты (первым — сгенерированная сверка SHA256, если включён `verify`). Логи и загрузчик возвращаются multipart-POST'ами (`log` + `phase` + `retcode`, `eeprom_version` + `eeprom_config`) через функцию `report()` скрипта: она повторяет запрос до 10 минут (`--retry-connrefused`, таймауты), потому что потерянный отчёт оставляет модуль «немым» — стартовый скрипт утилитарной ОС (`S99scriptexec`, `set -e`) после ненулевого выхода скрипта просто останавливается, IP остаётся, ничего не сообщается. В `/tmp/dd.log` попадают код выхода `curl`, stderr распаковщика и вывод `dd`; при сбое фазы `dd` контроллер добавляет в запись лога расшифровку (`ScriptExecuteController::WRITE_FAILURE_HINTS`). Пока модуль пишет длинный участок нулей, он не читает из сети, поэтому для `/uploads/` в nginx стоит `send_timeout 6h` (`debian/cmprovision`, для старых установок дописывает `postinst`).
3. `?alldone=1` — отметка о завершении и событие `CmProvisioningComplete`.

Параллельно скрипт сообщает живой статус: `progress_mark` перед каждым скриптом и записью, а `progress_start`/`progress_stop` на время записи образа и сверки раз в 5 секунд шлют число секторов из `/sys/block/<dev>/stat` (поле 7 — записано, 3 — прочитано). Это `GET ?progress=<фаза>&detail=&sectors=` без повторов и с таймаутом 4 секунды: статус необязателен и не должен тормозить прошивку. Сервер хранит фазу (`preinstall`, `write`, `verify`, `postinstall`, `done`, `failed`), её начало и байты в колонках `cms` (`Cm::setPhase()`), в лог такие запросы не пишутся. Дашборд показывает модули компонентом `ProvisioningStatus`: процент, скорость, остаток и «нет связи», если модуль молчит дольше `Cm::STALE_AFTER_*`.

Каждый переход фазы или скрипта `Cm::setPhase()` дописывает в `cms.timeline` (JSON `{phase, detail, at}`, старт прогона его обнуляет). Из него карточка модуля `/cms/{serial}` (компонент `CmCard`, на неё ссылаются дашборд и список CMs) строит шаги с длительностью и скоростью (`App\Support\RunTimeline`), а `App\Support\FailureAdvice` по причине сбоя, шагу, итогу прошивки и логам подсказывает оператору, где модуль остановился и что делать.

EEPROM «до и после»: сервер хранит доложенный загрузчик в `cms.eeprom_before`/`eeprom_config_before`, снимок прошиваемых настроек проекта на старте в `eeprom_config_after` и итог в `eeprom_result`, а `cms.firmware` остаётся «что в EEPROM после». Итог (`written`, `identical`, `failed`) берётся из строки `EEPROM_RESULT=` в логе пре-скриптов. Скрипт прошивки печатает её из переменной: под `sh -v` в лог копируются и строки самого скрипта, и буквальная строка совпала бы с ответом. Сбой пре-скриптов без такой строки означает, что не прошла сама прошивка.

Светодиоды модуля задаёт `resources/views/scriptexecute/leds.blade.php`; эти функции входят и в скрипт модуля, и в ответ с отказом. Режимы выбраны с оператором на WLAN Pi M4+, где оба светодиода красные:
- «идёт» — ACT мигает 10 раз в секунду (таймер ядра), PWR горит;
- «готово» — ACT и PWR по очереди плавно загораются и гаснут;
- «ошибка» — ACT тусклый, PWR даёт двойную вспышку раз в две секунды;
- «опознать» — оба быстро чередуются 30 секунд.

Плавность и тусклость даёт помощник `ledpattern` (программный ШИМ), которого модуль скачивает с сервера. Без него те же режимы показываются триггерами ядра, без плавности. ACT сидит на GPIO 42, а этот вывод оверлей `spi-gpio40-45` отдаёт шине SPI для flashrom. Пока драйвер `leds-gpio` не переподключён (`led_take_act`), ACT не горит, поэтому переподключение идёт после пре-скриптов. Любой конец прогона, успешный или нет, уходит в `finish`, и скрипт больше не завершается. Модуль показывает итог и раз в 5 секунд шлёт `?identify=poll`. Сервер отвечает `identify`, пока оператор просил опознаться: кнопка Identify в карточке и на дашборде (`Cm::identify()`) включает мигание на `Cm::IDENTIFY_SECONDS`, а Stop (`Cm::stopIdentify()`) выключает его раньше. Пока модуль мигает, он спрашивает сервер каждые 2 секунды и мигает, только пока слышит `identify`. Опрос не пишется в лог, а `cms.polled_at` обновляется не чаще раза в минуту. По нему кнопка видна только у модуля, который ещё на стенде.

События провижининга пишутся в таблицу `cmlogs` (`ScriptExecuteController::logInfo()`); дашборд показывает последние 100 записей.

## Связи между файлами

- Параметры запроса модуля задаются плейсхолдерами в `scriptexecute/cmdline.txt` (их подставляет initramfs) и читаются в `ScriptExecuteController::startProvisoning()`. Меняйте обе стороны вместе.
- Подсеть 172.20.0.0/16 с сервером 172.20.0.1 зашита в `etc/dnsmasq.conf`, `scriptexecute/cmdline.txt`, `Host::firstAvailableIP()`, `NetworkStatus::SERVER_ADDRESS`, `NetworkStatus::STAND_NETWORK` (проверка `StandNetworkOnly`) и README.
- `scriptexecute.blade.php` рендерит shell, а `{{ }}` экранирует HTML (`&` → `&amp;`): сырой shell-код вставляйте через `{!! !!}`. Пользовательские скрипты записываются в файлы через quoted heredoc с маркером `CMPROVISIONINGEOF`. Директива Blade в конце строки с shell-кодом (`... @endif`) компилируется в `?>`, после которого PHP съедает перевод строки, и следующая строка склеивается с этой; хвост строки выводите через `{!! !!}` (после echo Blade перевод строки сохраняет). Так однажды `RETCODE=$?` приклеился к запуску скрипта.
- Строки `dhcp-host=` в `etc/dnsmasq.conf` генерирует `Settings::regenDnsmasqConfAndRestart()` из таблицы `hosts`, остальные строки сохраняются. Файл объявлен conffile в `debian/conffiles`.
- Через `sudo` веб-приложению разрешён только `systemctl restart cmprovision-dnsmasq` (`debian/010_cmprovision`); журналы читаются благодаря группе `systemd-journal`, которую выдаёт `postinst`. Новый привилегированный вызов требует правки sudoers-файла.
- Побочные эффекты активации проекта живут в `App\Services\ProjectActivator`, а не в модели: запись `public/uploads/pieeprom.bin` с вшитым `bootconf.txt` проекта и его SHA256 в настройку `active_eeprom_sha256`. Через него идут `Projects::setActive()` и `PATCH /api/projects/{id}` (`refreshIfActive()` после правки активного проекта). Форма проекта принимает прошивку только из хранилища, API — пока любую строку.
- Встроенный Wi-Fi — холодный запас (2.5.2, спека `docs/superpowers/specs/2026-10-15-uplink-cold-spare-design.md`): `tools/uplink-spare` (POSIX sh, root) ставится в `/usr/lib/cmprovision/uplink-spare`, `tools/90-cmprovision-uplink` — в `/usr/lib/NetworkManager/dispatcher.d/` (каталог дистрибутива, не conffile; NetworkManager запускает только скрипты root без записи для других), страховка — `cmprovision-uplink.timer` (через 2 минуты после загрузки, потом раз в 5 минут). Встроенный Wi-Fi — беспроводное устройство на шине `sdio`; его отключают (`nmcli device disconnect` — устройство, не профиль), когда маршрут IPv4 по умолчанию через другое устройство держится `STABLE_SECONDS` (60), и подключают, когда такого маршрута нет `LOST_SECONDS` (30); решение — по текущему состоянию, а не по событию, отложенные перепроверки — временные таймеры `systemd-run` с уникальными именами. Состояние — `/run/cmprovision/uplink-spare` (`state`: standby, active, waiting, off; `since`, `spare`, `uplink`, `up_since`, `lost_since`), его читает `NetworkStatus` (поле `spare`); «30 s» в строке `UplinkSummary` — тот же `LOST_SECONDS`. Выключатель — `SPARE=no` в `/etc/default/cmprovision-uplink` (пишет `postinst`, если файла нет; не conffile; в бэкапе). `prerm` при удалении и откате ниже 2.5.2 зовёт `uplink-spare release` — иначе встроенный остался бы отключённым до перезагрузки.
- Печать этикеток (FTP или команда; плейсхолдеры `$mac`, `$serial`, `$provisionboard`, `$switch`, `$port`, `$file`) реализована дважды: `App\Services\LabelPrinter::print()` (его зовут `ScriptExecuteController::printLabel()` и задача `PrintLabel`) и `Labels::printTestLabel()`. Когда печатать, задаёт `label_moment` проекта.

## Данные и хранилище

- `settings` — таблица ключ-значение (PK `key`): `active_project` (активен не более одного проекта), `active_eeprom_sha256`, `firmware_last_update`. Ключи `ethernetswitch_*` — настройки коммутатора 2.3: с 2.4 они нужны только для отката пакета (миграция скопировала их в `ethernet_switches` и оставила).
- Коммутаторы стенда — таблица `ethernet_switches` (модель `EthernetSwitch`): адрес (уникален), SNMP чтения и записи (`write_*` — для перезапуска по PoE; секреты скрыты от сериализации), метод таблицы MAC и сработавший метод, то, что коммутатор сказал о себе на последнем удачном опросе (`sys_name`, `base_mac` — уникален, `own_macs`), и найденные линки к соседям (`links`: ifIndex → id соседа); всё это при каждом опросе сохраняет `Stand`. `config()` — массив для SNMP-классов (`SwitchSnapshot::forConfig()`, `PoeControl::forConfig()`, привязка `SnmpClient`), `hostname()` — sysName до первой точки (IP как есть), без него адрес. Удаление коммутатора обнуляет `switch_id` у модулей и строк `poe_outages`; Settings не удаляет коммутатор, у которого порт остался выключенным после перезапуска.
- `Firmware` — не Eloquent-модель. Прошивки — файлы `<firmware_dir>/<канал>/pieeprom-*.bin` (`config/cmprovision.php`, по умолчанию `storage/app/firmware`); каналы `default` и `latest` наполняет `FirmwareUpdater` (страница Firmware и `artisan firmware:update`) из GitHub contents API `firmware-2711/*` и из пакета `rpi-eeprom`, скачивая только недостающие файлы и никогда не удаляя; старые каналы `stable`/`beta`/`critical` показываются, пока в них есть файлы. Время последней удачной проверки — настройка `firmware_last_update`.
- Порт модуля ищет задача очереди `App\Jobs\ResolveBoards` (очередь `boards`): старт с коммутаторами пишет `cms.board_pending_since` и отдаёт скрипт сразу, а задачу ставит, когда старт решён (`ScriptExecuteController::lookUpBoardLater()`, и при отказе; ошибка постановки старт не роняет). Один опрос стенда (`Stand::current()`, снимок не старше последнего старта, у повтора — новее прошлого опроса) даёт платы всех ждущих модулей по правилам `PortLookup::resolve()`; чужой опрос того же коммутатора задача ждёт до 10 с (`PortLookup::WAIT`). Модуля нет на карте — новый прогон через `RETRY_SECONDS` (3 с), через `GIVE_UP_SECONDS` (60 с) — предупреждение без платы. Запись сверяет `board_pending_since` (`settle()`): модуль, стартовавший заново, получает плату нового старта; этикетку preinstall ставит отдельной задачей `PrintLabel` тот, кто записал плату (медленный принтер не держит платы волны), отказанному модулю — нет; строки журнала этого старта получают плату задним числом. Ошибка на одном модуле не мешает остальным; упавший или снятый по таймауту прогон (`$timeout` 80 с у всех трёх задач — меньше `retry_after` очереди, 90 с) ставит следующий (`failed()`); поиск, который не выполнился за `STALE_MINUTES` (10 мин), снимается без платы и этикетки с предупреждением. Задача уникальна до взятия воркером (`ShouldBeUniqueUntilProcessing`) и следующий прогон ставит сама: старт во время прогона получает свой; прогоны двух воркеров безопасно идут одновременно. Пока плата ищется, дашборд показывает «…», карточка — «looking up the switch port…». `PortLookup::find()` — то же для одного MAC вместе с опросом. Плата — «hostname порт» (порт — описание `ifAlias`, иначе `ifName`), в `cms` идут ещё `switch_id`, `switch_name` и `switch_port`; предупреждение в журнале модуля называет коммутаторы, которые не ответили. MAC, который два порта видят поровну, — «[multiple ports]». Без коммутаторов плата — инвертированные биты джамперов (GPIO 5/13/21, `scriptexecute/config.txt`). Таблицу MAC читает `App\Services\Switch\MacTable`, методы по очереди: Q-BRIDGE-MIB (VLAN-коммутаторы: Huawei, MikroTik, Cisco Business), BRIDGE-MIB (Huawei VRP/YunShan; порт в ifIndex через `dot1dBasePortIfIndex` или HUAWEI-L2IF-MIB), HUAWEI-L2MAM-MIB и Cisco IOS — экземпляр BRIDGE-MIB на каждый VLAN (`community@vlan`, у v3 контекст `vlan-N`, список VLAN из CISCO-VTP-MIB). `App\Services\SwitchPortFinder` остался для кнопки Test на странице Settings (компонент `SwitchSettings`, список коммутаторов и форма одного) и artisan-команды: `scan()` показывает всю таблицу MAC.
- SNMP идёт через интерфейс `Snmp\SnmpClient` из контейнера (`PhpSnmpClient`, в тестах `Tests\Support\FakeSnmp`). php-snmp хранит указатель на имя контекста из `setSecurity()`, а не копию, поэтому строка контекста живёт в свойстве клиента: освобождённая, она превращалась в мусор, и коммутатор молчал. SHA-2 для v3 php-snmp умеет с PHP 8.1, поэтому `PhpSnmpClient::authProtocols()` в 2.0 предлагает все шесть протоколов. Проверка на настоящем агенте — `SnmpAgentTest` со snmpsim, см. `docker/README.md`.
- Страница Ports (`/ports`, компонент `Ports`) показывает стенд по портам коммутаторов: у каждого свой блок с корпусом, сводка с чипами одна на стенд. `App\Services\Switch\SwitchSnapshot` одним опросом читает физические порты (IF-MIB: Ethernet по `ifType` и `ifConnectorPresent`, если агент его сообщает), линк, скорость, MAC на портах (`MacTable` — та же таблица, что у `SwitchPortFinder`) и PoE (`Poe`: HUAWEI-POE-MIB по ifIndex, у Cisco IOS — CISCO-POWER-ETHERNET-EXT-MIB с ENTITY-MIB, у остальных — RFC 3621 по номеру порта). Коммутатор, не назвавший ни одного интерфейса (например, при неверной учётке v3), — ошибка, а не пустая панель. `SnapshotCache` (свой у каждого коммутатора) хранит снимок 5 секунд (у медленного коммутатора — вдвое дольше опроса), после неудачного опроса спрашивает коммутатор снова не раньше чем через 30 секунд (`ERROR_SECONDS`: иначе каждый опрос страницы и каждый старт модуля ждали бы таймаут), опрашивает одним запросом за раз, при молчании показывает последний снимок с ошибкой и пишет в журнал Laravel строку на смену «отвечает/не отвечает». `App\Support\StandMap` собирает одну карту из снимков всех коммутаторов (`Stand::current()`): раскладывает порты каждого как на корпусе (PoE-порты блоками по 12, остальные — блок аплинков) и считает сводку стенда. Ключ плитки — `s<id коммутатора>p<ifIndex>`; у плитки есть `switch`, `label` («hostname порт»: так порт называют журнал, сообщения и плашка PoE), `board` и `link`. Линк — порт, где виден собственный MAC другого коммутатора стенда (базовый MAC, `ifPhysAddress` вместе с SVI и MAC его адреса в ARP провижинера — `SwitchSnapshot` кладёт их в `own_macs`; на 2960CX MAC управления виден только так), или порт, найденный линком раньше, пока сосед молчит (`links` в строке коммутатора). Линк — аплинк: модулей и перезапуска на нём нет. MAC модуля принадлежит одному порту стенда (`owners`): с меньшим числом адресов, при равенстве — где остальные адреса тоже модули, иначе никакому; на прочих портах он не модуль и не чужое устройство. Разъём порта (`SwitchSnapshot::media()`) берётся из ENTITY-MIB, если там есть контейнеры (класс 5): гнездо SFP — контейнер с именем порта (у Cisco «GigabitEthernet0/11 Container»), combo — гнездо, рядом с которым у порта есть и своя сущность (RJ45), модуль в гнезде — сущность внутри контейнера. Без контейнеров разъём угадывается: на PoE-коммутаторе гнёзда — порты без PoE, на остальных — по имени (`StandMap::CAGE_NAMES`) или скорости от 10G. Порт без линка — свободный, даже если MAC ещё в таблице коммутатора; аплинк — порт с MAC провижинера (`NetworkStatus::serverMac()`) или больше 3 MAC, не принадлежащих модулям. Если на порту несколько модулей, те, что не идут и не опрашивают сервер (`isActive()`, `canIdentify()`), уступают живому: так коммутатор, помнящий MAC после падения линка, не показывает снятый модуль рядом с новым. Любой сбой опроса, не только `SnmpError` (например, предупреждение php-snmp о неразрешимом имени хоста), — ошибка коммутатора, а не падение страницы. Линк без единого MAC дольше 3 минут (по `ifLastChange` и `sysUpTime`) — «тихое» устройство (`LNK`), а не загружающийся модуль. Порт, где все незнакомые MAC из блоков Raspberry Pi (`StandMap::RASPBERRY_PI_PREFIXES`, реестр IEEE), в первые те же 3 минуты линка — загружающийся модуль, который ещё не обратился к серверу; если коммутатор не сообщил возраст линка, это чужое устройство. У порта в снимке остаются первые 64 MAC и их число (`mac_count`). Метод таблицы MAC, который уже находил модули (`ethernetswitch_method_detected`), достаточен, если в нём есть строки, и таблица обходится один раз; `ifDescr` и `ifSpeed` спрашиваются, только если их нет в ifXTable. Фильтр по чипам сводки живёт в Alpine. Строка внутри блока коммутатора (hostname, S/N, MAC, адрес, модель с ревизией, давность опроса, PoE в ваттах) — то, что коммутатор говорит о себе (`SwitchSnapshot::identity()`): модель, ревизия и серийный номер шасси из ENTITY-MIB (`entPhysicalClass` = 3; у Huawei серийный номер может лежать на главной плате, класс 9), базовый MAC из BRIDGE-MIB `dot1dBaseBridgeAddress` (php-snmp отдаёт шесть октетов как есть) и `sysName`. Без модели шасси коммутатор называет первая строка sysDescr. Снимок, сохранённый в кэше прошлой версией, приходит без `identity`. Замолчавший коммутатор держит в блоке последний снимок с «As of …, not answering since …», не ответивший ни разу — причину, а вердикт сводки называет молчащих; на два коммутатора с одним именем страница предупреждает. На настоящем Cisco WS-C2960CX-8PC-L (IOS 15.2(3)E2 и 15.2(7)E14) проверены поиск порта, PoE с ваттами, заголовок и перезапуск по PoE; при одной VLAN порт находит обычный BRIDGE-MIB (метод `bridge`), опрос по каждой VLAN не нужен. Гнёзда SFP и медные аплинки по ENTITY-MIB проверены на том же 2960CX. Huawei проверен только на snmpsim (`tests/fixtures/snmp`: `s5731`, `c9200`, `cbs350`, `crs`), как и combo-порты и эвристика «медь или гнездо» для коммутатора без контейнеров: SFP на портах с именем Gi она не отличает. Остальное — пункт 1 ROADMAP.
- Перезапуск по PoE (спека `docs/superpowers/specs/2026-10-12-poe-restart-design.md`). Запись идёт через `SnmpClient::set()` отдельной учёткой: Write community для v2c или свой пользователь v3 (`PoeControl::forConfig()`). Учётка своя у каждого коммутатора; у портов коммутатора без неё кнопок нет. Объект для записи даёт `Poe::admin()` с тем же сопоставлением портов, что у чтения: `hwPoePortEnable.<ifIndex>` у Huawei, `pethPsePortAdminEnable.<группа>.<порт>` у остальных (Cisco IOS эту запись принимает, проверено на 2960-CX); 1 — включено, 2 — выключено. Оба значения сохраняются при перезагрузке коммутатора. Если порт сопоставлен только по номеру (не Huawei и не Cisco IOS), запись разрешена лишь тогда, когда имя порта кончается его номером PoE: управляющий порт перед остальными сдвинул бы номера.
  - Какой порт можно перезапускать, решает `StandMap::restartBlocker()` по свежему снимку (`App\Services\Switch\Stand`, тот же `SnapshotCache`). На порту должен быть один наш модуль и ничего больше (поле плитки `others` равно 0) или загружающаяся Raspberry Pi, а PoE на порту не выключено (его включает Power on, а не перезапуск). Модуль, который пишет загрузчик EEPROM и отвечает серверу, не перезапускается: обрыв питания посреди записи оставит загрузчик, который не грузится по сети. Перед выключением каждого порта `PoeRestart::switchAllOff()` перечитывает это из базы — по MAC, которые видел снимок, и по `switch_id`/`switch_port` из поиска платы: снимку бывает полминуты, а загружающаяся Raspberry Pi за это время успевает начать запись. Порт, который не удалось так проверить, остаётся под питанием. Модуль ищется среди модулей, которые карта показывает на порту (`Stand::tileOf()`), а не по `provisioning_board` и не по любому MAC в таблице. Так снятый модуль, чей MAC коммутатор ещё помнит рядом с новым, порта не получит.
  - `PoeRestart` работает под замками затронутых коммутаторов (`poe-restart:<id>`, берутся по возрастанию id): перезапуск на одном коммутаторе не мешает другому. Замок живёт 10 минут: столько идёт перезапуск 48 портов у замолчавшего коммутатора. Замок своего коммутатора берёт Check write access, чтобы записанное обратно значение не выключило порт после перезапуска. Решение принимается по снимку коммутатора не старше 30 секунд (`SNAPSHOT_SECONDS`): пока другая страница опрашивает коммутатор, `SnapshotCache` отдаёт последний снимок, которому может быть сколько угодно. Порты коммутатора без записи, молчащего или прочитанного давно пропускаются с причиной (`PoeRestart::switchBlocker()`); сначала выключаются порты всех коммутаторов, потом одна пауза, потом каждый коммутатор включает свои по одному. Итог ключуется плиткой: `['label', 'serial', 'why']`. До выключения пишет строку в `poe_outages` (с `switch_id`), затем выключает и читает значение обратно, ждёт 5 секунд и включает порты по одному с шагом 0,5 с. На включение три попытки с чтением обратно. Сбой на одном порту не мешает включить остальные. Отказ коммутатора на выключении, как и запись, после которой порт всё ещё «включено», удаляет строку. Таймаут или предупреждение php-snmp её не удаляют: коммутатор мог выключить порт и потерять ответ, поэтому порт включается вместе с остальными. У загружающейся Raspberry Pi нет серийного номера, и в `cmlogs` пишется пустая строка, потому что колонка `cm` не допускает NULL.
  - Открытая строка с ошибкой или старше 2 минут — порт остался выключенным (`PoeOutage::stayedOff()`). Его показывает плашка `PoeOutages` с кнопками Power on и Forget на дашборде, странице Ports и в карточке модуля; Power on пишет через коммутатор строки (`switch_id`, у строк до 2.4 — по адресу `switch_host`). После перезапуска страница шлёт событие `poe-outages-changed`, и плашка появляется сразу. Страница Ports закрывает такую строку, если объект порта на коммутаторе снова «включено»: `closeSeenOn()` читает его учёткой на чтение, у каждого отвечающего коммутатора — только его строки (`PoeOutage::forSwitch()`). Слова статуса PoE у вендоров разные, а снимок мог быть снят ещё до выключения, поэтому по снимку строки не закрываются.
  - Кнопки: карточка модуля (строка «Power (PoE)»), панель порта и сводка Ports, дашборд («Restart failed (N)» и Restart в строке упавшего или замолчавшего модуля). Дашборд предлагает Restart модулю, если запись есть у его коммутатора (`cms.switch_id`), а модулю без него — если она есть хоть у одного. Строки журнала `cmlogs` пишутся с именем оператора. Строка «Power (PoE)» спрашивает коммутатор уже после показа карточки (`wire:init="loadPower"`): медленный коммутатор не задерживает её открытие.
- Образы `.gz`/`.xz`/`.bz2` принимает обычный контроллер `AddImageController`, потому что Livewire не справляется с большими файлами (лимит 8G задан в `debian/cmprovision` и `postinst`). Файлы лежат в `public/uploads/` под случайными именами, модули качают их напрямую через nginx. SHA256 сжатого и распакованного образа считает задача очереди `ComputeSHA256` (очередь `images`, служба `cmprovision-queue-images`); пока нет `uncompressed_sha256`, проект с `verify` провижинить отказывается.
- События `CmProvisioningStarted`, `CmProvisioningComplete` и `CmProvisioningFailed` (причина в `phase_detail`) — точки расширения: авто-обнаружение событий включено (`EventServiceProvider::shouldDiscoverEvents()`), слушателю достаточно лежать в `app/Listeners`.
- Уведомления: каналы в таблице `notification_channels` (типы — `NotificationChannel::TYPES`, настройка на странице Settings, компонент `NotificationSettings`), отправка — `App\Services\Notifier`. Слушатель `SendProvisioningNotifications` пишет событие в `notification_outbox` (строка на каждый включённый канал), отправляет задача `FlushNotifications` (очередь `notifications`) через окно `WINDOW` (10 с) пачками: чату — сообщение на партию с частями по событиям, на которые он подписан (длиннее 4000 символов делится по строкам), JSON webhook — запрос на событие. Сводка правится раньше ответов, и каждое сообщение помечает свои события отправленными: 429 посреди пачки ничего не шлёт дважды. Другая ошибка правки (сводку удалили в чате) ответы не держит и остаётся в `last_error`. Упавший прогон ставит следующий (`FlushNotifications::failed()`); ошибка записи события в очередь до модуля не доходит (слушатель её ловит). Между вызовами к одному чату не меньше секунды (`Notifier::pace()`), 429 откладывает канал на `retry_after` (кэш `notify-blocked:<id>`), ошибка — повтор через 30 с (до того канал не трогает и прогон, поставленный новым событием), после 5 попыток событие снимается с `error`; отправленные события хранятся `KEEP_DAYS` (7 дней). Сводку, которую начал публиковать и не дописал убитый процесс (пустой `external_id` старше минуты), публикует следующий прогон. Строки выключенного канала снимаются, удалённого — уходят каскадом, события удалённого модуля пропускаются. Адрес Bot API — `config('cmprovision.telegram_api')` (`TELEGRAM_API`: заглушка репетиции). Кнопка Test шлёт сразу. В JSON вебхука есть `board` и отдельно `switch` и `port` (пустые без коммутатора). Модули одного проекта объединяются в партию (`notification_batches`, `cms.notification_batch_id`), которая закрывается через `NotificationBatch::IDLE_HOURS` простоя, при смене проекта или кнопкой. Партию выбирает `NotificationBatch::current()` под замком `notification-batch`: волна стартов попадает в одну. Боты (Mattermost, Telegram) держат на партию тред: сводку правят после каждой пачки свежими числами, модули идут ответами. Только один процесс публикует сводку, это гарантирует уникальный ключ `notification_threads`. Ошибки отправки пишутся в `last_error` канала и до модуля не доходят. Сертификат сервера (`App\Services\TlsTrust`; типы `NotificationChannel::TLS_TYPES` — Mattermost bot и оба webhook): канал может доверять своим сертификатам (настройка `tls_ca` в PEM и `tls_ca_for` — «host:port», для которого они сохранены; на другом адресе они не действуют) или не проверять сертификат вовсе (`tls_insecure`). Сертификаты уходят в curl через `CURLOPT_CAINFO_BLOB` в дополнение к системным CA (каталог CA curl остаётся), имя хоста проверяется. curl по умолчанию принимает доверенным и не корневой сертификат (partial chain), поэтому промежуточный CA из цепочки сервера переживает перевыпуск сертификата; отсюда зависимость пакета от php-curl. Кнопка Fetch from the server (`TlsTrust::fetch()`) берёт цепочку, которую предъявляет сервер, и предупреждает, если сертификат выписан на другое имя. Ошибке сертификата `TlsTrust::explain()` ставит в начало подсказку, что делать (о своём сертификате — только каналам, у которых он бывает): таблица каналов показывает только начало `last_error`. Тексты ошибок для страницы готовит `Notifier::errorText()`: Guzzle пишет в сообщение URL запроса, а в URL Telegram — токен бота, поэтому `Notifier::redact()` его вырезает. `TlsTrust::fetch()` — метод экземпляра из контейнера: тест подменяет сеть.
- При обновлении пакета `postinst` выполняет только `migrate`, сидеры запускаются лишь при первой установке. Данные для существующих установок добавляйте миграцией.
- `postinst` не должен падать: запуск служб (`#DEBHELPER#`) стоит в его конце, и после ошибки сервер остаётся без dnsmasq и очереди до следующего успешного configure. Команды artisan там — только с `--force` (в `.env` стоит `APP_ENV=production`).
- `postinst` на каждом configure идемпотентно правит окружение существующих установок: `send_timeout` для `/uploads/` в сайте nginx, `upload_tmp_dir = storage/app/upload-tmp` в php.ini (на Debian 13 `/tmp` в RAM), `APP_ENV=production`/`APP_DEBUG=false` в `.env` вместо значений из старого шаблона. Новые правки такого рода добавляйте туда же, а не только в шаблоны: сайт nginx и `.env` при обновлении не перезаписываются.
- Время хранится в UTC, показывается в `config('app.display_timezone')` (`APP_DISPLAY_TIMEZONE` или системный пояс сервера) через макрос `Carbon::local()`; CSV-экспорт и API отдают UTC. Системный пояс читает `App\Support\SystemTimezone` из `/etc/timezone` или ссылки `/etc/localtime`: спрашивать PHP нельзя — PHP 8.4 в Debian 13 возвращает UTC при любом поясе системы, и `date.timezone` по умолчанию там тоже `UTC`.

## Фронтенд

- Страницы — full-page Livewire-компоненты (`app/Http/Livewire/*` + `resources/views/livewire/*`), подключённые прямо в `routes/web.php`.
- Livewire 3: классы компонентов остаются в `App\Http\Livewire` (`class_namespace` в `config/livewire.php`), макет полностраничных компонентов — `layouts.app`. Простой `wire:model` отправляет значение с действием, `wire:model.live` — сразу. Методы компонента, которые не должны вызываться из браузера, — `protected`: всё публичное доступно как действие. Объекты, которые Livewire 3 не сериализует (например, `App\Models\Firmware`), передаются в шаблон данными `render()`, а не публичными свойствами.
- Две ловушки шаблонов. Тестовый помощник Livewire 3 (`assertSee`) вырезает значения `wire:snapshot` и `wire:effects` заменой по всей странице: при `wire:effects="[]"` из проверяемого HTML пропадают все `[]` (например, в `x-data`), поэтому такую разметку проверяйте `assertSeeHtml`. Blade ищет php-блоки раньше, чем вырезает комментарии: в шаблоне с однострочными `@php(...)` блок `@php … @endphp` — и даже слово `@endphp` в комментарии `{{-- --}}` — захватывает текст от первой однострочной директивы и ломает компиляцию (`ports.blade.php` поэтому обходится однострочными).
- Раскладка Laravel 8 сохранена (Kernel, провайдеры, конфиги, `App\Exceptions\Handler`), `bootstrap/app.php` нет. То, что Laravel 11+ задаёт там, здесь в провайдерах: куда отправлять гостя — `AuthenticateSession::redirectUsing()` и `AuthenticationException::redirectUsing()` в `AppServiceProvider`. Без них сессия, которую закрыла смена пароля в другом браузере, получает пустой 401 вместо страницы входа.
- Шаблоны Jetstream 5 опубликованы в `resources/views/{components,api,profile,auth}` (компоненты `<x-…>` без префикса) и переведены на токены; неиспользуемые (welcome, условия и политика, удаление аккаунта, команды) удалены.
- Каркас (вариант A): верхняя панель (`navigation-menu`, 48 px, 64 px в просторной плотности) вместо полосы заголовка, страница — `.cmp-page` во всю ширину до 1920 px; название страницы во вкладке — `#[Title]` полностраничного компонента или `<x-app-layout title>`. Правила ячеек `.cmp-table` весят один класс (`:where`), поэтому класс на ячейке (`align-top`, цвет рамки) их перебивает: отступы старой вёрстки на ячейках не оставляйте. Карточка с таблицей — `.cmp-card-scroll`: уже `xl` таблица прокручивается вбок внутри карточки и шапка прилипает к её верху (карточка тогда сама контейнер прокрутки), с `xl` шапка прилипает под панелью. Ссылки страниц в панели при нехватке места прокручиваются к текущей (`aria-current`), а не наезжают на итог партии.
- Оформление: `public/js/appearance.js` в `<head>` до отрисовки ставит на `<html>` `data-style` (warm, neutral), `data-density` (compact, roomy) и `data-mode` (light, dark) по выбору из `localStorage` (`cmprovision-appearance`, по умолчанию warm, compact, auto). Auto светлая от восхода до заката в городе часового пояса сервера (`App\Support\SunPlace` кладёт `data-sun`); без места (UTC) и без восхода — системная тема; на восходе и закате тема меняется без перезагрузки. Таймер, заведённый до сна ноутбука, срабатывает позже на время сна, а страница из bfcache не слышала событий `storage`, поэтому выбор перечитывается на `pageshow` и `visibilitychange`, а тема сверяется раз в минуту. Окно Appearance в панели — Alpine `appearancePopover()`.
- Цвета — только токены: CSS-переменные четырёх тем и плотности в `app.css`, цвета Tailwind (`bg-panel`, `text-fg-muted`, `bg-neg-bg`…) и общие классы `.cmp-*`. `TokenGuardTest` не пускает в шаблоны цвета палитры, произвольные цвета (`bg-[#…]`; `var()` можно), `dark:` и цвета в `style` (hex, `rgb()`, названия), `PageLayoutTest` следит, что каждая страница в рамке `.cmp-page`; контраст пар текста проверяет `tests/js/tokens.test.mjs`. Собранный `public/css/app.css` проверяет `tests/js/css-rules.test.mjs`: плагин forms красит поля и флажки сам (синее кольцо фокуса, белый отступ кольца), причём `.form-checkbox:focus` — в слое компонентов, после базовых правил, поэтому переопределение — `input.form-checkbox:focus`; у `.cmp-field` — `background-color`, а не `background`: сокращение стирает стрелку `select`. Корпус и плитки страницы Ports (`ports-*`) рисуют железо и остаются в своих цветах.
- Итог партии: `NotificationBatch::open()` (не закрыта, без простоя, активного проекта) и `App\Support\BatchSummary`; компонент `BatchIndicator` в панели опрашивает раз в 10 с с `keep-alive` (без него Livewire почти не опрашивает фоновую вкладку) и кладёт `data-tab-title`/`data-tab-icon`, которые `public/js/tab-status.js` переносит в заголовок и значок вкладки (`favicon-run|fail|stale|done`). Заголовок — состояние партии, затем название страницы («1 failed · 3 running · CMs · cmprovision»). Модули, которые молчат дольше `Cm::STALE_AFTER_*` (`silentFor()`), `BatchSummary` считает отдельно (`silent`; `running` — активные, которые ещё отвечают): «1 no report», жёлтый чип в панели и жёлтая точка (`stale`), в оценку окончания они не входят. Счётчики `counts` остаются как у ботов (`NotificationBatch::counts()`). В начале прогона модуль забывает партию прошлого прогона: отказ до назначения партии (нет активного проекта) ни к какой партии не относится. Что пользователь раскрыл или открыл (журнал, окно Appearance), живёт в Alpine: атрибуты разметки Livewire при опросе возвращает к серверным.
- Знак cmprovision (линия «cm» на тёплой плитке) заменил малину Raspberry Pi: шапка — `application-mark`, страницы входа — `authentication-card-logo` (знак и название живым текстом, `.cmp-lockup` в `app.css`), вкладка — `public/favicon.svg`, `favicon.ico` и `apple-touch-icon.png` (и `favicon-run|fail|stale|done` для состояния партии). Цвета знака — токены `--mark-*`: в тёмной теме плитка светлее. У каждой встроенной копии свой id градиента: id общие для всей страницы. Исходники, PNG для этикеток, правила и генератор `build_logo.py` — в `docs/brand`; `BrandingTest` проверяет цвета в страницах и файлы иконок.
- Собранный `public/css/app.css` закоммичен и попадает в `.deb` как есть. Своего JS-бандла нет: Alpine 3 приходит со скриптами Livewire, `public/js/upload-progress.js`, `appearance.js` и `tab-status.js` — обычные скрипты без сборки, покрыты `tests/js`.
- Загрузка образа идёт XMLHttpRequest'ом из Alpine-компонента `imageUploader()` (определён в `images.blade.php`, форма в `addimage.blade.php`) на тот же `POST /addImage`; расчёт скорости и остатка — `public/js/upload-progress.js`, обычный скрипт без сборки, покрыт `tests/js`. Пока у какого-то образа не посчитан SHA256, страница Images опрашивает сервер (`wire:poll`), кроме момента, когда открыт диалог.
- Значок подключения сервера в верхней панели — компонент `UplinkIndicator`, один экземпляр на все размеры экрана. Данные собирает `App\Services\NetworkStatus` так, как может пользователь www-data:
  - маршрут по умолчанию — из `/proc/net/route`;
  - тип, шина и драйвер интерфейса — из `/sys/class/net`;
  - Wi-Fi — через `iw dev <if> link|info` (`App\Support\WifiLink`, поколение по признакам HT/VHT/HE/EHT);
  - адреса — из `net_get_interfaces()`;
  - «предпочтительное подключение не подключено» — по профилям `nmcli` с меньшей метрикой.

  Состояние холодного запаса встроенного Wi-Fi `NetworkStatus` читает из `/run/cmprovision/uplink-spare`. Тексты значка и подсказки готовит `App\Support\UplinkSummary`. Снимок лежит в кэше под ключом `network-status`. Значок сам обновляется раз в `POLL_SECONDS` (300 с) и берёт снимок не старше `PASSIVE_MAX_AGE`, а наведение или нажатие — не старше `FRESH_MAX_AGE` (10 с).
