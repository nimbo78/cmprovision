# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Обзор

Веб-приложение для массовой прошивки Raspberry Pi Compute Module 4 (и Pi 4 с включённой сетевой загрузкой); CM3/3+ с 2.5.1 не поддерживаются. Стек: Laravel 13, Jetstream 5.5 (Livewire 3 + Fortify + Sanctum 4), Tailwind 3.4 (самостоятельный бинарник, без Node), SQLite. Форк `raspberrypi/cmprovision`.

Целевая среда — Raspberry Pi OS на Pi 4: пакет `cmprovision4` ставится в `/var/lib/cmprovision` и работает поверх nginx + php-fpm, dnsmasq, rpiboot и systemd. Код вызывает Linux-утилиты (`systemctl`, `journalctl`, `sudo`, `bash`, `gzip`/`xz`/`bunzip2`, `sha256sum`), поэтому страница Settings и подсчёт хешей образов работают только на Linux, а сквозной провижининг проверяется только на Pi с подключёнными модулями.

Приложение требует исправленных версий PHP: 8.3.36+ для ветки 8.3, 8.4.27+ для 8.4, 8.5.12+ для 8.5 (CVE-2026-109618/109619), и ставится на Debian 13 / Raspberry Pi OS Trixie. `debian/control` требует реальные версионированные пакеты CLI и FPM: версия метапакета `php-fpm` не отражает патч PHP. `composer.json` закрепляет `config.platform.php = 8.3.36`, чтобы lock подходил для поддерживаемых веток; `composer check-platform-reqs --lock --no-dev` проверяет фактический CLI, и сборка Docker выполняет эту проверку. Upload Progress остаётся с настройкой PHP по умолчанию; исправление обеспечивает обновлённый PHP. Ветка 1.6.x (Laravel 8, PHP 7.4) заморожена на теге `v1.6.11`; рабочий провижинер пользователя — Raspberry Pi OS Trixie (Debian 13, PHP 8.4, NetworkManager) на WLAN Pi M4+ с версией 2.16.0.

- Тесты: `php artisan test` (база в памяти задана в `phpunit.xml`); для одного класса или метода добавьте `--filter=AuthenticationTest`. JS без сборки: `npm run test:js` (Node ≥ 20; файлы `tests/js/` перечислены в `package.json`: каталог аргументом `node --test` не работает).
- Линтера и форматтера в проекте нет.

Пересборка: `sh tools/ledpattern/build.sh` с кросс-компилятором `gcc-arm-linux-gnueabihf` (в WSL-стенде — `/root/bench/18-ledpattern.sh`, исходники на stdin). Провижинер на arm64 умеет его запускать: `public/tools/ledpattern` без аргументов печатает подсказку.
- Artisan-команды проекта: `auth:create-user` — штатный способ завести пользователя (регистрация выключена в `config/fortify.php`); `ethernetswitch:configure` — добавить или изменить коммутатор стенда (только v2c; пустой адрес — список коммутаторов, `--remove=<адрес>` убирает; полная настройка — на странице Settings).
- `.deb` собирается debhelper'ом из `debian/` (например, `dpkg-buildpackage -b -us -uc`); версия пакета — верхняя запись `debian/changelog`. `dh_auto_build` запускает корневой `Makefile`, цель `vendor` (`composer install --optimize-autoloader --no-dev`), а `debian/install` кладёт `vendor/` в пакет как есть. Если `vendor/` уже существует, цель пропускается и в пакет уходит локальный `vendor/` (с dev-зависимостями, если они ставились) — перед сборкой удаляйте его. debhelper выставляет всем файлам пакета mtime из даты записи changelog, поэтому при повторной установке той же версии opcache не замечает изменённый код — `postinst` перезапускает php-fpm при обновлении; при ручном копировании файлов на сервер перезапускайте его сами. `tools/backup.sh` и `tools/restore.sh` ставятся пакетом как `cmprovision-backup`/`cmprovision-restore` в `/usr/sbin`. После снимка в `/var/backups/cmprovision` `backup.sh` оставляет пять последних (`--keep N|all`, `CMPROVISION_BACKUP_KEEP`) и удаляет только каталоги `<дата>-<время>-<версия>`; свой каталог назначения он не чистит, `--prune` только чистит (тест — `BackupRetentionTest`). Обычный restore возвращает и системные конфиги (сайт nginx с сокетом конкретной версии PHP, php.ini, сеть), поэтому для переезда на другую систему есть `cmprovision-restore --data-only`: на установленный пакет он кладёт только базу, `.env` (APP_KEY), `storage/app` (прошивки), `public/uploads` (если бэкап сделан `--with-uploads`) и `etc/dnsmasq.conf`, затем выполняет `migrate`. Пакет на debhelper compat 13 (`debhelper-compat (= 13)` в `debian/control`): службы включает и запускает `dh_installsystemd`, при обновлении он их перезапускает, а не останавливает до распаковки.
- Как передать код на рабочий провижинер (`wlanpi-da2`), собрать там `.deb` и поставить его — [docs/deploy-to-provisioner.md](docs/deploy-to-provisioner.md). Ручной флоу до пуша: `git archive HEAD` на провижинер в пустой каталог, `dpkg-buildpackage -b -us -uc -d` (пакет `Architecture: all`, собирается на самом da2), затем `dpkg -i`.
- 2.5 рассчитана на 40–48 модулей разом. Сайт работает в своём пуле php-fpm: `postinst` пишет `/etc/php/<версия>/fpm/pool.d/cmprovision.conf` (`[cmprovision]`, сокет `/run/php/cmprovision-fpm.sock`, `pm.max_children` 16; файл пишется заново при каждом configure, ручная правка теряется) и вписывает сокет в сайт nginx, если пул есть. Сайт — conffile: его копия в пакете (`debian/cmprovision`) остаётся с `php-fpm.sock`, иначе dpkg при обновлении остановится на вопросе о conffile. Новая версия PHP требует `dpkg-reconfigure cmprovision4`, `postrm purge` удаляет пул. При откате ниже 2.5 `prerm` останавливает и выключает `cmprovision-queue-images`: его юнит уходит вместе с пакетом. Очередь обслуживают две службы: `cmprovision-queue` (`boards,notifications`) и `cmprovision-queue-images` (`boards,images,default`: платы, если первая занята, и задачи, оставшиеся от 2.4), Settings → Status показывает обе. SQLite работает в WAL (`busy_timeout` 5000, `synchronous` NORMAL, `config/database.php`), транзакции — `IMMEDIATE`: замок записи берётся в начале, иначе два воркера очереди, резервируя задачи (чтение, затем запись), получают «database is locked» сразу, мимо `busy_timeout` (Laravel ставит режим на PHP 8.4 и новее). root не открывает базу: в WAL это значит открыть по имени и `-wal`/`-shm` в каталоге веб-пользователя, где подложенная ссылка заставила бы root писать в любой файл или отдать его www-data. Поэтому artisan в `postinst` и `restore.sh` идёт через `runuser -u www-data`, а `backup.sh` делает копию от www-data в его временном каталоге и пишет снимок из потока его `cat`. Вручную — тоже от www-data (`sudo -u www-data …`). `restore.sh` до подмены базы останавливает и nginx с php-fpm (соединение, открытое через подмену, смешало бы старые `-wal`/`-shm` с новой базой), а после — чистит кэш: в нём замки уникальности задач, которых в восстановленной таблице нет.
- Обновление с версии ниже 2.5 (1.x → 2.0, 2.0–2.4 → 2.5) страхует `debian/preinst`: до распаковки он запускает `cmprovision-backup` старой версии (три попытки, каждая в своём каталоге), а `.deb` старой версии кладёт в снимок сам — `dpkg-repack` отказывается работать с пакетом в состоянии half-installed, а в `preinst` старый пакет именно такой. Без снимка обновление останавливается, и старая версия остаётся установленной; `CMPROVISION_NO_SNAPSHOT=1` пропускает снимок. `cmprovision-restore` не раскладывает снимок без пакета поверх другой установленной версии (`--force` разрешает). Репетиция на WSL-стенде — `/root/bench/26-upgrade-2.0.sh` (через `27-rehearse.sh`) и `28-snapshot-guards.sh`.
- Сайт nginx включается ссылкой `sites-enabled/cmprovision.conf`: в WLAN Pi OS `nginx.conf` — ссылка на конфиг wlanpi-core, который подключает только `*.conf`. На WLAN Pi OS 26.10 наш `default_server` забирает порт 80 у переадресации веб-интерфейса WLAN Pi на https, а сам веб-интерфейс остаётся на 443. UDP 69 там держит `tftpd-hpa`, и `cmprovision-dnsmasq` без TFTP не стартует (`postinst` предупреждает). Ещё на WLAN Pi OS (но **не** на рабочем провижинере) NetworkManager не управляет Wi-Fi, а `config.txt` выключает встроенный Wi-Fi CM4 (`dtoverlay=disable-wifi`): там холодный запасной и управление Wi-Fi (2.5.2, 2.5.3) недоступны. Рабочий провижинер wlanpi-da2 — Raspberry Pi OS Trixie, где NM управляет Wi-Fi и встроенная карта включена; как собрана его сеть (две карты, keyfile-профили с привязкой к MAC, метрики, `eth0` 172.20.0.1/16 с `never-default`) — в [docs/provisioner-network.md](docs/provisioner-network.md).
- Владельцы файлов: код принадлежит root, `www-data` пишет только в `storage/`, `bootstrap/cache/`, `public/uploads/`, `etc/` (dnsmasq.conf и ссылка `etc/boot`), каталог `database/` с файлом SQLite и `.env`. Это задают `override_dh_fixperms` в `debian/rules`, функция `fix_ownership` в начале и в конце `postinst` (dpkg не меняет владельца существующих каталогов при обновлении; artisan в `postinst` и `restore.sh` работает от www-data через `runuser`) и `tools/restore.sh`. Новое место, куда приложение пишет, добавляйте во все три.

Локальный запуск повторяет `debian/postinst`. Корневого `.env.example` нет, шаблон — `debian/env.example`: скопируйте его в `.env`, замените прод-путь в `DB_DATABASE`, выполните `php artisan key:generate`, создайте пустой файл БД, затем `php artisan migrate --seed`, `php artisan auth:create-user`, `php artisan serve`. Задачи очереди (`QUEUE_CONNECTION=database`) обрабатывает `php artisan queue:work`.

## Провижининг: сквозной поток

Модуль загружает утилитарную ОС: нашу (`scriptexecute64/`, собирается из `utility-os/`, раздел «Утилитарная ОС») или старую (`scriptexecute/`, готовые файлы raspberrypi/scriptexecutor 2022, 32 бита). Какую — задаёт ссылка `etc/boot`:

- **CM4 / Pi 4 — по Ethernet.** `etc/dnsmasq.conf` (сервис `cmprovision-dnsmasq`) раздаёт DHCP в 172.20.0.0/16, узнаёт Pi по сигнатуре в GUID из DHCP option 97 (в обоих порядках байтов) и отдаёт по TFTP каталог, на который указывает `etc/boot` (`tftp-root=/var/lib/cmprovision/etc/boot`).
- **CM4 по USB.** Модуль, загруженный по USB (bootmode 3: новый CM4 или переключённый джампером), получает утилитарную ОС от `rpiboot -l -d /var/lib/cmprovision/etc/boot/usb` (сервис `cmprovision-rpiboot`, при сбое `Restart=on-failure`). В каталоге `usb/` каждой ОС лежат `bootfiles.bin` (с usbboot 20261002 вторую ступень `bootcode4.bin` берёт он), `config.txt` из одной строки `boot_ramdisk=1` и `boot.img` — FAT32-образ с файлами этой ОС (`config.txt`, `cmdline.txt`, ядро, `scriptexecute.img`, `start4.elf`, `fixup4.dat`, три dtb и оверлеи `dwc2` и `spi-gpio40-45`): `rpiboot` отдаёт его RAM-диском, и ядро стартует из него. Образ — от 40 до 180 МиБ (предел CM4); его собирает `tools/utility-os/usb_image.py` (dosfstools и mtools; заодно переписывает `MANIFEST`), `--check` сверяет каждый файл с каталогом ОС, а `UtilityOsUsbTest` — что поставляемый образ содержит выбранную ОС. Сетевая загрузка берёт файлы каталога ОС, а не `usb/`. К серверу модуль идёт по Ethernet, как при сетевой загрузке. CM3/3+ с 2.5.1 не поддерживаются: у них нет Ethernet, а USB-гаджету с IPv6 link-local `/scriptexecute` не отвечает; секции `[pi3]`, файла `cmdline.txt.ipv6ll` и правки dhcpcd в `postinst` больше нет, загрузочные файлы CM3 в `scriptexecute/` остались как есть.

USB-подготовка (2.12, `docs/usb-provisioning.md#set-a-board-to-boot-from-the-network-usb-prep`): пока режим включён (`App\Services\UsbPrep`, настройка `usb_prep_until`, кнопка на Dashboard — `UsbPrepPanel`, час простоя и выключается сам, каждая плата продлевает), плата, загруженная по USB (`bootmode=3`), получает не проект, а только загрузчик: свою прошивку из хранилища и свои настройки (`usb_prep_firmware`, `usb_prep_settings`, по умолчанию флотские с `BOOT_ORDER=0xf12`, сеть первой; карточка в Settings → Provisioning — `UsbPrepSettings`), образ собирается в `public/uploads/pieeprom-usbprep.bin` с суммой в `usb_prep_sha256` (`EepromImage::forFirmware()`, его же использует `ProjectActivator`; скрипт прошивки — `EepromFlashScript::make()`). В `startLockedProvisioning` это `$prep`: проекта нет (`$project = null`), строка получает `cms.usb_prep_at`, ответ — `prepScript()` с `resources/views/scriptexecute/usbprep.blade.php` (версия загрузчика, прошивка, отчёт `phase=preinstall`, `alldone`, `finish done`; образа, `blkdiscard`, проверки ОС и этикетки нет). `provisioningComplete()` для такой строки — `prepComplete()` (фаза `done` с подсказкой вынуть и переставить в PoE), а `failed()` для неё ничего не рассылает: события `CmProvisioningStarted/Complete/Failed` и партия не затрагиваются (`notification_batch_id` пуст). Обычный старт сбрасывает `usb_prep_at`, поэтому плата, потом прошитая на стенде, снова обычная. Загрузчик остаётся «сеть первой», пока проект не прошьёт своё EEPROM (у проекта без прошивки EEPROM порядок остаётся), и без DHCP-сервера такая плата ждёт сеть до 45 с. Тесты — `UsbPrepTest`, `UsbPrepPagesTest`.

Дальше модуль общается с `/scriptexecute` → `ScriptExecuteController`. Маршрут открыт без входа, но только для сети стенда: `routes/module.php` подключается в `RouteServiceProvider` с middleware `stand` (`App\Http\Middleware\StandNetworkOnly`) вместо группы `web`, поэтому у модуля нет ни сессии (раньше каждый его запрос писал строку в `sessions`), ни cookie, ни проверки CSRF. Пропускаются `NetworkStatus::STAND_NETWORK` (`172.20.0.0/16`) и loopback (`127.0.0.0/8`, `::1`: нагрузочная репетиция `tests/load` и дымовой тест стенда WSL ходят на `127.0.0.1`) по сырому `REMOTE_ADDR` соединения, а не по `$request->ip()`; остальным, в том числе IPv6 link-local (он есть и у Wi-Fi-аплинков), — 403 `text/plain` с причиной. Обратный прокси перед nginx стал бы адресом клиента сам и открыл бы маршрут всем; модуль realip самого nginx (`set_real_ip_from` и `real_ip_header` в `nginx.conf` или `conf.d/`) брал бы адрес клиента из заголовка — с тем же итогом. Сайт пакета их не задаёт. Кэш маршрутов, сделанный вручную (`artisan optimize`), убирают `route:clear` в `postinst` и `restore.sh`: иначе после обновления `/scriptexecute` остался бы в группе `web`, без проверки стенда и с отказом 419 на каждый отчёт модуля.

1. `GET ?serial=…&mac=…&model=…` — upsert `Cm` по серийному номеру; ответ — shell-скрипт из `resources/views/scriptexecute.blade.php` (`text/plain`). Модуль исполняет любой ответ, поэтому отказ и ошибка сервера тоже отдаются как shell (`resources/views/scriptexecute/failed.blade.php`): причина на консоль, «ошибка» на светодиоды.
2. Скрипт сообщает загрузчик, с которым модуль пришёл (`vcgencmd bootloader_version` и `bootloader_config`; при загрузке через rpiboot — версию с самого чипа), затем выполняет пре-скрипты проекта (первым — сгенерированная прошивка EEPROM через `flashrom`, если у проекта выбрана прошивка), затем запись образа (`resources/views/scriptexecute/write.blade.php`, 2.6.1): `fetch_image | распаковка | запись`. Оборванную загрузку `fetch_image` продолжает с принятого байта (`curl -C`, байты считает сам curl через `-w '%{stderr}FETCHED %{size_download}'`: BusyBox `dd` числа байт не печатает), а распаковщик и `dd` работают всё время и обрыва не видят; 5xx и сбои связи — повтор раз в 5 с, 10 минут без байта — провал, 4xx и код 33 (сервер отдал файл целиком) — провал сразу, упавший распаковщик (код 23) и ответ без единого байта, когда файл ещё не докачан (на сервере он короче, чем сказано в скрипте), — тоже сразу. `--speed-limit` нет: пока `dd` пишет длинные нули, curl законно стоит минутами (для `/uploads/` в nginx поэтому `send_timeout 6h`: `debian/cmprovision`, для старых установок дописывает `postinst`), мёртвую связь ловит `--keepalive-time 15`. Первый мебибайт (таблица разделов) явно зануляется после `blkdiscard` и пишется последним: модуль, обесточенный посреди записи, с eMMC не грузится и уходит в сеть. Суммы байт на модуле — через awk (`bytes_add`, `bytes_at_least`: оболочка может быть 32-битной). Потом пост-скрипты (первым — сгенерированная сверка SHA256, если включён `verify`). Логи и загрузчик возвращаются multipart-POST'ами (`log` + `phase` + `retcode`, `eeprom_version` + `eeprom_config`) через функцию `report()` скрипта: она повторяет запрос до 10 минут (`--retry-connrefused`, таймауты), потому что потерянный отчёт оставляет модуль «немым» — стартовый скрипт старой утилитарной ОС (`S99scriptexec`, `set -e`) после ненулевого выхода скрипта просто останавливается; у нашей init печатает код выхода и тоже больше ничего не делает, IP остаётся, ничего не сообщается. В `/tmp/dd.log` попадают код выхода `curl`, stderr распаковщика и вывод `dd`; при сбое фазы `dd` контроллер добавляет в запись лога расшифровку (`ScriptExecuteController::WRITE_FAILURE_HINTS`).
3. `?alldone=1` — отметка о завершении и событие `CmProvisioningComplete`.

Докачка после перезагрузки (2.6.1) — только в проектах с галкой `split_image` («Split the image into 512 MB pieces»).

- **Копия.** Задача `App\Jobs\SplitImage` (очередь `images`) делает кусковую копию образа: один `.gz`, член 0 — первый мебибайт, каждый следующий — кусок по `cmprovision.split_piece_mb` (512) МиБ; смещения членов — `images.split_offsets`, состояние — `split_error`, `split_queued_at`. Копия засчитывается, только распаковавшись в тот же SHA256; оригинал не трогается. Задачу ставят сохранение проекта (форма, API), Retry на Images и старт модуля, если запись о копии есть, а файла нет (restore без `--with-uploads`); упавшая ждёт Retry. Сбой постановки старт не роняет. Laravel оставляет замок уникальности задачи, которую не удалось поставить, и молча пропускал бы следующие, поэтому `queueSplit()` снимает его сам, а `uniqueFor` равен таймауту задачи (2 ч). Таймаут задачи — ошибка, перезапуск воркера — новая попытка (до трёх).
- **Отметки.** Модуль пишет копию `write_pieces`: кусок за куском с `fsync`. Когда кусок k записан, надёжным объявляется кусок k−1: CRC его члена распаковщик уже проверил. Отметка в МиБ уходит отметкой прогресса `durable_mb` в `cms.durable_bytes` и `durable_at`: только у прогона с `cms.durable_image_id`, в фазе `write`, только вверх и не дальше образа.
- **Решение при старте** — `Cm::resumableFrom()`: прошлый прогон остановился на записи (фаза `write` или провал сразу после неё); надёжен хотя бы кусок, и он есть в копии; отметки не старше начала прогона (прогон, который их не знает, например 2.6.0 после отката, писал поверх); тот же проект с галкой и тот же образ, копия готова. Контроллер добавляет «тот же накопитель» (CID и размер, если модуль их сообщает). Тогда `resumeProvisioning()` продолжает тот же прогон (шаг «Resumed after a restart at …» с ключом `from` в `timeline`, `progress_base` для скорости) без доклада загрузчика, пре-скриптов и `blkdiscard`, с первым мебибайтом внутри скрипта (base64 члена 0). Проверку ОС он ставит по способу загрузки, как любой старт: по USB — `skipped`.
- **Модуль перед докачкой** сверяет первый мебибайт накопителя (`storage_unchanged`): там нули (его пишут последним) или он свой. Иначе накопитель перезаписали (прошили в другом месте, вставили другую карту): запись проваливается со строкой «the storage was written after the write stopped», сервер стирает отметки, и следующий старт пишет с начала. Кнопка Start over в карточке тоже их стирает.

Проверка ОС после первой загрузки (2.6.0) включается галкой проекта `os_check`.

- **Старт** ставит `cms.os_check`: `pending` — проверка будет; `skipped` — загрузка по USB, `bootmode=3`: перезагрузка вернула бы модуль в USB; null — проверки нет.
- **Скрипт модуля** несёт три вещи:
  - службу `cmprovision-firstboot` (`resources/views/scriptexecute/firstboot.blade.php`, POSIX sh; сервер рендерит её под модуль);
  - скрипты первой загрузки (`script_type = firstboot`);
  - шаг установки (`scriptexecute/oscheck-install.blade.php`). Это последний шаг пост-установки, «Installing the OS check»: он монтирует `$PART2` (ext4) и кладёт службу в `/etc/systemd/system/` и `/usr/local/lib/cmprovision-firstboot/`.
- **После `alldone`** модуль перезагружается (`reboot -f`). Сервер держит прогон в фазе `firstboot` («Checking the OS», `os_check = waiting`) и ставит задачу `FirstBootTimeout` (очередь `boards`) через `Cm::FIRSTBOOT_SECONDS` (15 минут); упавшая задача (`failed()`) ставит следующую через 30 с, пока модуль ждёт этого прогона. Повторный `alldone` (его шлёт `report()`, если ответ задержался) и поздние `?progress=` утилитарной ОС фазу не трогают.
- **Служба** живёт одну загрузку:
  - ждёт конца загрузки;
  - качает пакеты проекта (до 30 попыток на пакет: сеть ещё поднимается), сверяет SHA256, доделывает установку, прерванную перезагрузкой (`dpkg --configure -a`), и ставит их одним `apt-get` без источников (`Dir::Etc::SourceList=/dev/null`, пустой `SourceParts`) и без рекомендуемых пакетов: в сети стенда нет интернета, поэтому apt ничего не качает, а недостающая зависимость сразу даёт провал. `--no-download` нельзя: apt 3.0 с ним отказывает любому локальному `.deb` («Pathname to install is not absolute»), это нашла живая проверка 2.6.0;
  - выполняет скрипты, каждому по 2 минуты (`timeout -k`: скрипт, не услышавший TERM, получает KILL через 10 с);
  - шлёт один отчёт `POST ?firstboot=1&retcode=` с именем хоста, состоянием systemd, упавшими юнитами и журналом;
  - после отчёта (2.6.4, `resources/views/scriptexecute/firstboot-leds.blade.php`) удаляет себя: ссылку включения, юнит и каталог службы со скриптами и пакетами (в нём могут быть секреты). Остаётся только копия помощника `ledpattern` в закрытом каталоге `/run/cmprovision-leds.*`, и светодиоды показывают `ready` или `fail`. Дальше цикл раз в 5 секунд (во время Identify раз в 2) спрашивает `?identify=poll&identify_run=<начало прогона>`: ответ `identify` включает чередование ACT и PWR, любой другой ответ или сбой запроса возвращает `ready`/`fail`. Цикл живёт до следующей перезагрузки.
  Журнал `/var/log/cmprovision-firstboot.log` (`chmod 600`) и каталог службы (`chmod 700`) — только для root: `sh -v` пишет в журнал текст скриптов вместе с паролями, если они там есть.
- **Отчёт** (`registerFirstBoot()`) завершает прогон. Удачный — фаза `done`, событие `CmProvisioningComplete` и этикетка момента `firstboot` с `$hostname` (её печатает задача `PrintLabel`). Неудачный — фаза `failed` с причиной «OS check failed: …».
- **Модуль снова стартует, пока прогон в фазе `firstboot`** — значит, новая система не запустилась: провал «The new system did not start…» без повторной записи. Исключения закрывают ждущий прогон (`closeTheCheck()`, уведомление о провале) и начинают новый: загрузка по USB (`bootmode=3`, оператор перешивает модуль) — «Interrupted: the module was booted over USB.»; старт позже `FIRSTBOOT_SECONDS` (таймаут потерялся) — `Cm::OS_NO_REPORT`.
- **Отчёт после таймаута** тоже засчитывается (`Cm::awaitsOsReport()`).
- **Строка On the bench** в карточке модуля, приславшего отчёт (`os_checked_at`), называет новую систему и время отчёта. Саму новую систему сервер не спрашивает, но её цикл светодиодов (2.6.4) опрашивает `?identify=poll` с номером своего прогона: Identify и Stop у такого модуля работают, пока он опрашивает (`cms.polled_at`), то есть до следующей перезагрузки; начатый заново прогон прежний цикл не оживляет (`identifyPoll()` на чужой `identify_run` отвечает пусто). Тесты — `ModuleIdentifyTest`.
- **Перезапуск по PoE** не предлагается модулю, провалившему проверку собственным отчётом (`Cm::failedInItsSystem()`), и «Restart failed» дашборда его пропускает: питание загрузило бы ту же систему. Модулю в фазе `firstboot` или без отчёта окно подтверждения говорит, что он снова загрузит новую систему.
- **Галка проекта**: снятая, она сбрасывает момент этикетки `firstboot` на `postinstall`, пакеты и скрипты первой загрузки (`Projects::updatedOsCheck()`); API отвечает 422 на скрипты первой загрузки или момент `firstboot` без проверки.

Параллельно скрипт сообщает живой статус: `progress_mark` перед каждым скриптом и записью, а `progress_start`/`progress_stop` на время записи образа и сверки раз в 5 секунд шлют число секторов из `/sys/block/<dev>/stat` (поле 7 — записано, 3 — прочитано). Это `GET ?progress=<фаза>&detail=&sectors=` без повторов и с таймаутом 4 секунды: статус необязателен и не должен тормозить прошивку. Сервер хранит фазу (`preinstall`, `write`, `verify`, `postinstall`, `done`, `failed`), её начало и байты в колонках `cms` (`Cm::setPhase()`), в лог такие запросы не пишутся. Дашборд показывает модули компонентом `ProvisioningStatus`: процент, скорость, остаток и «нет связи», если модуль молчит дольше `Cm::STALE_AFTER_*`. Порядок строк (2.14.0) — `Cm::newestFirst()` и на Dashboard, и в списке CMs: сначала идущие (`isRunning()`, позже начавший выше), потом по времени, когда модуль залит (`Cm::flashedAt()`: конец прогона, у упавшего — момент сбоя), новые выше, не прошивавшиеся — в конце; порядок по портам убран. Клик по заголовку столбца (2.15.0, `<x-sort-th column=… :sort :dir>`, трейт `Concerns\SortsColumns`, класс `App\Support\ColumnSort`) сортирует по нему: первый клик — как задано у столбца (`first`: текст по возрастанию, время и прогресс по убыванию), второй разворачивает, третий возвращает порядок по времени; строки без значения всегда в конце, равные идут в порядке по времени; столбцы описывает `columns()` компонента (Dashboard: board, module, step, progress, time; CMs: mac, hostname, serial, model, project, board, result, finished), выбор лежит в адресе (`#[Url]` `sort` и `dir`; незнакомое значение — порядок по времени), выгрузка CSV идёт в том же порядке. Плитка USB prep (`UsbPrepPanel`) — вложенный компонент в конце ряда итоговых плиток `ProvisioningStatus` (корень `display: contents`; при ширине от 1440 px пятая колонка, уже — своя строка под плитками); всё происходит в самой плитке: текст под заголовком — следующий шаг для платы, подготовленной последней (`UsbPrepPanel::MINUTES` = 120 мин; остальные — «+N more»), ничего не раскрывается ниже; плата, получившая только загрузчик, в таблице — «Ready (USB prep)».

Каждый переход фазы или скрипта `Cm::setPhase()` дописывает в `cms.timeline` (JSON `{phase, detail, at}`, старт прогона его обнуляет). Из него карточка модуля `/cms/{mac}` (компонент `CmCard`, на неё ссылаются дашборд и список CMs) строит шаги с длительностью и скоростью (`App\Support\RunTimeline`), а `App\Support\FailureAdvice` по причине сбоя, шагу, итогу прошивки и логам подсказывает оператору, где модуль остановился и что делать.

EEPROM «до и после»: сервер хранит доложенный загрузчик в `cms.eeprom_before`/`eeprom_config_before`, снимок прошиваемых настроек проекта на старте в `eeprom_config_after` и итог в `eeprom_result`, а `cms.firmware` остаётся «что в EEPROM после». Итог (`written`, `identical`, `failed`) берётся из строки `EEPROM_RESULT=` в логе пре-скриптов. Скрипт прошивки печатает её из переменной: под `sh -v` в лог копируются и строки самого скрипта, и буквальная строка совпала бы с ответом. Сбой пре-скриптов без такой строки означает, что не прошла сама прошивка.

Светодиоды модуля задаёт `resources/views/scriptexecute/leds.blade.php`; эти функции входят и в скрипт модуля, и в ответ с отказом. Режимы выбраны с оператором на WLAN Pi M4+, где оба светодиода красные:
- «идёт» — ACT мигает 10 раз в секунду (таймер ядра), PWR горит;
- «готово» — ACT и PWR по очереди плавно загораются и гаснут;
- «ошибка» — ACT тусклый, PWR даёт двойную вспышку раз в две секунды;
- «опознать» — оба быстро чередуются 30 секунд.
- «ОС проверена» (2.6.0, в записанной системе после проверки ОС) — ACT и PWR плавно загораются и гаснут одновременно (`ledpattern ready`).

Плавность и тусклость даёт помощник `ledpattern` (программный ШИМ), которого модуль скачивает с сервера. Без него те же режимы показываются триггерами ядра, без плавности. ACT сидит на GPIO 42, а этот вывод оверлей `spi-gpio40-45` отдаёт шине SPI для flashrom. Пока драйвер `leds-gpio` не переподключён (`led_take_act`), ACT не горит, поэтому переподключение идёт после пре-скриптов. С ядром 6.18 одного переподключения мало: `led_take_act` сначала отвязывает от драйвера `spi-bcm2835` контроллер `fe204000.spi`, который после flashrom держит GPIO 42, а потом отвязывает и заново привязывает `leds`, в том числе когда первый probe не удался (пути драйверов переопределяют `LED_SPI_DRIVER` и `LEDS_DRIVER`). Любой конец прогона, успешный или нет, уходит в `finish`, и скрипт больше не завершается. Модуль показывает итог и раз в 5 секунд шлёт `?identify=poll`. Сервер отвечает `identify`, пока оператор просил опознаться: кнопка Identify в карточке и на дашборде (`Cm::identify()`) включает мигание на `Cm::IDENTIFY_SECONDS`, а Stop (`Cm::stopIdentify()`) выключает его раньше. Пока модуль мигает, он спрашивает сервер каждые 2 секунды и мигает, только пока слышит `identify`. Опрос не пишется в лог, а `cms.polled_at` обновляется не чаще раза в минуту. По нему кнопка видна только у модуля, который ещё на стенде.

Режимы с графиками, этапы прогона и устройство помощника для оператора и разработчика — [docs/leds.md](docs/leds.md). Графики `docs/leds/*.svg` собирает `docs/leds/build_diagrams.py` (только стандартная библиотека Python) из `ledpattern.c`, `leds.blade.php` и `Cm.php`. Если код изменился так, что скрипт его не понимает, он останавливается. `LedDocsTest` пересобирает графики (нужен python3) и сверяет их с файлами в репозитории, так что правка режима требует пересборки графиков.

События провижининга пишутся в таблицу `cmlogs` (`ScriptExecuteController::logInfo()`); дашборд показывает последние 100 записей.

## Связи между файлами

- Параметры запроса модуля задаются плейсхолдерами в `scriptexecute/cmdline.txt` и `utility-os/board/cmprovision/cmdline.txt` (их подставляет init утилитарной ОС; у нашей в конце ещё `&uos=<версия>`) и читаются в `ScriptExecuteController::startProvisoning()`. Меняйте все стороны вместе.
- Подсеть 172.20.0.0/16 с сервером 172.20.0.1 зашита в `etc/dnsmasq.conf`, `scriptexecute/cmdline.txt`, `utility-os/board/cmprovision/cmdline.txt`, `Host::firstAvailableIP()`, `NetworkStatus::SERVER_ADDRESS`, `NetworkStatus::STAND_NETWORK` (проверка `StandNetworkOnly`) и README.
- `scriptexecute.blade.php` рендерит shell, а `{{ }}` экранирует HTML (`&` → `&amp;`): сырой shell-код вставляйте через `{!! !!}`. Пользовательские скрипты записываются в файлы через quoted heredoc с маркером `CMPROVISIONINGEOF`. Директива Blade в конце строки с shell-кодом (`... @endif`) компилируется в `?>`, после которого PHP съедает перевод строки, и следующая строка склеивается с этой; хвост строки выводите через `{!! !!}` (после echo Blade перевод строки сохраняет). Так однажды `RETCODE=$?` приклеился к запуску скрипта.
- Строки `dhcp-host=` в `etc/dnsmasq.conf` генерирует `Settings::regenDnsmasqConfAndRestart()` из таблицы `hosts`, остальные строки сохраняются. Файл объявлен conffile в `debian/conffiles`.
- Через `sudo` веб-приложению разрешены только `systemctl restart cmprovision-dnsmasq` и пять команд помощника Wi-Fi (`debian/010_cmprovision`, по строке на команду, без аргументов); журналы читаются благодаря группе `systemd-journal`, которую выдаёт `postinst`. Новый привилегированный вызов требует правки sudoers-файла (это conffile: правленный вручную остановит обновление вопросом dpkg).
- Побочные эффекты активации проекта живут в `App\Services\ProjectActivator`, а не в модели: запись `public/uploads/pieeprom.bin` с вшитым `bootconf.txt` проекта и его SHA256 в настройку `active_eeprom_sha256`. Через него идут `Projects::setActive()` и `PATCH /api/projects/{id}` (`refreshIfActive()` после правки активного проекта). Форма проекта принимает прошивку только из хранилища, API — пока любую строку.
- Встроенный Wi-Fi — холодный запас (2.5.2): `tools/uplink-spare` (POSIX sh, root) ставится в `/usr/lib/cmprovision/uplink-spare`, `tools/90-cmprovision-uplink` — в `/usr/lib/NetworkManager/dispatcher.d/` (каталог дистрибутива, не conffile; NetworkManager запускает только скрипты root без записи для других), страховка — `cmprovision-uplink.timer` (через 2 минуты после загрузки, потом раз в 5 минут). Встроенный Wi-Fi — беспроводное устройство на шине `sdio`; его отключают (`nmcli device disconnect` — устройство, не профиль), когда маршрут IPv4 по умолчанию через другое устройство держится `STABLE_SECONDS` (60), и подключают, когда такого маршрута нет `LOST_SECONDS` (30); решение — по текущему состоянию, а не по событию, отложенные перепроверки — временные таймеры `systemd-run` с уникальными именами и `AccuracySec=1s` (по умолчанию таймер systemd точен до минуты: 30 с превратились бы в 90); переключение ждёт NetworkManager не дольше 20 с (`nmcli -w 20`), потому что из диспетчера помощник держит его очередь; диспетчер зовёт его и на `device-remove` (карта с упавшим драйвером может пропасть без `down`), а отсчёты из файла состояния, которые не число или впереди часов, считаются «сейчас». Состояние — `/run/cmprovision/uplink-spare` (`state`: standby, active, waiting, off; `since`, `spare`, `uplink`, `up_since`, `lost_since`), его читает `NetworkStatus` (поле `spare`); «30 s» в строке `UplinkSummary` — тот же `LOST_SECONDS`. Выключатель — `SPARE=no` в `/etc/default/cmprovision-uplink` (пишет `postinst`, если файла нет; не conffile; в бэкапе). `prerm` при удалении и откате ниже 2.5.2 зовёт `uplink-spare release` — иначе встроенный остался бы отключённым до перезагрузки. `release` и переход на `SPARE=no` подключают отключённый встроенный сами (`nmcli device connect`; при `SPARE=no` — один раз, дальше решает NetworkManager): устройство, отключённое `nmcli device disconnect`, NetworkManager не подключает, даже если вернуть ему `autoconnect yes` (проверено на wlanpi-da2, NetworkManager 1.52).
- Сети Wi-Fi провижинера из Settings (2.5.3): раздел — компонент `WifiSettings`, чтение — `App\Services\WifiNetworks` (`nmcli -t` от `www-data` без `-s`; профили одного SSID — одна сеть; не keyfile в `/etc/NetworkManager/system-connections`, Enterprise и открытые — серые строки), запись — root-помощник `tools/wifi-networks` (POSIX sh, ставится в `/usr/lib/cmprovision/`) через `sudo -n` с вводом `ключ=значение` на stdin: `save`, `delete`, `order`, `check`, `scan`. Сеть — один профиль без привязки к карте (`multi-connect=multiple`, метрика −1, `autoconnect-priority` по порядку 100, 99…); метрики дают устройства — `/usr/lib/NetworkManager/conf.d/90-cmprovision-uplink.conf` (`brcmfmac` — 600, остальной Wi-Fi — 100). Пароль сети не попадает ни в аргументы процессов (строку `psk=` помощник вписывает в keyfile сам, через `ENVIRON` awk, и сверяет, прочитав `nmcli -s`), ни в журнал, ни в снимок Livewire: поле живёт в Alpine и уходит параметром `save(secret)`. Каждое изменение — после `<x-confirms-password>` (Jetstream; его окно выводится `@once`, поэтому на странице Settings он только в этом компоненте). Check now поднимает на простаивающем встроенном (`state=standby` холодного запаса, под его замком) не сам профиль, а его копию в памяти NetworkManager (`/run/NetworkManager/system-connections`, имя `cmprovision-check`, привязана к встроенному, без автоподключения) и удаляет её: блок автоподключения, который NetworkManager ставит профилю после отказа «нет секретов» (неверный пароль), достаётся копии, а подключение карты не трогается даже у профиля без `multi-connect`. Новая сеть добавляется без автоподключения и получает его, когда пароль записан. Поиск сетей ждёт тот же замок, что и изменения. `pmf` по умолчанию (0) раздел показывает смешанной защитой (это поведение NetworkManager по умолчанию), WPA2-Personal — `pmf=1`. Тесты помощника задают места переменными `WIFI_NETWORKS_*` (`RUNTIME` — куда класть копию, `WAIT` — сколько ждать замок). Первое сохранение сети из нескольких профилей оставляет активный профиль (правит на месте, подключение не рвётся) и удаляет остальные. Журнал — `logger -t cmprovision-wifi`.
- Печать этикеток (FTP или команда; плейсхолдеры `$mac`, `$serial`, `$hostname` (после проверки ОС), `$provisionboard`, `$switch`, `$port`, `$file`) реализована дважды: `App\Services\LabelPrinter::print()` (его зовут `ScriptExecuteController::printLabel()` и задача `PrintLabel`) и `Labels::printTestLabel()`. Когда печатать, задаёт `label_moment` проекта: `never`, `preinstall`, `postinstall` или `firstboot` (после проверки ОС).

С 2.7.0 (руководство `docs/utility-os.md`).

- Наша ОС — BR2_EXTERNAL-дерево `utility-os/` (имя `CMPROVISION`) на buildroot LTS 2025.02.x; версии и SHA256 всех

  `board/cmprovision/linux.fragment`; `CONFIG_MODULES` включён (без него Kconfig встроил бы каждое `=m`), модули

- Собранный каталог `scriptexecute64/` и `tests/fixtures/utility-os/messages.txt` коммитятся (пакет собирается без сети),
  только когда новая версия ОС принята. Версия ОС — `ГГГГ.ММ` (`2026.10.1` — вторая за месяц).
- Init `board/cmprovision/rootfs-overlay/etc/init.d/S99scriptexec` (POSIX sh, без `set -e`) подставляет в шаблон
  `script=` из `cmdline.txt` те же значения в тех же форматах, что старый, плюс `uos=`; перемычки читает `pinctrl`
  (номера GPIO в sysfs с ядра 6.6 сдвинуты). Полностью скачанный ответ 200 исполняет, 5xx и обрыв повторяет через 10 с, другой код печатает и
  останавливается; вернувшийся скрипт второй раз не запускает. Пути `/proc`, `/sys`, `/tmp` переопределяются
  переменными `UOS_PROC`, `UOS_SYS`, `UOS_TMP` (так его гоняет тест).
- Состав — надмножество `utility-os/legacy-commands.txt` (команды старой ОС без камеры и мультимедиа rpi-userland);
  консоль как у старой: ход на tty1, getty на tty2; служб входа по сети нет (`CONFIG_TELNETD` выключен, `test.sh`
  сверяет список `/etc/init.d/S*`).
- Ссылка `etc/boot` (www-data) → `../scriptexecute` или `../scriptexecute64`: её делает и чинит `tools/boot-link`

## Данные и хранилище

### Перепрошивка установленной ОС (2.6.3)

- Сценарий и ограничения — `docs/operations.md#re-provision-an-installed-sensor`. В карточке вложенный `ReprovisionDialog`: Check access → ключ или учётка → при необходимости смена пароля → явное подтверждение wipe. Произвольный IP из браузера не принимается: `SensorAddress` читает DHCP-аренду по MAC, исключает сервер и всё вне сети стенда.
- `projects.reprovision` выключен по умолчанию. `ScriptExecuteController::postinstallScripts()` добавляет установщик агента после сверки и пользовательских postinstall, до OS check; общий метод используется и при resume. Агент поддерживает только eMMC/SD, MBR и корень ext4 на втором разделе. В агенте путь диска фиксирован; перед wipe он проверяет serial, CID, размер и соответствие диску работающего корня. Ошибка установки не роняет прошивку; ошибка dd/sync не даёт положительного ответа и не запускает reboot.
- `cms.storage` остаётся ёмкостью. `cms.provisioning_storage` — снимок пути при выдаче скрипта. Старые durable-марки миграция очищает один раз: у них нет снимка пути. `ReprovisionOperation` хранит состояние, проверенную идентичность и отпечаток проекта без паролей. Намерение записывается до отправки команды; неизвестный результат не повторяется автоматически. Возврат к network boot проверяет проект и MAC, сбрасывает resume и связывает операцию с новым прогоном. При изменённом/просроченном проекте оператор подтверждает текущий проект и перезапускает модуль.
- `SensorShell` подменяется в тестах; `OpenSshSensorShell` использует argv-массивы Symfony Process, askpass и stdin для sudo, отдельный known_hosts на операцию. Пара ключей — `storage/app/ssh/id_ed25519`, private 0600; helper установлен из `tools/sensor-askpass`. Settings показывает только public key. Бэкап и data-only restore сохраняют ключ вместе с APP_KEY.
- `SavedAccounts` хранит редактируемые профили сенсоров в `settings.reprovision_accounts` целиком зашифрованными через Crypt/APP_KEY. В браузер уходят только метаданные. По умолчанию включён wlanpi/wlanpi, выключен legacy pi/raspberry; до 10 профилей, до 3 включённых. После отказа ключа первая проверка пробует профили по порядку, с общим cooldown 60 с на serial; повтор той же операции и ручная учётка не повторяют автоматические попытки. Успешная учётка попадает в обычный зашифрованный cache на 120 с. Смена пароля отдельного сенсора не меняет общий профиль. `confirms-password` ограничивает окно и события ID своего Livewire-компонента, иначе независимые формы Settings перехватывали бы подтверждение друг друга.
- Пароли — аргументы действий из Alpine, не публичные свойства Livewire. Между шагами — Crypt + cache на 120 секунд, доступ к операции привязан к user/session. При отмене/отправке секреты удаляются; вывод SSH и PAM редактируется. `ModuleOperationLock` общий для SSH, PoE и старта provisioning. Никакого root-доступа на самом сервере для SSH-клиента не нужно.
- `python3 tests/ssh/run.py` запускают от root только в отдельной Linux-тестовой среде: временный sshd слушает loopback, одноразовый пользователь/sudoers удаляются в finally. PHPUnit без него пропускает интеграционные SSH-тесты. Агент тестируется настоящим sh с временными device nodes и fake dd/reboot; записи идут в обычный одноразовый файл.

- `settings` — таблица ключ-значение (PK `key`): `active_project` (активен не более одного проекта), `active_eeprom_sha256`, `firmware_last_update`. Ключи `ethernetswitch_*` — настройки коммутатора 2.3: с 2.4 они нужны только для отката пакета (миграция скопировала их в `ethernet_switches` и оставила).
- Коммутаторы стенда — таблица `ethernet_switches` (модель `EthernetSwitch`): адрес (уникален), SNMP чтения и записи (`write_*` — для перезапуска по PoE; секреты скрыты от сериализации), метод таблицы MAC и сработавший метод, то, что коммутатор сказал о себе на последнем удачном опросе (`sys_name`, `base_mac` — уникален, `own_macs`), и найденные линки к соседям (`links`: ifIndex → id соседа); всё это при каждом опросе сохраняет `Stand`. `config()` — массив для SNMP-классов (`SwitchSnapshot::forConfig()`, `PoeControl::forConfig()`, привязка `SnmpClient`), `hostname()` — sysName до первой точки (IP как есть), без него адрес. Удаление коммутатора обнуляет `switch_id` у модулей и строк `poe_outages`; Settings не удаляет коммутатор, у которого порт остался выключенным после перезапуска.
- `Firmware` — не Eloquent-модель. Прошивки — файлы `<firmware_dir>/<канал>/pieeprom-*.bin` (`config/cmprovision.php`, по умолчанию `storage/app/firmware`); каналы `default` и `latest` наполняет `FirmwareUpdater` (страница Firmware и `artisan firmware:update`) из GitHub contents API `firmware-2711/*` и из пакета `rpi-eeprom`, скачивая только недостающие файлы и никогда не удаляя; старые каналы `stable`/`beta`/`critical` показываются, пока в них есть файлы. Время последней удачной проверки — настройка `firmware_last_update`. Заметки к выпускам (2.7.6) лежат рядом с файлами, `<firmware_dir>/release-notes.md`: `FirmwareUpdater::updateNotes()` берёт копию из пакета `rpi-eeprom` (`release-notes.md` в `system_firmware_dir`, работает без сети) и `FirmwareUpdater::NOTES_URL` (raw GitHub, не API: лимита запросов нет) и оставляет ту, где новее последняя запись; файл заменяется только заметками, которые доходят не меньше прежних, а недоступные заметки ошибкой обновления не считаются (`result['notes']`: `updated`, `unchanged`, `unavailable`). `App\Services\FirmwareNotes` разбирает заголовки `## ГГГГ-ММ-ДД<разделитель>заголовок (канал)` во всех формах, что встречаются за семь лет (`: `, ` - `, `(recovery.bin)`, `- STABLE`); безымянный `## …` заканчивает запись. Дата записи — дата образа (`pieeprom-<дата>.bin`), запись «Promote <дата> …» — куда образ продвинули (показывается строкой «Promoted»), а не изменение. Страница Firmware показывает изменения у каждого файла и метку «new» у образов, попавших в хранилище не раньше `Firmware::NEW_DAYS` (14) дней назад по времени файла; форма проекта — «Changes since <дата текущего образа>» при выборе другого (если выбран старее текущего — что у текущего есть сверх выбранного). Текст заметок всегда экранируется.
- Порт модуля ищет задача очереди `App\Jobs\ResolveBoards` (очередь `boards`): старт с коммутаторами пишет `cms.board_pending_since` и отдаёт скрипт сразу, а задачу ставит, когда старт решён (`ScriptExecuteController::lookUpBoardLater()`, и при отказе; ошибка постановки старт не роняет). Один опрос стенда (`Stand::current()`, снимок не старше последнего старта, у повтора — новее прошлого опроса) даёт платы всех ждущих модулей по правилам `PortLookup::resolve()`; чужой опрос того же коммутатора задача ждёт до 10 с (`PortLookup::WAIT`). Модуля нет на карте — новый прогон через `RETRY_SECONDS` (3 с), через `GIVE_UP_SECONDS` (60 с) — предупреждение без платы. Запись сверяет `board_pending_since` (`settle()`): модуль, стартовавший заново, получает плату нового старта; этикетку preinstall ставит отдельной задачей `PrintLabel` тот, кто записал плату (медленный принтер не держит платы волны), отказанному модулю — нет; строки журнала этого старта получают плату задним числом. Ошибка на одном модуле не мешает остальным; упавший или снятый по таймауту прогон (`$timeout` 80 с у всех трёх задач — меньше `retry_after` очереди, 90 с) ставит следующий (`failed()`); поиск, который не выполнился за `STALE_MINUTES` (10 мин), снимается без платы и этикетки с предупреждением. Задача уникальна до взятия воркером (`ShouldBeUniqueUntilProcessing`) и следующий прогон ставит сама: старт во время прогона получает свой; прогоны двух воркеров безопасно идут одновременно. Пока плата ищется, дашборд показывает «…», карточка — «looking up the switch port…». `PortLookup::find()` — то же для одного MAC вместе с опросом. Плата — «hostname порт» (порт — описание `ifAlias`, иначе `ifName`), в `cms` идут ещё `switch_id`, `switch_name` и `switch_port`; предупреждение в журнале модуля называет коммутаторы, которые не ответили. MAC, который два порта видят поровну, — «[multiple ports]». Без коммутаторов плата — инвертированные биты джамперов (GPIO 5/13/21, `scriptexecute/config.txt`). Таблицу MAC читает `App\Services\Switch\MacTable`, методы по очереди: Q-BRIDGE-MIB (VLAN-коммутаторы: Huawei, MikroTik, Cisco Business), BRIDGE-MIB (Huawei VRP/YunShan; порт в ifIndex через `dot1dBasePortIfIndex` или HUAWEI-L2IF-MIB), HUAWEI-L2MAM-MIB и Cisco IOS — экземпляр BRIDGE-MIB на каждый VLAN (`community@vlan`, у v3 контекст `vlan-N`, список VLAN из CISCO-VTP-MIB). `App\Services\SwitchPortFinder` остался для кнопки Test на странице Settings (компонент `SwitchSettings`, список коммутаторов и форма одного) и artisan-команды: `scan()` показывает всю таблицу MAC.
- SNMP идёт через интерфейс `Snmp\SnmpClient` из контейнера (`PhpSnmpClient`, в тестах `Tests\Support\FakeSnmp`). php-snmp хранит указатель на имя контекста из `setSecurity()`, а не копию, поэтому строка контекста живёт в свойстве клиента: освобождённая, она превращалась в мусор, и коммутатор молчал. SHA-2 для v3 php-snmp умеет с PHP 8.1, поэтому `PhpSnmpClient::authProtocols()` в 2.0 предлагает все шесть протоколов. Проверка на настоящем агенте — `SnmpAgentTest` со snmpsim, см. `docker/README.md`.
- Страница Ports (`/ports`, компонент `Ports`) показывает стенд по портам коммутаторов: у каждого свой блок с корпусом, сводка с чипами одна на стенд. `App\Services\Switch\SwitchSnapshot` одним опросом читает физические порты (IF-MIB: Ethernet по `ifType` и `ifConnectorPresent`, если агент его сообщает), линк, скорость, MAC на портах (`MacTable` — та же таблица, что у `SwitchPortFinder`) и PoE (`Poe`: HUAWEI-POE-MIB по ifIndex, у Cisco IOS — CISCO-POWER-ETHERNET-EXT-MIB с ENTITY-MIB, у остальных — RFC 3621 по номеру порта). Коммутатор, не назвавший ни одного интерфейса (например, при неверной учётке v3), — ошибка, а не пустая панель. `SnapshotCache` (свой у каждого коммутатора) хранит снимок 5 секунд (у медленного коммутатора — вдвое дольше опроса), после неудачного опроса спрашивает коммутатор снова не раньше чем через 30 секунд (`ERROR_SECONDS`: иначе каждый опрос страницы и каждый старт модуля ждали бы таймаут), опрашивает одним запросом за раз, при молчании показывает последний снимок с ошибкой и пишет в журнал Laravel строку на смену «отвечает/не отвечает». `App\Support\StandMap` собирает одну карту из снимков всех коммутаторов (`Stand::current()`): раскладывает порты каждого как на корпусе (PoE-порты блоками по 12, остальные — блок аплинков) и считает сводку стенда. Ключ плитки — `s<id коммутатора>p<ifIndex>`; у плитки есть `switch`, `label` («hostname порт»: так порт называют журнал, сообщения и плашка PoE), `board` и `link`. Линк — порт, где виден собственный MAC другого коммутатора стенда (базовый MAC, `ifPhysAddress` вместе с SVI и MAC его адреса в ARP провижинера — `SwitchSnapshot` кладёт их в `own_macs`; на 2960CX MAC управления виден только так), или порт, найденный линком раньше, пока сосед молчит (`links` в строке коммутатора). Линк — аплинк: модулей и перезапуска на нём нет. MAC модуля принадлежит одному порту стенда (`owners`): с меньшим числом адресов, при равенстве — где остальные адреса тоже модули, иначе никакому; на прочих портах он не модуль и не чужое устройство. Разъём порта (`SwitchSnapshot::media()`) берётся из ENTITY-MIB, если там есть контейнеры (класс 5): гнездо SFP — контейнер с именем порта (у Cisco «GigabitEthernet0/11 Container»), combo — гнездо, рядом с которым у порта есть и своя сущность (RJ45), модуль в гнезде — сущность внутри контейнера. Без контейнеров разъём угадывается: на PoE-коммутаторе гнёзда — порты без PoE, на остальных — по имени (`StandMap::CAGE_NAMES`) или скорости от 10G. Порт без линка — свободный, даже если MAC ещё в таблице коммутатора; аплинк — порт с MAC провижинера (`NetworkStatus::serverMac()`) или больше 3 MAC, не принадлежащих модулям. Если на порту несколько модулей, те, что не идут и не опрашивают сервер (`isActive()`, `canIdentify()`), уступают живому: так коммутатор, помнящий MAC после падения линка, не показывает снятый модуль рядом с новым. Любой сбой опроса, не только `SnmpError` (например, предупреждение php-snmp о неразрешимом имени хоста), — ошибка коммутатора, а не падение страницы. Линк без единого MAC дольше 3 минут (по `ifLastChange` и `sysUpTime`) — «тихое» устройство (`LNK`), а не загружающийся модуль. Порт, где все незнакомые MAC из блоков Raspberry Pi (`StandMap::RASPBERRY_PI_PREFIXES`, реестр IEEE), в первые те же 3 минуты линка — загружающийся модуль, который ещё не обратился к серверу; если коммутатор не сообщил возраст линка, это чужое устройство. У порта в снимке остаются первые 64 MAC и их число (`mac_count`). Метод таблицы MAC, который уже находил модули (`ethernetswitch_method_detected`), достаточен, если в нём есть строки, и таблица обходится один раз; `ifDescr` и `ifSpeed` спрашиваются, только если их нет в ifXTable. Фильтр по чипам сводки живёт в Alpine. Строка внутри блока коммутатора (hostname, S/N, MAC, адрес, модель с ревизией, давность опроса, PoE в ваттах) — то, что коммутатор говорит о себе (`SwitchSnapshot::identity()`): модель, ревизия и серийный номер шасси из ENTITY-MIB (`entPhysicalClass` = 3; у Huawei серийный номер может лежать на главной плате, класс 9), базовый MAC из BRIDGE-MIB `dot1dBaseBridgeAddress` (php-snmp отдаёт шесть октетов как есть) и `sysName`. Без модели шасси коммутатор называет первая строка sysDescr. Снимок, сохранённый в кэше прошлой версией, приходит без `identity`. Замолчавший коммутатор держит в блоке последний снимок с «As of …, not answering since …», не ответивший ни разу — причину, а вердикт сводки называет молчащих; на два коммутатора с одним именем страница предупреждает. На настоящем Cisco WS-C2960CX-8PC-L (IOS 15.2(3)E2 и 15.2(7)E14) проверены поиск порта, PoE с ваттами, заголовок и перезапуск по PoE; при одной VLAN порт находит обычный BRIDGE-MIB (метод `bridge`), опрос по каждой VLAN не нужен. Гнёзда SFP и медные аплинки по ENTITY-MIB проверены на том же 2960CX. Huawei проверен только на snmpsim (`tests/fixtures/snmp`: `s5731`, `c9200`, `cbs350`, `crs`), как и combo-порты и эвристика «медь или гнездо» для коммутатора без контейнеров: SFP на портах с именем Gi она не отличает. Остальное — пункт 1 ROADMAP.
- Соседи по LLDP и CDP (2.13.0, `docs/unrecognized-devices.md#what-the-device-says-about-itself-lldp-and-cdp`). `App\Services\Switch\Neighbors` читает таблицы коммутатора при каждом снимке (`SwitchSnapshot::take()`: порт получает `neighbors`, снимок — `discovery` `{lldp, cdp}`): LLDP-MIB `lldpRemTable` (`.1.0.8802.1.1.2.1.4.1.1`, индекс timeMark.localPortNum.remIndex), адреса управления из индекса `lldpRemManAddrTable`, CISCO-CDP-MIB `cdpCacheTable`. `lldpRemLocalPortNum` — не всегда ifIndex (у 2960-CX счёт 1, 2, … при ifIndex 10101, …): порт ищется по `lldpLocPortId`/`lldpLocPortDesc` против ifName, потом против ifDescr, и только потом по номеру. Устройство, говорящее и по LLDP, и по CDP (WLAN Pi OS), — один сосед (`protocol` = `lldp/cdp`, одно имя на порту); не больше четырёх на порт. Все тексты — чужие: `Neighbors::text()` (UTF-8, без управляющих и невидимых символов, обрезка) до того, как они попадут в страницу или табло. Чтение живёт 20 с в кэше (`switch-neighbors:<адрес>`), у замолчавшего коммутатора последний ответ показывается до 10 минут; сбой чтения соседей снимок не роняет. `StandMap`: плитка получает `neighbors`; порт провижинера (`server`, `hasServer()`) находится и по MAC в таблице, и по LLDP-соседу с `serverMac`; сосед с MAC или именем другого коммутатора стенда (`neighbourIs()`) делает порт линком. `App\Services\OuiVendors` называет производителя по MAC для порта с неузнанным устройством (реестры IEEE пакета `ieee-data`: `oui.txt`, `mam.txt`, `oui36.txt`, самый длинный блок побеждает; блоки Raspberry Pi встроены; локально администрируемый MAC производителя не имеет; пакет в `Recommends`, путь — `cmprovision.ieee_data_dir`). Плитка порта провижинера (`server`) рисует знак cmprovision из верхней панели (`<x-application-mark :gradient="'cmp-ports-'.$t['key']">`, у каждой копии свой id градиента) вместо «UP», в деталях — «The provisioner (this server) is on this port»; на HDMI тот же порт подписан `cm`. Страница Ports: блок «Says about itself» в деталях порта и итог по коммутатору в его строке. Тесты — `NeighborsTest` (с ответом настоящего 2960-CX), `OuiVendorsTest`, `StandMapTest`, `PortsPageTest`.
- Перезапуск по PoE (`docs/operations.md#switches-and-poe-restart`). Запись идёт через `SnmpClient::set()` отдельной учёткой: Write community для v2c или свой пользователь v3 (`PoeControl::forConfig()`). Учётка своя у каждого коммутатора; у портов коммутатора без неё кнопок нет. Объект для записи даёт `Poe::admin()` с тем же сопоставлением портов, что у чтения: `hwPoePortEnable.<ifIndex>` у Huawei, `pethPsePortAdminEnable.<группа>.<порт>` у остальных (Cisco IOS эту запись принимает, проверено на 2960-CX); 1 — включено, 2 — выключено. Оба значения сохраняются при перезагрузке коммутатора. Если порт сопоставлен только по номеру (не Huawei и не Cisco IOS), запись разрешена лишь тогда, когда имя порта кончается его номером PoE: управляющий порт перед остальными сдвинул бы номера.
  - Какой порт можно перезапускать, решает `StandMap::restartBlocker()` по свежему снимку (`App\Services\Switch\Stand`, тот же `SnapshotCache`). На порту должен быть один наш модуль и ничего больше (поле плитки `others` равно 0) или загружающаяся Raspberry Pi, а PoE на порту не выключено (его включает Power on, а не перезапуск). Модуль, который пишет загрузчик EEPROM и отвечает серверу, не перезапускается: обрыв питания посреди записи оставит загрузчик, который не грузится по сети. Перед выключением каждого порта `PoeRestart::switchAllOff()` перечитывает это из базы — по MAC, которые видел снимок, и по `switch_id`/`switch_port` из поиска платы: снимку бывает полминуты, а загружающаяся Raspberry Pi за это время успевает начать запись. Порт, который не удалось так проверить, остаётся под питанием. Модуль ищется среди модулей, которые карта показывает на порту (`Stand::tileOf()`), а не по `provisioning_board` и не по любому MAC в таблице. Так снятый модуль, чей MAC коммутатор ещё помнит рядом с новым, порта не получит.
  - `PoeRestart` работает под замками затронутых коммутаторов (`poe-restart:<id>`, берутся по возрастанию id): перезапуск на одном коммутаторе не мешает другому. Замок живёт 10 минут: столько идёт перезапуск 48 портов у замолчавшего коммутатора. Замок своего коммутатора берёт Check write access, чтобы записанное обратно значение не выключило порт после перезапуска. Решение принимается по снимку коммутатора не старше 30 секунд (`SNAPSHOT_SECONDS`): пока другая страница опрашивает коммутатор, `SnapshotCache` отдаёт последний снимок, которому может быть сколько угодно. Порты коммутатора без записи, молчащего или прочитанного давно пропускаются с причиной (`PoeRestart::switchBlocker()`); сначала выключаются порты всех коммутаторов, потом одна пауза, потом каждый коммутатор включает свои по одному. Итог ключуется плиткой: `['label', 'serial', 'why']`. До выключения пишет строку в `poe_outages` (с `switch_id`), затем выключает и читает значение обратно, ждёт 5 секунд и включает порты по одному с шагом 0,5 с. На включение три попытки с чтением обратно. Сбой на одном порту не мешает включить остальные. Отказ коммутатора на выключении, как и запись, после которой порт всё ещё «включено», удаляет строку. Таймаут или предупреждение php-snmp её не удаляют: коммутатор мог выключить порт и потерять ответ, поэтому порт включается вместе с остальными. У загружающейся Raspberry Pi нет серийного номера, и в `cmlogs` пишется пустая строка, потому что колонка `cm` не допускает NULL.
  - Открытая строка с ошибкой или старше 2 минут — порт остался выключенным (`PoeOutage::stayedOff()`). Его показывает плашка `PoeOutages` с кнопками Power on и Forget на дашборде, странице Ports и в карточке модуля; Power on пишет через коммутатор строки (`switch_id`, у строк до 2.4 — по адресу `switch_host`). После перезапуска страница шлёт событие `poe-outages-changed`, и плашка появляется сразу. Страница Ports закрывает такую строку, если объект порта на коммутаторе снова «включено»: `closeSeenOn()` читает его учёткой на чтение, у каждого отвечающего коммутатора — только его строки (`PoeOutage::forSwitch()`). Слова статуса PoE у вендоров разные, а снимок мог быть снят ещё до выключения, поэтому по снимку строки не закрываются.
  - Кнопки: карточка модуля (строка «Power (PoE)»), панель порта и сводка Ports, дашборд («Restart failed (N)» и Restart в строке упавшего или замолчавшего модуля). Дашборд предлагает Restart модулю, если запись есть у его коммутатора (`cms.switch_id`), а модулю без него — если она есть хоть у одного. Строки журнала `cmlogs` пишутся с именем оператора. Строка «Power (PoE)» спрашивает коммутатор уже после показа карточки (`wire:init="loadPower"`): медленный коммутатор не задерживает её открытие.
- Образы `.gz`/`.xz`/`.bz2` принимает обычный контроллер `AddImageController`, потому что Livewire не справляется с большими файлами (лимит 8G задан в `debian/cmprovision` и `postinst`). Файлы лежат в `public/uploads/` под случайными именами, модули качают их напрямую через nginx. SHA256 сжатого и распакованного образа считает задача очереди `ComputeSHA256` (очередь `images`, служба `cmprovision-queue-images`); пока нет `uncompressed_sha256`, проект с `verify` провижинить отказывается.
- Образы из интернета (2.8.0, `docs/operations.md#images-from-the-internet`). Окно `ImageSources` на странице Images (Livewire, вкладки GitHub release / Raspberry Pi OS / любая ссылка; списки лежат в `#[Locked]` свойствах: адреса из них скачиваются) просит, проверяет и ставит скачивание; скачивает цепочка задач очереди `images`:
  - Запись образа (`images`): `source_type` (`github`, `raspberrypi`, `url`; пусто у загруженного из браузера), `source` (JSON для людей, адрес без query), `download_url` (полный адрес источника с query, приведение `encrypted`, скрыт из JSON API), `download_state` (`queued`, `downloading`, `converting`, `checking`, `failed`; пусто — образ принят), `download_bytes`/`download_total`, `download_error`, `expected_sha256` (файла как опубликован), `expected_uncompressed_sha256`, `checksum_source`. `Image::isReady()` (state и error пусты) обязано стоять везде, где образ выбирают или пишут: форма проекта и её образ по умолчанию, `Projects::store()`, старт модуля (`ScriptExecuteController`: `notReadyReason()` — отказ), `PATCH /api/projects`; загруженный из браузера образ готов всегда.

  - `DownloadImage` — один ломоть (`image_download_slice`, 45 с, меньше `retry_after` очереди): докачивает с байта из `.part` через `ImageFetcher::download()` и ставит следующий ломоть в хвост очереди, так что хеши и копии кусками других образов не ждут часами; сбой — повтор через 5/15/30/60 с и дальше через 120 с (`BACKOFF_MAX`), двенадцатый подряд (около четверти часа; на живой проверке пять сбоев за 110 с сдались при обрыве в 150 с) или двенадцать ломтей без байта проваливают образ, обрыв, после которого `.part` вырос, считается за один сбой, причина ожидания — в кэше `image-retry:<id>` и в строке образа; `tries` = 3: убитый воркер (питание, OOM) оставляет задачу занятой на `retry_after` (90 с), потом очередь запускает ломоть снова с `.part`; сервер без Range (ответил 200 на докачку, `ignoredRange`) не умеет складывать ломти: файл либо приходит за один ломоть, либо образ проваливается с этой причиной; замок `image-fetch-<id>` не даёт ломтям одного образа идти вместе; `failed()` не оставляет образ «скачивающимся».
  - `ImageFetcher` (curl): `probe()` (размер, докачка, имя — запросом `Range: bytes=0-0`), `download()` (Range, 200 вместо 206 или изменившийся размер — с начала, обрыв оставляет принятое, застой замечает сама по XFERINFO: у curl скорость усредняется за пять секунд), `text()` (маленький файл суммы). Всё через `ImageUrlGuard`: только https к публичным адресам (частные, loopback, link-local, CGNAT, мультикаст, адреса, несущие IPv4, числовые хосты, `user:password@` — отказ), каждый адрес разрешается до подключения и соединение закрепляется за выбранным (`CURLOPT_RESOLVE`), перенаправления идут по одному и проверяются, не больше пяти. Настройка `image_test_loopback` (только тесты) разрешает http к loopback. Больше объявленного размера сервер не присылает (`receive()` обрывает). `ImageSourceException` несёт `fatal` (повтор не поможет) и `status` (HTTP).
  - Суммы: `ImageChecksums` разбирает `.sha256`, `SHA256SUMS` и голый hex; `GitHubReleases` (кэш 5 минут, лимит API без токена 60 в час — сообщение с временем сброса; только ассеты из релизов самого репозитория) выбирает сумму по порядку digest → `.sha256` рядом → список релиза, расходящиеся суммы останавливают; `RaspberryPiCatalog` (кэш час) берёт `extract_sha256` распакованного образа из каталога Imager и `.sha256` рядом (404 — не ошибка).
  - Проверка — в `ComputeSHA256` для образа с `source_type` в состоянии `checking`: сумма файла и сумма распакованного сверяются с ожидаемыми, несовпадение, как и файл, который не распаковывается, удаляет файл и проваливает образ (Retry качает заново), ошибка самой задачи проваливает образ через `failed()` с файлом (у задачи одна попытка; временная ошибка не повод качать заново).
  - `ConvertImageArchive` (`.zip`): сумма архива, ровно один `.img` (папки и `__MACOSX` не в счёт), поток записи архива идёт в `nice gzip -6` без распакованной копии, CRC32 записи сверяется, потом новый файл занимает место архива, архив удаляется, дальше `ComputeSHA256`. Прогресс — доля размера архива.
  - `ImageSpace`: нужно размер + резерв (`image_reserve_gb`, 2 ГиБ) + остаток идущих скачиваний, `.zip` ещё и 1,3 размера под результат; `unused()` — образы без проекта, не в пути и не в прогоне модуля, который не закончен (любая фаза кроме `done`/`failed`: скрипт уже называет файл), их удаляет кнопка Delete unused images. 32-битный PHP: функция выключена (`start()` отказывает).

Пересборка внутри транзакции удалила бы каскадом строки `project_script` и проекты у модулей и партий: внутри транзакции SQLite не выключает внешние ключи. - События `CmProvisioningStarted`, `CmProvisioningComplete` и `CmProvisioningFailed` (причина в `phase_detail`) — точки расширения: авто-обнаружение событий включено (`EventServiceProvider::shouldDiscoverEvents()`), слушателю достаточно лежать в `app/Listeners`.
- Уведомления: каналы в таблице `notification_channels` (типы — `NotificationChannel::TYPES`, настройка на странице Settings, компонент `NotificationSettings`), отправка — `App\Services\Notifier`. Слушатель `SendProvisioningNotifications` пишет событие в `notification_outbox` (строка на каждый включённый канал), отправляет задача `FlushNotifications` (очередь `notifications`) через окно `WINDOW` (10 с) пачками: чату — сообщение на партию с частями по событиям, на которые он подписан (длиннее 4000 символов делится по строкам), JSON webhook — запрос на событие. Сводка правится раньше ответов, и каждое сообщение помечает свои события отправленными: 429 посреди пачки ничего не шлёт дважды. Другая ошибка правки (сводку удалили в чате) ответы не держит и остаётся в `last_error`. Упавший прогон ставит следующий (`FlushNotifications::failed()`); ошибка записи события в очередь до модуля не доходит (слушатель её ловит). Между вызовами к одному чату не меньше секунды (`Notifier::pace()`), 429 откладывает канал на `retry_after` (кэш `notify-blocked:<id>`), ошибка — повтор через 30 с (до того канал не трогает и прогон, поставленный новым событием), после 5 попыток событие снимается с `error`; отправленные события хранятся `KEEP_DAYS` (7 дней). Сводку, которую начал публиковать и не дописал убитый процесс (пустой `external_id` старше минуты), публикует следующий прогон. Строки выключенного канала снимаются, удалённого — уходят каскадом, события удалённого модуля пропускаются. Адрес Bot API — `config('cmprovision.telegram_api')` (`TELEGRAM_API`: заглушка репетиции). Кнопка Test шлёт сразу. В JSON вебхука есть `board` и отдельно `switch` и `port` (пустые без коммутатора). Модули одного проекта объединяются в партию (`notification_batches`, `cms.notification_batch_id`), которая закрывается через `NotificationBatch::IDLE_HOURS` простоя, при смене проекта или кнопкой. Партию выбирает `NotificationBatch::current()` под замком `notification-batch`: волна стартов попадает в одну. Боты (Mattermost, Telegram) держат на партию тред: сводку правят после каждой пачки свежими числами, модули идут ответами. Только один процесс публикует сводку, это гарантирует уникальный ключ `notification_threads`. Ошибки отправки пишутся в `last_error` канала и до модуля не доходят. Сертификат сервера (`App\Services\TlsTrust`; типы `NotificationChannel::TLS_TYPES` — Mattermost bot и оба webhook): канал может доверять своим сертификатам (настройка `tls_ca` в PEM и `tls_ca_for` — «host:port», для которого они сохранены; на другом адресе они не действуют) или не проверять сертификат вовсе (`tls_insecure`). Сертификаты уходят в curl через `CURLOPT_CAINFO_BLOB` в дополнение к системным CA (каталог CA curl остаётся), имя хоста проверяется. curl по умолчанию принимает доверенным и не корневой сертификат (partial chain), поэтому промежуточный CA из цепочки сервера переживает перевыпуск сертификата; отсюда зависимость пакета от php-curl. Кнопка Fetch from the server (`TlsTrust::fetch()`) берёт цепочку, которую предъявляет сервер, и предупреждает, если сертификат выписан на другое имя. Ошибке сертификата `TlsTrust::explain()` ставит в начало подсказку, что делать (о своём сертификате — только каналам, у которых он бывает): таблица каналов показывает только начало `last_error`. Тексты ошибок для страницы готовит `Notifier::errorText()`: Guzzle пишет в сообщение URL запроса, а в URL Telegram — токен бота, поэтому `Notifier::redact()` его вырезает. `TlsTrust::fetch()` — метод экземпляра из контейнера: тест подменяет сеть.
- При обновлении пакета `postinst` выполняет только `migrate`, сидеры запускаются лишь при первой установке. Данные для существующих установок добавляйте миграцией.
- `postinst` не должен падать: запуск служб (`#DEBHELPER#`) стоит в его конце, и после ошибки сервер остаётся без dnsmasq и очереди до следующего успешного configure. Команды artisan там — только с `--force` (в `.env` стоит `APP_ENV=production`).
- `postinst` на каждом configure идемпотентно правит окружение существующих установок: `send_timeout` для `/uploads/` в сайте nginx, `upload_tmp_dir = storage/app/upload-tmp` в php.ini (на Debian 13 `/tmp` в RAM), `APP_ENV=production`/`APP_DEBUG=false` в `.env` вместо значений из старого шаблона. Новые правки такого рода добавляйте туда же, а не только в шаблоны: сайт nginx и `.env` при обновлении не перезаписываются.
- Время хранится в UTC, показывается в `config('app.display_timezone')` (`APP_DISPLAY_TIMEZONE` или системный пояс сервера) через макрос `Carbon::local()`; CSV-экспорт и API отдают UTC. Системный пояс читает `App\Support\SystemTimezone` из `/etc/timezone` или ссылки `/etc/localtime`: спрашивать PHP нельзя — PHP 8.4 в Debian 13 возвращает UTC при любом поясе системы, и `date.timezone` по умолчанию там тоже `UTC`.

- Значок подключения сервера в верхней панели — компонент `UplinkIndicator`, один экземпляр на все размеры экрана. Данные собирает `App\Services\NetworkStatus` так, как может пользователь www-data:
  - маршрут по умолчанию — из `/proc/net/route`;
  - тип, шина и драйвер интерфейса — из `/sys/class/net`;
  - Wi-Fi — через `iw dev <if> link|info` (`App\Support\WifiLink`, поколение по признакам HT/VHT/HE/EHT);
  - адреса — из `net_get_interfaces()`;
  - «предпочтительное подключение не подключено» — по профилям `nmcli` с меньшей метрикой.

  Состояние холодного запаса встроенного Wi-Fi `NetworkStatus` читает из `/run/cmprovision/uplink-spare`. При аварии карты предупреждение значка берётся из этого состояния (`state=active`): с одним профилем на обе карты неподключённого «предпочтительного» профиля нет. В подсказке — ссылка на Settings → Wi-Fi networks. Тексты значка и подсказки готовит `App\Support\UplinkSummary`. Снимок лежит в кэше под ключом `network-status`. Значок сам обновляется раз в `POLL_SECONDS` (300 с) и берёт снимок не старше `PASSIVE_MAX_AGE`, а наведение или нажатие — не старше `FRESH_MAX_AGE` (10 с).
